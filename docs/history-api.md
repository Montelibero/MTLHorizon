# Исторический API: маршруты, форматы и отклонения от upstream

Этап 06, раздел 8 задания. Код — [`app/history_api/`](../app/history_api);
приложение подключает его в корень: `from app.history_api import build_router`,
`app.include_router(build_router(engine, settings))`.

API читает только локальную PostgreSQL и ни при каком запросе не обращается к
Horizon. Это не обозреватель и не замена Horizon:

| | |
| --- | --- |
| Отвечает | тем, что установка успела собрать о выбранных аккаунтах и рынках |
| Не отвечает | текущими балансами, леджерами, офферами, аккаунтом как объектом сети, потоком событий (SSE), приёмом транзакций |
| Пустой список | «в этом архиве этого нет», а не «этого не было в сети» |
| 404 | «этого нет в этом архиве», а не «этого не существует»; в самом ответе так и сказано |

Форма ответов — та, что у Horizon `30.0.1-6f7cff39`; факты о ней — в
[`horizon-schema.md`](horizon-schema.md). С живым сервером ничего не
сверялось: сравнивать не с чем, кроме сохранённых ответов, — и сравнивается с
ними (раздел 13).

| Модуль | Что в нём |
| --- | --- |
| `router.py` | маршруты; то, через что проходит каждый (`Guarded`: база, доступ, ошибки) |
| `access.py`, `problems.py` | политика доступа; problem-документы |
| `params.py`, `paging.py` | чтение параметров, курсоров; ссылки страницы |
| `streams.py` | SQL: страницы как проходы по индексам, чтение в транзакции только для чтения |
| `records.py` | строки базы → записи Horizon со своими ссылками |
| `manage_data.py`, `aggregations.py`, `coverage.py` | то, что в разделах 8–10 |

## 1. Доступ

| `MTL_HORIZON_API_ACCESS` | `MTL_HORIZON_API_TOKENS` | Кто читает | Чужим отвечают |
| --- | --- | --- | --- |
| `open` (как в `compose.yaml`) | любые | всякий, кто достиг API: архив публичный | — |
| `token` | заданы | держатель одного из токенов | 401 |
| `token` | пусты | никто: закрыто | 403 |

`open` — режим установки: он задан в `compose.yaml`. Само приложение без
этой настройки ведёт себя как в режиме `token`, поэтому установка, поднятая
не по этому файлу, закрыта, пока `open` не сказано.

Токен передаётся только в заголовке `Authorization: Bearer <token>`. Каждый
настроенный токен сравнивается с предъявленным за постоянное время, и все
сравниваются всегда: время ответа не говорит, каким по счёту был бы верный.
Токен не повторяется в ответе и не попадает в журнал; 401 одинаков для
«нет токена» и «неверный токен».

Без базы (движок `None`) каждый маршрут отвечает 503 — раньше, чем смотрит на
токен: такие ответы ничего не открывают, а `/ready` и так говорит о базе
открыто.

Заголовок `Cache-Control: no-cache, no-store, max-age=0` стоит на каждом
ответе, как у upstream. CORS не настроен: страница админки читает API со
своего origin, а открывать чтение с чужих страниц токену не нужно.

Политику для 401 и 403 пришлось дать свою: у Horizon нет таких ответов, а
выдумывать адреса под `https://stellar.org/horizon-errors/` нельзя. Тип там
`about:blank`, смысл — в `title` (раздел 11).

## 2. Маршруты

Все — `GET`. Других методов нет: `POST` на любой из них отвечает 405.

| Маршрут | Что отвечает | upstream |
| --- | --- | --- | --- |
| `/accounts/{account_id}/transactions` | транзакции, в которых аккаунт — участник | есть |
| `/accounts/{account_id}/operations` | операции, в которых аккаунт — участник; расширение: фильтр по типу и по данным | есть |
| `/accounts/{account_id}/effects` | эффекты аккаунта | есть |
| `/accounts/{account_id}/trades` | сделки, где аккаунт — любая из сторон | есть |
| `/transactions` | локальная выборка: все транзакции архива по курсору | есть, но у upstream — весь поток сети |
| `/transactions/{transaction_hash}` | транзакция; fee-bump находится и по внешнему, и по внутреннему хешу | есть |
| `/transactions/{transaction_hash}/operations` | операции транзакции, и неудачной тоже | есть |
| `/transactions/{transaction_hash}/effects` | эффекты транзакции (у неудачной — пусто) | есть |
| `/operations` | локальная выборка: все операции архива по курсору | есть, у upstream — поток сети |
| `/operations/{id}` | операция | есть |
| `/operations/{id}/effects` | эффекты операции | есть |
| `/effects` | локальная выборка: все эффекты архива по курсору | есть, у upstream — поток сети |
| `/trades` | сделки архива; с парой активов — сделки рынка в заданной ориентации | есть |
| `/trade_aggregations` | корзины рынка | есть |
| `/v1/coverage` | покрытие и контекст субъекта | нет, расширение установки |

Чего намеренно нет, хотя есть у upstream: `/ledgers`, `/accounts/{id}`
(объект аккаунта с балансами), `/accounts/{id}/data/{key}`, `/assets`,
`/offers`, `/payments`, `/operations/{id}/trades` (нет и у upstream),
корень `/`. `/payments` не сделан: платежи выбираются из
`/accounts/{id}/operations?type=payment` (параметр этой установки, раздел 7), а
полнотой совместимости это не назовёшь.
Запрос по маршруту, которого здесь нет, получает обычный 404 приложения
(`{"detail": "Not Found"}`), не problem-документ: маршрут не наш.

Глобальные `/transactions`, `/operations`, `/effects` и `/trades` без пары —
это **не** поток сети. В них только то, что пришло через наблюдаемые аккаунты
и рынки; каждая такая страница говорит об этом в члене `scope`.

## 3. Параметры

Общие для потоков:

| Параметр | Значения | По умолчанию | Неверно |
| --- | --- | --- | --- |
| `cursor` | курсор записи того же потока или `now` | начало потока | 400, `invalid_field: cursor` |
| `order` | `asc`, `desc` | `asc` | 400 |
| `limit` | целое 1…200 | 10 | 400 |
| `include_failed` | логическое, как читает Go: `true`/`false`, `1`/`0`, `True`… | не задан | 400 |

`include_failed` действует в потоках транзакций и операций: без него
неудачные транзакции и их операции скрыты, как у upstream. В потоках эффектов
и сделок параметр принимается и ничего не меняет — у неудачной транзакции нет
ни того, ни другого. Операции неудачной транзакции всегда доступны, когда её
спрашивают саму (`/transactions/{hash}/operations`), тоже как у upstream.

Только для сделок: `trade_type=orderbook|liquidity_pool` и пара активов.
Пара задаётся как у upstream: `base_asset_type` и `counter_asset_type`
(`native`, `credit_alphanum4`, `credit_alphanum12`), для не-native — ещё
`*_asset_code` и `*_asset_issuer`. Назван один актив пары без другого — 400.
Пара в любом порядке: одна и та же сделка, стороны переставлены (раздел 5).
Актив без пары, например `base_asset_type=native` один, — ошибка, не «все
сделки с XLM»: фильтра по одному активу у upstream нет, и выдумывать его здесь
не стали.

Параметры, которых здесь не знают (например, `join=transactions`), игнорируются
— как их игнорирует upstream.

`/trade_aggregations` и `/v1/coverage` — в разделах 9 и 10. Все параметры
страницы, которые поняты, повторяются в её ссылках, так что переход по `next`
фильтр не теряет.

## 4. Страницы и ссылки

Страница — HAL, `application/hal+json`:

```json
{
 "_links": {
  "self": {"href": "https://horizon.example.org/accounts/G…/transactions?cursor=&include_failed=true&limit=1&order=asc"},
  "next": {"href": "https://horizon.example.org/accounts/G…/transactions?cursor=429496729600&include_failed=true&limit=1&order=asc"},
  "prev": {"href": "https://horizon.example.org/accounts/G…/transactions?cursor=429496729600&include_failed=true&limit=1&order=desc"}
 },
 "_embedded": {"records": [ … ]},
 "scope": { … }
}
```

Ссылки строятся здесь, а не берутся из сохранённого ответа источника:

- `self` — запрос как он был понят: `cursor` (пустой, если не задан), `limit`,
  `order` и остальные понятые параметры, по алфавиту, как у upstream;
- `next` — тот же запрос с курсором последней записи страницы;
- `prev` — с курсором первой записи и обратным порядком.

У пустой страницы курсор в ссылках пуст или повторяет запрошенный. `next`
есть у каждой страницы, включая последнюю и пустую, — как у upstream; страница
короче лимита — последняя, и ссылка об этом ничего не говорит.

Адрес — эта установка: `MTL_HORIZON_PUBLIC_ORIGIN`, если задан, иначе база
запроса. Ссылки с чужим host не отдаются никогда: сохранённый `raw` содержит
`_links` сервера-источника, и они отбрасываются при выводе (раздел 5).

Записи несут свои `_links` с теми же именами, что у upstream. Три из них ведут
к маршрутам, которых эта установка не обслуживает: `account` и `ledger` у
транзакции, `base` и `counter` у сделки (аккаунт или пул ликвидности). Имена и
пути оставлены как у upstream — клиент находит то, что ищет, — а переход по
ним даёт 404 приложения. Ссылка `self` у сделки пуста, как у upstream: маршрута
одной сделки у Horizon нет.

## 5. Записи

Запись собирается из двух мест. То, что знают колонки, берётся из колонок:
база проверяет их согласованность, и они не зависят от того, в каком виде
источник ответил в этот раз. Остальное — члены, свойственные типу записи
(`amount`, `from`, `path` у операции, `preconditions` у транзакции), — из
сохранённого ответа источника (`raw`). Строки без `raw` (возможны у будущего
импорта) отдают только первое: этих членов не будет. Отсутствующее не
придумывается: `result_meta_xdr` появляется, только если он хранится (публичный
Horizon его не отдаёт, и обычно его нет), `fee_meta_xdr` — только если хранится.

Суммы, цены, последовательности — строки, как у upstream; чисел с плавающей
точкой в ответах нет (проверено тестом по всем маршрутам).

**Транзакция.** `id`, `hash`, `signatures` зависят от того, по какому хешу её
спросили, как у upstream: по внешнему хешу fee-bump (или в потоке) — внешние
`id`, `hash` и подписи fee-bump; по внутреннему — внутренние. Внешний хеш
всегда в `fee_bump_transaction.hash`; `paging_token` от способа запроса не
зависит. `max_fee` — плата fee-bump, `inner_transaction.max_fee` — внутренней
транзакции. `fee_account` — плательщик (у обычной транзакции — её источник).

**Операция.** `transaction_successful` и `transaction_hash` — от транзакции
(хеш внешний, как у upstream). Тип, которого код не знает, остаётся как
хранился: `type: "unknown"` с настоящим `type_i`.

**Сделка** строится из одних колонок. Хранится она в ориентации источника;
если рынок спросили другой стороной, base и counter меняются местами вместе с
суммами, счетами, офферами, `base_is_seller` и ценой (`n` и `d` меняются
местами). `id` и `paging_token` от ориентации не зависят. Для сделки пула:
`trade_type: "liquidity_pool"`, `liquidity_pool_fee_bp`, `*_liquidity_pool_id`
вместо счёта и оффера на стороне пула. Цена `0/0` — так upstream показывает
сделку без сохранённой цены (очень старые записи).

**Эффект.** `id` дополнен нулями, `paging_token` — нет; оба кодируют пару
(операция, номер), как у upstream.

## 6. Курсоры

| Поток | Курсор | Где в записи |
| --- | --- | --- |
| транзакции | Total Order ID (SEP-35), часть операции 0 | `paging_token` |
| операции | Total Order ID | `id` = `paging_token` |
| эффекты, сделки | `<operation id>-<order>` | `paging_token` (= `id` сделки) |

Правила — как у upstream ([`horizon-cursors.py`](../app/sources/horizon_cursors.py),
раздел 4 `horizon-schema.md`):

- тот же курсор в другом порядке читает в другую сторону: `asc` — что после
  него, `desc` — что до него; сама запись с этим курсором не повторяется;
- без курсора `asc` начинается с самой старой записи, `desc` — с самой новой;
- `now` — «после всего в последнем леджере архива»: `desc` отдаёт новые записи,
  `asc` — пустую страницу. Установка не знает последнего леджера сети и не
  делает вид, что знает;
- для эффектов и сделок курсор одним числом означает «эта операция и любой
  номер»: читается всё, что дальше по номеру операции; второй компонент
  обрезается до `MaxInt32`;
- не число, отрицательное число, больше int64, пара там, где ждут одно число,
  три компонента — 400 с `invalid_field: cursor`.

Курсоры стабильны (это позиции в базе, не смещения) и непрозрачны для клиента.
410 `before_history` не отдаётся никогда: у архива нет одной границы удержания.
То, что источник уже не может подтвердить, названо в `/v1/coverage`
состоянием `unverifiable`.

## 7. Расширения ответа

Клиент, написанный под Horizon, этих членов не заметит; они для тех, кто знает
о них.

**`scope` — на каждой странице и в `/trade_aggregations`:**

| `kind` | Что говорит | `coverage` |
| --- | --- | --- |
| `account` | здесь только то, что собрано об аккаунте | `/v1/coverage?account=…` |
| `market` | … о рынке | `/v1/coverage?base_asset=…&counter_asset=…` |
| `archive` | локальная выборка, не поток сети | — |
| `transaction` | список при одной транзакции | `/v1/coverage?transaction=…` |
| `operation` | эффекты одной операции | тот же, транзакции |

`note` — то же словами. Для `transaction` и `operation` есть ещё
`context_loaded` (логическое): `false` означает, что транзакция хранится без
полного контекста и список может быть неполным — так бывает при импорте в
режиме `parents`, по умолчанию у очереди истории. `true` — операции, эффекты
или сделки прочитаны у источника целиком; для операций `true` ставится и тогда,
когда хранится столько операций, сколько транзакция говорит, что у неё есть.

**`data_change` — в записях операций `manage_data`** (раздел 8).

**Параметры `/accounts/{id}/operations`:** `type` (имя типа, как у Horizon,
или его номер), `data_name`, `data_value` (раздел 8). У upstream таких
параметров нет, и там они были бы молча проигнорированы.

## 8. manage_data

Horizon показывает `value` операции `manage_data` пустой строкой и когда
запись удаляется, и когда записывается пустое значение — по операции их не
отличить. Здесь их отличает то, что хранится, в таком порядке:

1. **конверт транзакции (XDR).** Сама операция говорит, несёт ли она значение
   или удаляет запись; в XDR три случая различимы — байты, пустые байты и
   «нет значения». Читается и обычный конверт, и fee-bump;
2. **эффект операции**, если эффекты собраны: `data_removed` против
   `data_created` и `data_updated`;
3. иначе — `unknown`; ничего не предполагается.

Если конверт и эффект противоречат друг другу, ответ тоже `unknown`: одно из
двух хранится не тем, чем является. Для транзакции, которая не прошла, эффектов
нет, и говорит только конверт — о том, что операция *просила*. Применилось ли
это — в `transaction_successful` самой записи.

```json
"name": "config", "value": "aGVsbG8=",
"data_change": {"request": "set", "told_by": "xdr", "value": "aGVsbG8=", "effect": "data_created"}
```

| Член | Значения |
| --- | --- |
| `request` | `set` (записать значение, возможно пустое), `remove` (удалить), `unknown` |
| `told_by` | `xdr`, `effect` или `null` |
| `value` | base64, как показывает Horizon; только для `set` и когда известно |
| `effect` | имя сохранённого эффекта записи данных этой операции или `null` |

Обычные члены `name` и `value` остаются как у upstream (удаление и пустое
значение — оба `""`), чтобы клиент Horizon видел привычное.

Фильтры в `/accounts/{account_id}/operations`:

| Параметр | Что оставляет |
| --- | --- |
| `type=manage_data` (или `type=10`) | операции этого типа |
| `data_name=…` | операции с таким `name` |
| `data_value=…` | операции, у которых сохранённый `value` равен этому (base64) |

`data_value=` (пустой) — сам по себе фильтр: записи с пустым `value`, то есть
удаления вместе с пустыми значениями; различает их `data_change`. Имя и
значение читаются из сохранённого ответа источника; строка без него фильтру не
соответствует, потому что показать соответствие нечем.

## 9. Aggregations

`GET /trade_aggregations` — корзины рынка: счёт, объёмы, средняя цена и цены
открытия, закрытия, максимума и минимума. Данные для графика в админке; годится
и внешнему клиенту.

Параметры как у upstream: пара активов (обязательна, раздел 3), `start_time` и
`end_time` (миллисекунды эпохи, `end_time` больше `start_time`; сделки с
`start_time ≤ время < end_time`), `resolution` — ровно одно из `60000`,
`300000`, `900000`, `3600000`, `86400000`, `604800000` (1, 5, 15 минут, час,
сутки, неделя), `order` (по умолчанию `asc`), `limit` (по умолчанию 10, не
больше 200), `offset` (по умолчанию 0).

Формулы — те, что этап 03 сверил с живым сервером; они вызываются из
[`app/backfill/verify.py`](../app/backfill/verify.py), а не написаны второй раз:

- `trade_count`, `base_volume`, `counter_volume` — счёт и суммы сторон в
  ориентации запроса;
- `avg` — объём counter к объёму base, семь знаков; точного `avg_r` нет, как и
  у upstream. Если объём base корзины нулевой, делить не на что: отдаются счёт
  и объёмы, без средней и цен;
- `high`, `low` — наибольшая и наименьшая из **цен сделок** (не отношения
  сумм: для сделки через пул они расходятся), `open` и `close` — цены первой и
  последней сделки корзины по порядку операций.

Корзины нарезаны по границам, кратным разрешению от эпохи, то есть по UTC.
Отдаются только корзины с сделками: пустой интервал — без корзины, как у
upstream. Первая и последняя корзины периода могут быть обрезаны его краями;
upstream их не помечает, и здесь тоже.

```json
{"timestamp": "1767225600000", "trade_count": "2",
 "base_volume": "9.8650872", "counter_volume": "46.3659098", "avg": "4.7000000",
 "high": "4.7000000", "high_r": {"n": "47", "d": "10"},
 "low": "4.7000000", "low_r": {"n": "47", "d": "10"},
 "open": "4.7000000", "open_r": {"n": "47", "d": "10"},
 "close": "4.7000000", "close_r": {"n": "47", "d": "10"}}
```

`*_r` — дробь той сделки, из которой взята цена, как она хранится, без
сокращения: в сохранённых ответах живого сервера они не сокращены
(`93088/30880`, а не `5818/1930`). Состав и типы членов сверены с сохранённым
ответом живого сервера (`tests/fixtures/history_api/trade_aggregations_live.json`).
Сделки пула входят. Обе ориентации пары дают одни объёмы, переставленные, и
взаимно обратные цены. `_links` нет, как у upstream; переход страницами —
`offset` и `limit`.

## 10. /v1/coverage

`GET /v1/coverage` — `application/json`. Один субъект на запрос:

| Субъект | Параметры |
| --- | --- |
| аккаунт | `account=G…` |
| рынок | `base_asset=CODE:ISSUER&counter_asset=…` (или `native`), в любом порядке |
| транзакция | `transaction=<hash>` (любой из двух хешей fee-bump) |

Два субъекта сразу, ни одного, неверный адрес или актив — 400; транзакции нет
в архиве — 404. Неизвестный аккаунт или рынок — не ошибка: ответ говорит, что о
нём ничего не проверено.

Покрытие — утверждение о диапазоне, а не следствие наличия строк
(`architecture.md`, раздел 5). Ответ различает три вещи:

- `policies[].ranges` — что проверено, с состоянием каждого диапазона:
  `complete`, `empty`, `pending` (не прочитано), `unverifiable` (источник уже не
  ответит) и, у него, `detail` — почему;
- `policies[].window` — что планировалось, в самом широком виде: вне его ничего
  не утверждается;
- `stored` — до каких леджеров доходят сохранённые записи потока на самом
  деле: живые события и другие потоки приносят записи и вне проверенных
  диапазонов.

```json
{
 "subject": {"type": "account", "id": "G…"},
 "tracked": {"enabled": true, "origin": "yaml", "discovered_by": null,
             "watch_since_ledger": null, "boundary_due": true},
 "import": {"state": "waiting", "from_ledger": null, "to_ledger": 130, "…": "…"},
 "archive": {"oldest_ledger": 100, "newest_ledger": 118},
 "streams": {
  "transactions": {
   "stored": {"first_ledger": 110, "last_ledger": 118},
   "policies": [{"policy": "FULL", "policy_version": 1,
                 "window": {"from_ledger": 100, "to_ledger": 130},
                 "ledgers": {"complete": 20, "empty": 0, "pending": 11, "unverifiable": 0},
                 "ranges": [{"from_ledger": 100, "to_ledger": 110, "state": "pending",
                             "verified_at": null, "detail": null, "source": "horizon:pool"},
                            "…": "…"}]}
 },
 "complete": false,
 "incomplete": ["transactions: pending, not read yet — ledgers 100–110",
                "transactions: nothing is claimed below ledger 100 or above ledger 130",
                "…": "…"],
 "statement": "This is what the archive collected for this account, not its history on the network. …"
}
```

(Пример собран из двух ответов теста: `import` — отдельного запроса после
постановки задания; `"…": "…"` — сокращение.)

`incomplete` — каждый способ, которым поток не является полной историей
субъекта, словами: что `pending`, что `unverifiable` и почему, ниже и выше
какого леджера ничего не утверждается, где сохранённые записи выходят за
проверенное окно. `complete` всегда `false`: архив выбранных аккаунтов не может
знать, что держит всё, что случилось с одним из них.

Для рынка — поток `trades` и те же члены. Для транзакции:

```json
{"subject": {"type": "transaction", "hash": "…", "transaction_hash": "…",
             "inner_transaction_hash": null, "id": "536870912000", "ledger": 125,
             "successful": true},
 "context_loaded": [],
 "context": {"operations": {"complete": false, "stored": 1},
             "effects": {"complete": false, "stored": 1},
             "trades": {"complete": false, "stored": 0}},
 "incomplete": ["operations: not loaded as a whole; 1 are stored, and there may be more",
                "effects: not loaded as a whole; 1 are stored, and there may be more",
                "trades: not loaded as a whole; none are stored, and there may be some"],
 "statement": "…"}
```

`context_loaded` — сохранённый список частей, прочитанных у источника целиком
(`architecture.md`, раздел 11); `context.*.stored` — сколько записей каждой
части хранится. Для неудачной транзакции сказано, что у неё нет эффектов и
сделок в сети.

`import` — задание истории субъекта, как его держит очередь (`history_job`);
`null`, если задание не планировалось. `tracked` — наблюдается ли субъект;
`null` — не числится. `archive` — старейший и новейший леджер, для которых
что-то хранится. Какой сервер пула прочитал диапазон, не говорится: называется
логический источник, не серверы за ним.

Счётчиков записей нет: `COUNT` по активному аккаунту стоит пропорционально
его истории, а границ (`stored`) хватает, чтобы увидеть, где записи есть.

## 11. Ошибки

| Статус | `type` | `title` | Когда |
| --- | --- | --- | --- |
| 400 | `…/horizon-errors/bad_request` | Bad Request | параметр не читается: `extras.invalid_field` называет его |
| 404 | `…/horizon-errors/not_found` | Resource Missing | транзакции или операции нет в архиве |
| 401 | `about:blank` | Unauthorized | нет токена или он не из настроенных; `WWW-Authenticate: Bearer` |
| 403 | `about:blank` | Forbidden | доступ по токену, а токены не настроены |
| 500 | `…/horizon-errors/internal_server_error` | Internal Server Error | сбой в запросе; причина — в журнале, не в ответе |
| 503 | `…/horizon-errors/service_unavailable` | Service Unavailable | нет базы; база не отвечает; запрос остановлен по времени |

`…` — `https://stellar.org`. Тело — `application/problem+json`:
`type`, `title`, `status`, `detail`, для 400 ещё `extras`. Значение параметра,
которое не прочиталось, в ответе не повторяется.

```json
{"type": "https://stellar.org/horizon-errors/bad_request", "title": "Bad Request", "status": 400,
 "detail": "cursor is not a paging token of this stream: a total order id, or now",
 "extras": {"invalid_field": "cursor"}}

{"type": "https://stellar.org/horizon-errors/not_found", "title": "Resource Missing", "status": 404,
 "detail": "the transaction is not in this archive; this says nothing about the network"}
```

400 предшествует 404: если запрос нельзя понять, об этом говорят и тогда, когда
ресурса в архиве нет.

## 12. Стоимость запросов: EXPLAIN

Каждый запрос идёт в **транзакции только для чтения** (`SET TRANSACTION READ
ONLY`; попытка записи в ней отвергается — проверено тестом) с
`statement_timeout` 10 секунд: тяжёлый запрос отменяется сервером, а запрос
получает 503 с советом спросить уже. Настройки действуют до конца транзакции,
и соединение возвращается в пул прежним. Читатели не берут блокировок и не
мешают писателю.

Каждая страница — `LIMIT + 1`: лишняя строка говорит, полна ли страница. Ни один
поток не читается целиком, чтобы потом отрезать.

Замер — тест `test_a_page_is_a_walk_of_an_index_as_long_as_the_page`
(`local/t.sh tests/test_history_api.py -k walk_of_an_index -s` печатает планы).
База: 1500 леджеров, 7500 транзакций, столько же операций, 15 000 эффектов,
3000 сделок, 30 000 строк участников; строки такой же ширины, как настоящие
(несколько килобайт XDR и JSON), — от этого зависит, сколько страниц в таблице.
Аккаунт, который спрашивают: 150 транзакций, 150 операций, 300 эффектов, 300
сделок. `EXPLAIN (ANALYZE)`, `actual rows` — что реально прочитано:

| Страница | План | Прочитано строк, `limit=10` | `limit=200` |
| --- | --- | --- | --- |
| транзакции аккаунта | Index Only Scan `ix_history_transaction_participants_account` → Index Scan PK транзакций | 11 | 150 (все, что есть) |
| операции аккаунта | Index Only Scan участников операций → PK операций → PK транзакций | 11 | 150 |
| эффекты аккаунта | Index Scan `ix_history_effects_account` | 11 | 150 |
| сделки аккаунта | две ветки: Index Scan `ix_history_trades_{base,counter}_account` → Incremental Sort → Limit; объединение, сортировка | 12 на ветку | 202 |
| `/transactions`, `/effects` архива | Index Scan Backward по первичному ключу | 11 | 201 |
| `/operations` архива | PK операций → PK транзакций | 11 | 201 |
| `/trades` архива | Index Scan `uq_history_trades_operation_order` | 11 | 201 |
| рынок | две ветки: Index Scan `ix_history_trades_market_counter` → Incremental Sort → Limit; Merge Append | 12 на ветку | 202 |
| агрегация за период | Append двух Index Scan `ix_history_trades_market_*` | все сделки периода | — |

То же с курсором в середине (вперёд и назад) — те же планы и те же числа: чтение
начинается от курсора. Ни в одном плане нет Seq Scan и Bitmap Scan. Примеры:

```text
== [limit 10] account transactions, forwards from a cursor
Limit (actual rows=11 loops=1)
  ->  Nested Loop (actual rows=11 loops=1)
        ->  Index Only Scan using ix_history_transaction_participants_account on history_transaction_participants (actual rows=11 loops=1)
              Index Cond: ((account_id = 'G…'::text) AND (transaction_id > '7516192776192'::bigint))
        ->  Index Scan using pk_history_transactions on history_transactions (actual rows=1 loops=11)

== [limit 10] account trades, backwards from a cursor
Limit (actual rows=11 loops=1)
  ->  Sort → Unique → Sort → Append (actual rows=11)
        ->  Limit (actual rows=0)
              ->  Incremental Sort → Index Scan Backward using ix_history_trades_base_account (actual rows=0)
                    Index Cond: ((base_account_id = 'G…') AND (operation_id <= '7516192768001'::bigint))
                    Filter: (ROW(operation_id, trade_order) < ROW('7516192768001'::bigint, 0))
        ->  Limit (actual rows=11)
              ->  Incremental Sort (actual rows=11)   Presorted Key: operation_id
                    ->  Index Scan Backward using ix_history_trades_counter_account (actual rows=12)
                          Index Cond: ((counter_account_id = 'G…') AND (operation_id <= '7516192768001'::bigint))

== [limit 10] market trades, forwards from a cursor
Limit (actual rows=11 loops=1)
  ->  Merge Append (actual rows=11)
        ->  Limit (actual rows=11)
              ->  Incremental Sort (actual rows=11)   Presorted Key: ledger_close_time
                    ->  Index Scan using ix_history_trades_market_counter (actual rows=12)
                          Index Cond: (… asset pair … AND (ledger_close_time >= '…'))
                          Filter: (ROW(operation_id, trade_order) > ROW('7516192768001'::bigint, 0))
        ->  Limit (actual rows=0)  … вторая ориентация пары: таких сделок нет
```

Что нашлось по пути и как исправлено (на пробной базе в 15 000 транзакций):

1. **Курсор не доходил до индекса участников.** Условие стояло только на
   `history_transactions.id`; индекс `(account_id, transaction_id)` его не видел,
   и страница с курсором шла от первой строки аккаунта: 162 строки индекса,
   чтобы отдать 11. Теперь курсор стоит и на колонке участников.
2. **Планировщик недооценивал сделки аккаунта за курсором.** Оценил 29 строк,
   было 300, выбрал Bitmap Scan и ради 11 записей прочитал все 300 страниц.
   Поэтому потоки аккаунта на время одного запроса читаются с выключенными
   bitmap-сканами (`SET LOCAL enable_bitmapscan = off`): остаётся упорядоченный
   проход по индексу, который длиннее страницы, сколько бы строк ни оценивал
   планировщик. Настройка действует до конца транзакции.
3. **Сделки рынка проиндексированы по времени, а не по id.** В порядке id
   страница стоила бы сортировки всех сделок рынка. Время закрытия леджера
   растёт с номером леджера, а номер — старшие биты id операции; поэтому чтение
   идёт от времени закрытия леджера курсора, по времени, с Incremental Sort
   внутри одного момента, который и даёт порядок id upstream.

Если строки узкие (первый вариант пробной базы), планировщик для `limit=200`
выбирал Seq Scan с Hash Join — на маленькой таблице это дёшево и верно; с
настоящей шириной строк выбирает индексы. На настоящей базе планов никто не
видел: цифры выше — из тестовой базы.

Не ограничено страницей и не может быть:

- агрегация читает все сделки периода (ограничена таймаутом);
- `/accounts/{id}/operations?type=…` идёт по индексу аккаунта, пока не
  наберёт страницу подходящих: редкий тип на активном аккаунте стоит прохода
  по всем операциям аккаунта после курсора;
- количество строк меняется при импорте, но планы зависят от статистики, а не
  от момента.

## 13. Отклонения от upstream

| Где | upstream | Здесь | Почему |
| --- | --- | --- | --- |
| член `scope` | нет | на каждой странице и в aggregations | пустой список и короткая страница должны говорить, что они — об архиве |
| `/v1/coverage` | нет | есть | покрытие и неполнота — своими словами (раздел 10) |
| `data_change` в операциях `manage_data` | нет | есть | upstream не различает удаление и пустое значение (раздел 8) |
| `type`, `data_name`, `data_value` у операций аккаунта | игнорирует | фильтруют | задание: фильтр по аккаунту, типу, имени |
| глобальные `/transactions`, `/operations`, `/effects`, `/trades` | поток сети | локальная выборка | у установки нет потока сети |
| ссылки `account`, `ledger`, `base`, `counter` | ведут к ресурсам | те же пути, ресурсов нет | сохранить имена; переход — 404 |
| 401, 403 | нет таких | `about:blank` | не выдумывать адреса `stellar.org` |
| тело 400 | точный текст неизвестен | `type`/`title` upstream, `extras.invalid_field`, свой `detail` | `invalid_field` — из кода upstream (`horizon-schema.md`, раздел 4); дословный `detail` не сверялся |
| 410 `before_history` | есть | никогда | у архива нет одной границы удержания; `unverifiable` — в coverage |
| muxed-адрес в `{account_id}` | принимается (?) | только `G…`, иначе 400 | участники — базовые адреса; поведение upstream не проверялось |
| `resolution` | точный набор не сверялся | 6 значений из задания | раздел 15 |
| `served_by` диапазона | — | не отдаётся | API не называет серверы источника |
| `join` и прочие неизвестные параметры | игнорирует | игнорирует | совпадает |

Что совпадает и проверено против сохранённых ответов живого сервера
(`tests/fixtures/live/`): члены и значения транзакции (fee-bump по внешнему и по
внутреннему хешу), операции, эффектов (девять эффектов одной операции, пары
курсоров), сделок в обеих ориентациях рынка; пути и имена всех ссылок записей и
страниц; `paging_token` всех типов; состав и типы членов корзины агрегации.

## 15. Открытые вопросы

1. **Точные тела ошибок upstream.** `type` и `title` взяты из сохранённого
   ответа 503 и кода; `extras.invalid_field` — из описания кода в
   `horizon-schema.md`. Дословный `detail`, точный список `resolution`, ответ
   на пустую страницу живьём не сверялись: на это этапе 0 внешних запросов.
2. **`limit=200` на активном аккаунте.** На пробной базе планировщик выбирал
   индексы при настоящей ширине строк; на настоящей базе — не измерялось.
3. **Один актив.** `/trades?base_asset_type=native` без пары — 400. Если
   понадобится «все сделки с активом», это фильтр, которого у upstream нет.
4. **`data_value`** фильтрует по сохранённой строке, а не по истинному
   значению из XDR: для удаления и пустого значения результат одинаковый.
   Фильтр по `data_change.request` не сделан.
5. **M-адреса** в `{account_id}` не принимаются; поведение upstream не
   проверялось.
6. **Маршрута нет — 404 приложения**, не problem-документ: обработчик
   ошибок принадлежит приложению, а не маршрутизатору.
