# Отчёт по этапу 05: discovery, подписки и очередь исторического импорта

Этап 05 продолжил проект после этапа 04 (миграция `0006`, 392 теста). Сделаны
три блока задания: обнаружение держателей актива (discovery), управление
подписками Operations Notifier и постоянная очередь исторического импорта.
Аккаунт, попавший в список любым путём, теперь проходит одну жизнь: граница
начала → импорт всей доступной истории → подписка, подтверждённая чтением →
верхняя граница.

Кратко:

- **588 тестов** на настоящей PostgreSQL 17, без внешней сети (было 392).
- **25 исходящих запросов при потолке 20** — потолок **превышен на 5**; все
  25 — один мой незапланированный dry-run discovery (раздел 8). После него
  живых запросов не было.
- Миграции `0007`–`0010` проверены на черновой копии базы пилота (с `0003` и
  с `0006`, с данными) и на dev-базе: история не тронута, `alembic check`
  чистый, откат и повторный накат сходятся.
- Репозиторий Notifier не менялся, ни одной живой подписки не создано, ни
  одного настоящего уведомления не принято. **Автоматическая регистрация
  подписок проверена на встроенном Notifier, а не на настоящем.**
- Пока шёл этап, в Notifier переписали коммит v0.12.0 и вышла v0.13.0; обе
  ревизии сверены по diff и учтены (раздел 2).

## 1. Что сделано

| Блок | Что получилось |
| --- | --- |
| Discovery | Независимый флаг `discover` у актива. Проход читает `/accounts?asset=…` через пул страницами по адресу, считает trustline, а не баланс; о каждой странице хранит, кто и когда ответил. Новые адреса добавляются включёнными, с причиной и источником. Между проходами открытие trustline видно по эффекту `trustline_created` успешной транзакции в сохранённой истории. `python -m app.discovery run/status/on/off` |
| Подписки | Желаемое состояние — из списков наблюдения. Сверка сначала читает список у Notifier и только потом создаёт; активной подписка считается после чтения себя в списке; неоднозначность — человеку. Чужие не трогаются; сделанные вручную принимаются и не удаляются. `python -m app.subscriptions status/reconcile/adopt/release` |
| Жизнь аккаунта | Один проход держит всё в шаге и читает состояние только из базы: граница начала и импорт, подписка, верхняя граница после подтверждения, пауза при отключении, дочитывание после включения. Воркер делает проход в тишине между событиями. `python -m app.watch run/status/add-account/disable-account/enable-account` |
| Очередь истории | Отдельная таблица `history_job`, служба `history`. Срезы над теми же покрытием и чекпоинтами, что и backfill; справедливая, с арендой и восстановлением; `parents` по умолчанию; ниже истории пула — `unverifiable`, не «история начинается здесь». `python -m app.history run/once/status/pause/resume/retry/enqueue` |
| Логический источник | Чекпоинты и покрытие называют источник `horizon:pool`, а не первым сервером списка; миграция `0007` переименовывает и сливает то, что стало одним ключом |
| Порядок запуска | `worker` и `history` проверяют схему при старте и выходят, если миграции не применены; миграции — только командой, до служб |
| Проверки этапа 04 | Четыре вопроса задания проверены, доказанное исправлено; по ходу найдены и исправлены ещё два дефекта, уже в новом коде (раздел 10) |
| Клиент API Notifier | `app/notifier/client.py` и встроенный Notifier для тестов `tests/fake_notifier_api.py`, написанный по коду сервиса |

## 2. Notifier: ревизии, API подписок и форма уведомления

| | |
| --- | --- |
| Репозиторий | `Montelibero/operations-notifier`; только чтение |
| Изучено | `e4039fb` (v0.12.0) — API подписок; `0fb6050` (v0.13.0) — сверено по diff с `e4039fb` |
| Что случилось с ревизией этапа 04 | коммит `cea7e51` (v0.12.0), по которому этап 04 описывал форму уведомления, **переписан** (amend) в `e4039fb` в ходе этого этапа; на ветке его больше нет. `a474e9c` (v0.11.0) не менялся |
| Что переписанный коммит меняет в уведомлении | рядом с базовым `G…`-адресом появляется muxed-вид: `<поле>_muxed` и `<поле>_muxed_id` у `account`, `from`, `trustor` и `source` транзакции (было только у `destination`); базовый адрес остаётся на месте. Успех `create_passive_sell_offer` разбирается, как у других офферов. Подписка по умолчанию получает `filter_version` 2; в идентичность подписки входят владелец и версия правил |
| Что меняет v0.13.0 | доля пула ликвидности пишется как `asset_type: 3` с `liquidity_pool_id` (до этого её записывали как XLM); у операций с пулом — `assets` (пара пула) и `fee`, у сделок пула — `pool_assets`; одна сломанная операция больше не роняет всю транзакцию. Маршруты, валидация запроса подписки и `CURRENT_FILTER_VERSION = 2` не изменились |

Что с этим сделано в читателе уведомлений (`app/notifier/format.py`): базовые
адреса читаются, muxed-поля не мешают; доля пула узнаётся и получает
диагноз «pool share, which has no name here» (имени у неё здесь нет);
пара пула читается из `assets` операции — в сделке пула активы названы в
`asset_sold` и `asset_bought`, как в любой сделке. Такая доставка всё равно
ставится в очередь — как и любая, которую не удалось разобрать до конца.
Форма сверена с примерами `RESPONSE_EXAMPLES.md` ревизии `0fb6050` (раздел
6 этого файла — trustline к доле пула) тестами читателя.

### API подписок (по коду `e4039fb`)

| | |
| --- | --- |
| Маршруты | `GET /api/status`; `GET /api/subscription` (список); `POST /api/subscription` — объект или массив; `GET /api/subscription/:id`; `DELETE /api/subscription/:id`. Изменения нет: `PUT` → 405 `Subscription cannot be modified` |
| Авторизация | `disabled` — без токена; `token` — токен в `X-Access-Token` или `Authorization` (административный действует в любом режиме); режим с ed25519-подписью каждого запроса по nonce клиентом **не поддерживается** |
| Параметры подписки | `reaction_url` (обязателен), `account`, `contract`, `memo`, `asset_code` + `asset_issuer` (XLM — код `XLM` без эмитента), `operation_types`, `filter_version`, `expires`; хотя бы один фильтр; внутри подписки — И |
| Идентичность | владелец + `reaction_url` + фильтры + `filter_version`. Повторный POST того же возвращает существующую — **кроме актива**: хеш считается по запросу до валидации, а `asset_type` дописывает сервис, поэтому второй POST подписки на актив создаёт дубликат |
| Лимиты | `MAX_ACTIVE_SUBSCRIPTIONS` и `MAX_ACTIVE_SUBSCRIPTIONS_PER_USER` (по умолчанию 100). Ответ — **400** с телом `Forbidden. Max active subscriptions exceeded.`, хотя код ошибки внутри Notifier — 403. В режиме `disabled` лимит на пользователя **действует**: все подписки принадлежат анонимному администратору |
| Отказы | на POST — всегда 400 с JSON `{"error": …}`; 401, 403 (чужая подписка при `DELETE`) и 404 — без тела |
| Неизвестный id | `GET /api/subscription/:id` не отвечается вовсе: у обработчика нет ветки для отсутствующей подписки (на Node процесс, скорее всего, падает — запустить Node здесь было нельзя, проверено только по коду). Поэтому каждый запрос клиента идёт с таймаутом, и нет ответа — `NotifierUnavailable` |

Расхождения README Notifier с кодом (верен код): лимит отвечает 400, а не
403; про лимит на пользователя в режиме `disabled` README молчит; «повторный
POST возвращается как есть» для активов неверно.

### Ограничения автоматизации

1. **Живая интеграция не проверена.** Регистрация, подтверждение, снятие и
   приём проверены на `tests/fake_notifier_api.py`, написанном по
   `api/observer-routes.js`, `api/authorization-handler.js`,
   `logic/observer.js`, `logic/storage.js` ревизии `e4039fb`. Что не
   проверено вовсе: настоящее поведение сервиса, его хранилище, его тайминги.
2. **Тысяча аккаунтов не влезает в лимит по умолчанию.** 100 подписок на
   пользователя; владелец Notifier поднимает
   `MAX_ACTIVE_SUBSCRIPTIONS_PER_USER` в его конфиге. Иначе строки остаются в
   `error` с причиной и ждут.
3. **Режим ed25519-подписи запросов** не поддерживается — подписки вручную и
   `adopt`.
4. **Дубликаты подписок на активы не сливаются** сервисом. Сверка поэтому
   сначала ищет в списке; после таймаута создания задубликата не будет. Но
   если подходящих найдено больше одного — состояние `ambiguous`, решает
   человек.
5. **Рынок — не «И» двух подписок.** У Notifier нет И между подписками.
   Рынок покрывается одной подпиской на не-native актив пары (в каждой сделке
   есть оба, а правила v2 матчат операцию по её активам); native для рынка не
   подписывается никогда.
6. **Подписка на актив — не история актива.** Это наблюдение новых событий;
   полная история операций произвольного актива через REST невозможна — у
   Horizon нет такого endpoint.

## 5. Команды

```bash
alias ds='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.discovery'
alias sb='docker compose run --rm api python -m app.subscriptions'
alias wa='docker compose run --rm api python -m app.watch'
alias hi='docker compose run --rm api python -m app.history'

ds on CODE:ISSUER [--reason …]        # ds off CODE:ISSUER
ds run [--asset CODE:ISSUER] [--dry-run] [--resume] [--max-requests N] [--output file.json]
ds status

sb status                              # sb reconcile [--dry-run]
sb adopt --kind {account,asset} --key K --id <id у Notifier> [--no-verify]
sb release --id <строка>

wa add-account G… --reason "…" [--no-pass]     # wa disable-account G…  /  wa enable-account G…
wa status [--examples N]               # wa run

hi status [--examples N]               # hi once
hi pause (--id N | --account G… | --market BASE COUNTER | --all) --because "…"
hi resume (--id N | --account G… | --market … | --all)
hi retry [--id N]
hi enqueue (--account G… | --market BASE COUNTER) [--to-ledger L] [--from-ledger L] [--context parents|full]
```

Службы: `worker` (события и проход по списку в тишине) и `history` (очередь
истории) — обе поднимаются `docker compose up -d`, после миграций.

Порядок запуска: `docker compose up -d db` → `docker compose run --rm api
alembic upgrade head` → `docker compose up -d`.

Horizon, направленным на закрытый локальный порт: ни одного исходящего
запроса.

## 8. Бюджет запросов

Потолок этапа — 20 read-only запросов. Израсходовано **25**: потолок
превышен на 5.

| Запросов | Что |
| --- | --- |
| 25 | **незапланированные по размеру**: `python -m app.discovery run --asset EURMTL:… --dry-run` без `--max-requests` прочитал актив целиком — 24 страницы и root. Намеревался посмотреть 2–3 страницы |

Как вышло: я рассчитывал на 2–3 запроса и не поставил `--max-requests`,
хотя знал, что по умолчанию проход идёт до 1000 запросов. Актив оказался в
4 721 держателя, и проход закрыл его целиком за 24 секунды. Read-only,
dry-run: в базу ничего не записано. Сразу после этого живые запросы в
этапе закончились; журнал — `local/budget-stage05.log`. В помощи к
`--max-requests` теперь сказано, что страница в 200 аккаунтов — один
запрос, и в руководстве предупреждение об этом стоит первым в разделе о
discovery.

**Upgrade с данными, на копии.** Черновая база из `mtl_horizon_pilot_resume`
(этап 03, `0003`; сама пилотная база не тронута и осталась на `0003`):

`alembic check` после каждого наката — `No new upgrade operations detected.`
Черновая база удалена.

**Dev-база: найден и исправлен артефакт разработки.** Оказалась помечена
`0007`, но строки `sync_coverage` оставались `horizon:horizon.stellar.org` и

реальном обновлении такого состояния не бывает (на копии пилота и в тестах
миграция переименовывает). Исправлено честным путём: снимок (`local/backups/`,
не попадает в git) → откат до `0006` → накат уже исправлённой цепочки. До и
после: 1 аккаунт, 19 диапазонов покрытия, 3 транзакции, 99 операций, 247
эффектов — всё на месте; источник стал `horizon:pool`.

**Compose.** Образы пересобраны (`runtime`, `tests`, `collector`). На базе без
миграций `worker` и `history` выходят с кодом 1 и сообщением, какая команда
нужна; `/ready` при этом 503. После наката до `0010`: `db`, `api`, `worker`,
`history` поднялись, `/ready` 200, обе службы стартовали с пустой очередью
одной строкой в логе; за две минуты — не меньше одного прохода worker — ни
одного обращения к Horizon. `docker compose stop` — все три службы вышли с
кодом 0 за полсекунды, каждая со строкой «stopped on request». После проверки
службы остановлены и удалены; работает только `db`.

## 10. Что проверено после этапа 04 и что исправлено

| № | Вопрос | Что оказалось | Что сделано |
| --- | --- | --- | --- |
| 1 | Отвергает ли локальный фильтр уведомление управляемой подписки из-за неполного набора полей | мог: доставка от подписки установки о платеже в активе, который здесь никто не читает, сохранялась без задания | доставка от подписки, которую установка держит активной или взяла вручную, всегда ставит транзакцию в очередь |
| 2 | Превращается ли временный 404 свежей транзакции в окончательный `dead` | да: 404 на всех серверах сразу давал `dead` | 404 — неудача, как всякая: повтор до конца попыток, и только тогда `dead` |
| 3 | Устойчивы ли чекпоинты к смене порядка URL | нет: источник назывался первым сервером списка | `horizon:pool`, миграция `0007`; тест на чтение, продолженное после перестановки списка |
| 4 | Теряются ли исходные данные вебхука при долгой недоступности и retention | нет: тело лежит в `notifier_event.payload` целиком, XDR включён. Ниже retention теряется возможность принести контекст из Horizon, а не источник | ничего удалять не нужно; ограничение записано |
| 5 | Начало истории пула, когда сервер с самой глубокой историей молчит | **дефект, найденный в этом этапе** его же тестами. `history()` считал старейший леджер только по доступным: окно «вся доступная история» обрезалось по живым, и задание становилось `done`, не прочитав нижние леджеры; в backfill те же леджеры помечались `unverifiable` насовсем | старейший леджер — по последнему слову каждого сервера; `silent()`; задание с низом «до начала истории пула» не заканчивается, пока есть замолчавший |
| 6 | Пауза после отказа серверов | срез, который не удалось прочитать из-за серверов, откладывался на час | две минуты, но не больше `retry_cap`; попытки не тратятся |

О пункте 5 стоит сказать прямо: первый вариант моего теста «сервер умирает
посреди импорта» прошёл — и прошёл из-за этого дефекта: задание становилось
`done` на укороченном окне, пока сервер так и не вернулся. Защитный сценарий
увидел бы то же самое в работе.

## 11. Инциденты и мои ошибки

**Потолок живых запросов превышен** — раздел 8.

**Баги, пойманные до сдачи** (все — тестами на настоящей PostgreSQL):

1. Миграция `0007`: LIKE-шаблон `horizon:\_%` не совпадал ни с чем; слияние
   строк не учитывало направление чтения (у чтения назад дальше та строка, где
   курсор ниже); в откате не хватало привязки. Пойманы проверкой наката на
   копии пилота.
2. Очередь истории и пул — начало истории пула по живым серверам (раздел 10,
   пункт 5).
3. Пауза импорта выбирала и уже готовые задания (нашёл субагент, писавший
   очередь истории, при чтении моего кода).
4. Сверка подписок: подтверждение шло `GET /:id`, который у Notifier не
   отвечается для неизвестного id, — переведено на чтение списка; лимит
   принимался за 403, а это 400; строка `retired` сталкивалась с уникальным
   ключом при повторном включении — возрождается; подписка, принятая вручную
   у выключенного аккаунта, забывалась неправильно; `adopt` возвращал
   откреплённый объект ORM.
5. У `app.watch` не было `__main__.py`: `python -m app.watch` не запускался,
   а тест вызывал функцию напрямую и этого не видел. Найдено прогоном команд
   в настоящем образе; добавлен тест на входные точки всех четырёх пакетов.
6. `MTL_HORIZON_HISTORY_CONTEXT` был в `.env.example`, но не передавался в
   контейнеры Compose. Найдено при написании документации.
7. Число запросов на срез, заданное дробным меньше единицы (`0.5`), давало
   срез из нуля запросов — бесконечный пустой цикл. Теперь отказ на старте.
8. Десять строк внутренностей Alembic в логе службы при старте — убраны.
9. У встроенного API Notifier субагента тесты поймали два бага (батч
   хранился частично, повтор внутри батча хранился дважды) — исправлены им же.

**Ошибка командной строки:** `sed` с `#` в роли разделителя стёр
`.env.example`; восстановлен из git и применён заново.

## 12. Отклонения от задания и нерешённое

| Пункт задания | Как вышло |
| --- | --- |
| «Авария в каждом переходе lifecycle» | отдельные тесты на падение — у трёх переходов; остальные переходы идемпотентны по построению (каждый проход читает состояние из базы), но отдельного теста на падение у них нет |
| «Проверить upgrade с 0006 на копии базы с данными» | сделано: на копии пилота через `0006` и на dev-базе (раздел 9) |
| «По возможности дополнить сетевой изоляцией» | сделано: блокировка на уровне сокетов |
| Ограничить историю периодом существования аккаунта | не делается: merge/recreate по REST не отличить, и «текущий период существования» не выдаётся за всю историю адреса |
| Если открытие trustline нельзя определить точно — проверить линию через пул или отложить | проверка линии не понадобилась: открытие — эффект успешной транзакции из сохранённой истории. Единственная неопределённость («эффектов ещё нет») решается ожиданием |
| Атомарная запись открытия и задания discovery | вместо атомарности — долговечное повторное чтение из базы с курсором в `service_state` и запасом в пять минут |
| «Более широкая подписка и локальный фильтр» для рынков | не понадобились: одна подписка на актив пары покрывает рынок правилами v2 |
| Живая интеграция с Notifier | не проверялась: без разрешения владельца подписки не создавались. Форма уведомления сверена с кодом двух ревизий и с примерами `RESPONSE_EXAMPLES.md` ревизии `0fb6050` |
| Живые запросы | один незапланированный по размеру dry-run; всё остальное — на встроенных серверах |

Нерешённое — `docs/architecture.md`, раздел 32. Главное из него: живая
интеграция с Notifier; лимит подписок в 100 на пользователя по умолчанию;
замолчавший сервер держит низ окна истории (намеренно); полная история
произвольного актива через REST невозможна; discovery — не снимок; журнал
уведомлений растёт без политики хранения.

Из следующих этапов (по заданию — не делать) ничего не сделано: админка,
проверки пула с адресами через ENV, статистика активности, API истории и
графиков, снимки балансов, сверка и восстановление, пакетный импорт.

## 13. Что было бы полезно в Notifier

Наблюдение по его коду на `e4039fb` и `0fb6050`, не задача другому
репозиторию:

1. **Слияние подписок на актив.** Повторный POST создаёт дубликат, потому что
   идентичность считается по запросу до того, как сервис допишет `asset_type`.
   Считать её по нормализованной подписке — и дубликаты исчезнут у всех
   клиентов, не только здесь.
2. **Один код состояния для лимита.** Внутри — 403, наружу — 400. Клиент не
   может отличить «исправьте запрос» от «попросите владельца поднять лимит»
   иначе как по тексту сообщения.
3. **Ответ для неизвестного id.** `GET /api/subscription/:id` без подписки с
   таким id не отвечается вовсе; 404 снимал бы необходимость таймаута.
4. Из этапа 04 остаётся в силе: курсор доставки и повтор по запросу, леджер
   транзакции явным полем, ассеты словами Horizon.

docker compose run --rm -T api python -m app.watch status
