# Отчёт по этапу 04: события и пул Horizon

Этап 04 продолжил проект после этапа 03 (миграция `0003`, 287 тестов). Сделаны
три блока задания: приём и обработка уведомлений Operations Notifier,
отказоустойчивый пул серверов Horizon с общим темпом и независимые правила
наблюдения. Регулярный опрос перестал быть штатным способом: новая история
приходит как событие, а опрос остался инструментом восстановления.

Кратко:

- **392 теста** на настоящей PostgreSQL 17, без внешней сети (было 287).
- **21 исходящий запрос** из потолка 50, из них **до 6 — мои незапланированные**
  (раздел 8).
- Миграции `0004`–`0006` проверены на копии базы этапа 03 с данными; история
  не тронута; `alembic check` чистый.
- Репозиторий Notifier не менялся, подписки не создавались, рабочий Notifier
  ничего не присылал: живая проверка приёма шла с уведомлением, собранным
  вручную по записи Horizon.

## 1. Что сделано

| Блок | Что получилось |
| --- | --- |
| Правила наблюдения | У аккаунта флаг `enabled` вместо режима. Три списка независимы, объединяются по ИЛИ. Старый YAML с `mode` читается явно, без молчаливого включения |
| Пул Horizon | Клиент одного сервера с хуками и пул поверх: активный сервер, переход по кругу, cooldown, проверка root после сбоя, чужая сеть и отставание, 404/410 у резервных, происхождение данных в coverage. `python -m app.pool check/status` |
| Общий темп | Одна строка `http_pace` в PostgreSQL: все процессы и все серверы — один темп; события с приоритетом, фон не голодает; 429 ставит паузу всем |
| Приём событий | `POST /webhooks/notifier`: подпись ed25519, лимит тела, журнал и задание одной транзакцией до ответа, идемпотентность по `(id, subscription)` |
| Worker | `python -m app.worker run/once/status/retry/events`: аренда, шаги контекста, последняя часть атомарна с пометкой «готово», повторы с backoff, `partial`/`dead`, возврат зависших заданий, ручной retry |
| Переключение | `docker compose up` поднимает `db`, `api` и `worker`; `collector` — только через профиль |

## 2. Notifier: ревизия и фактическая форма

| | |
| --- | --- |
| Репозиторий | `Montelibero/operations-notifier` |
| Ревизия | `cea7e51e031969bbdda86ce5817142d289ec5139` (v0.12.0). Раньше в этом же этапе изучалась `a474e9cccd43aa318a861014a66ec5dc23c4264c` (v0.11.0): webhook и подпись между ними не изменились |
| Рабочее дерево репозитория | в момент проверки были незакоммиченные правки (`README.MD`, `logic/observer.js`, `logic/storage.js`, `logic/stream-processor.js`, `models/subscription-model.js`); они **не** использовались |
| Форма | `{id, subscription, type: "operation", created, sent, operation, transaction}`; одно уведомление — одна операция, каждой совпавшей подписке — свой POST |
| Идентификация | `operation.id` — TOID операции (проверено на операции `281876689297928193`: `paging_token` транзакции + номер с единицы); `transaction.hash` — как в Horizon, у fee-bump — hash конверта; `transaction.paging_token` — TOID транзакции; леджер выводится из него |
| Ассеты | цифрами: `asset_type` 0 (native), 1, 2 — не словами Horizon |
| XDR | `transaction.envelope_xdr`, `transaction.result_xdr`; `result_meta_xdr` нет |
| Подпись | ed25519 (stellar-sdk) над телом `JSON.stringify(data)`; `X-Request-ED25519-Signature`, base64; ключ — Stellar-пара, публичный ключ — `publicKey` в `/api/status` |
| Типы подписок | аккаунт, актив, фильтры memo / operation_types / contract; правила v1 у старых, v2 у новых (`filter_version`) |
| Повторная доставка | успех — любой 2xx; таймаут 20 с; неудача — повтор через `retries³` с; бросается через 7 дней (`maxNotificationAgeSeconds` 604800) или 100 неудач (`maxDeliveryFailures`); 10 брошенных подряд — подписка выключается |

Примеры (`RESPONSE_EXAMPLES.md`) гарантией поведения установленной версии не
считались: адаптер (`app/notifier/format.py`) не требует ни одного
необязательного поля и называет в `problems` то, чего не смог прочитать.

Что изменилось в v0.12.0 и учтено: `destination_muxed` / `destination_muxed_id`
(базовый `G…` всегда в `destination`), `destination` у `path_payment_*`,
`trades` у `create_passive_sell_offer`, счётчики пропущенных транзакций в
`/api/status` (`stream.skippedTransactions`, `stream.lastSkippedTransaction`).

## 10. Ограничения полноты

Подробно — `docs/architecture.md`, раздел 22. Коротко:

- Воркер приносит **то, о чём ему сказали**, целиком. Что всё будет услышано,
  не обещается: у Notifier нет курсора доставки и повтора по запросу.
- Чего может не быть в уведомлениях: операции неизвестного ему типа
  (пропускаются), транзакции, которые у него не разбираются (считаются в
  `/api/status`, не доставляются), доставки, на которые не ответили за 20 с
  (бросаются через 7 дней или 100 неудач), неявные изменения без операции,
  сделки пассивных офферов до v0.12.0, всё вне подписок и их правил.
- Наибольший леджер среди уведомлений — не фронтир; `worker status` печатает
  это вместе с цифрой.
- Подписка на актив не даёт полной истории актива: она матчится по полям
  операции, а не по факту сделок.
- Восстановление — backfill на окно или collector; автоматически и в фоне
  ничего не закрывается, скрытого штатного опроса нет.

## 11. Инциденты и мои ошибки

**Тесты сходили в настоящий Horizon.** Новый тест команд воркера вызывал
`once`, не предоставив фейк: пул строился по адресу из окружения Compose
(`https://horizon.stellar.org`) и делал настоящие запросы — root и
`/transactions/<фейковый хеш>` — в 2–3 прогонах, до 6 запросов. Заметил по
неожиданному коду возврата, проверил доступность (DNS и TCP, без HTTP),
зачёл запросы в бюджет по верхней границе и закрыл дыру структурно:
автофикстура `no_real_servers` даёт каждому серверу из окружения транспорт,
который отказывает в соединении, а тест, который его не предоставил, падает
на месте. Это был ровно тот случай, против которого написано «тесты по
умолчанию без внешней сети», и моя ошибка, что защита появилась только
после.

**Баги, пойманные тестами этого этапа** (все — до живых проверок):

1. Thread-local писался в потоке попытки запроса, а читался в вызывающем —
   `served_by` оставался пустым.
2. Ограничитель темпа записывал в `next_at` начало слота вместо конца: два
   процесса получали слоты одновременно.
3. Пул повторял сбойную попытку `A, B, A, A` вместо круга `A, B, A, B`.
4. Сервер чужой сети после проверки root попадал в отчёт как «оставлен».
5. 404 отстающего сервера считался доказательством отсутствия ресурса.
6. `history()` считал root свежим пять минут — коллектор пять минут не видел
   бы новых леджеров.
7. Шаги контекста шли в порядке множества: эффекты раньше операций, внешний
   ключ падал, задание уходило в `dead`.
8. Две одинаковые доставки одновременно — вторая получала 500.
9. Правило рынка сравнивало множество с кортежем и никогда не совпадало.
10. В настройках из-за приоритета операций возвращался вложенный кортеж.
11. Столбец `created_at` у журнала конфликтовал с служебным столбцом строки.

**`docker compose kill` не проверяет аварийность.** Явная остановка
контейнера не перезапускается политикой `unless-stopped`; авария — это когда
процесс умирает сам. Проверил, убив процесс внутри контейнера: возвращается.

## 12. Отклонения от задания и нерешённое

| Пункт задания | Как вышло |
| --- | --- |
| «Не запрашивать повторно, если payload содержит достоверные записи» | записи истории берутся из Horizon по хешу: уведомление — не запись Horizon (другая форма ассетов, нет эффектов, нет id операций); XDR из уведомления отдельно не хранится — в журнале оно есть в составе payload, а в историю ложится то же самое от Horizon |
| Защита endpoint | только подпись: секретного заголовка у Notifier нет; API на `127.0.0.1`, TLS-прокси — за владельцем |
| Путь webhook | фиксированный, `/webhooks/notifier`; настраиваемого пути нет |
| Настройки пула | только `.env`; поэтому сняты `--horizon-url` и `--rate`, а вместе с блокировками — `--wait-lock` (о снятии флагов в задании не сказано — следствие) |
| Ошибка запроса против сбоя сервера | решается проверкой root после сбоя — моя конструкция; cooldown с удвоением — тоже |
| Проверка пула | идёт через общий темп (может ждать события) и требует базу, чтобы сохранить состояние |
| Два worker на базу | разрешены: очередь безопасна, блокировки на один worker нет |
| `scripts/replay_window.py` | остался на клиенте одного сервера: читает запись с диска, не Horizon |
| Живая проверка Notifier | уведомление собрано вручную; от рабочего Notifier доставок не было |
| Не сделано (вне этапа) | discovery, автоматические подписки, очередь backfill, админка, сверка балансов, архивы |

Нерешённое — `docs/architecture.md`, раздел 24: живой Notifier не сверён;
общий темп есть только в пределах одной базы; инструмента «где именно пропуск»
нет; темпа на провайдера нет; журнал растёт без политики хранения.

## 13. Что было бы полезно в Notifier

Наблюдение по его коду на `cea7e51`, не задача другому репозиторию. Только то,
чего действительно не хватает:

1. **Курсор доставки и повтор по запросу.** Сейчас узнать, всё ли доставлено,
   и получить пропущенное нельзя — ни у подписки, ни у всего сервиса.
   Последовательность на подписку (или позиция «доставлено до») и endpoint
   «пришли всё после X» превратили бы «доставка без потерь не обещается» в
   проверяемое утверждение.
2. **Леджер транзакции явным полем.** Сейчас он выводится из `paging_token`;
   поле `ledger` (и время закрытия) сняло бы зависимость от формата TOID.
3. **Ассеты в обозначениях Horizon.** Либо слова (`native`,
   `credit_alphanum4`), либо оба варианта сразу — без слоя перевода.
4. **Плательщик комиссии fee-bump.** В `transaction` есть только источник
   внутренней транзакции; аккаунт, заплативший комиссию, в уведомлении не виден.
5. **Общие счётчики в `/api/status`.** Пропущенные транзакции там есть
   (с v0.12.0); брошенных доставок по всему сервису и глубины очереди
   доставки там нет — потери видны только на каждой подписке отдельно.
6. **Секретный заголовок дополнительно к подписи** — для установок, где
   сервис стоит за прокси с авторизацией по заголовку; подпись и так
   достаточна, это удобство, а не необходимость.
