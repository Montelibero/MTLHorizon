# Инструкция владельцу: админка, свой список, приём событий, подписки и история

Это инструкция, а не деплой: здесь написано, *как* поднять установку и
управлять ей из браузера — списки, discovery, подписки Operations Notifier,
импорт истории, — и что делать командами, когда браузера нет. Сам скрипт
выкладки и решение о запуске — за владельцем.

Команды и страницы проверены на этапе 06 (`docs/stage-06-report.md`) на
встроенных Horizon и Notifier. **Живая интеграция с Notifier не проверена**:
от рабочего Notifier доставок не было. Смоук-тест для неё приготовлен
(раздел 16) и ждёт вашего разрешения; пока он не пройден, установка готова
к пилоту, не к production.

## 1. Что понадобится

- Сервер с Docker и Docker Compose v2, немного места под PostgreSQL и
  исходящий HTTPS к Horizon.
- Решение об источнике: **публичный** `https://horizon.stellar.org` (1 запрос
  в секунду на адрес; сделки самых активных аккаунтов — 503) или **свой**
  Horizon, или **несколько** — тогда первый в списке основной, остальные
  подхватывают, когда он сбойнит. Не оставляйте в списке адрес мёртвого
  сервера: задания истории, которым нужны его леджеры, будут ждать его
  (раздел 8).
- Рабочий **Operations Notifier**, которому доступен ваш webhook. Его ключ —
  в разделе 5; там же — как регистрировать подписки: автоматически через его
  API или вручную.
- HTTPS-перед API: API слушает только `127.0.0.1:8000`, и Notifier должен
  доставать до `/webhooks/notifier`. Публикуйте его только за своим прокси
  с TLS: защита webhook — подпись, но и её лучше не возить по открытой сети.
- **Секрет админки** — длинная случайная строка в `MTL_HORIZON_ADMIN_SECRET`.
  Без него админка закрыта для всех. Если API виден из интернета, задайте
  ещё `MTL_HORIZON_PUBLIC_ORIGIN` (адрес, по которому к нему приходят):
  cookie станет `Secure`, и менять состояние можно будет только со страниц
  установки.
- Для исторического API — один или несколько токенов
  (`MTL_HORIZON_API_TOKENS`, через запятую). Без токенов API не читает никто.

## 2. Поднять

Порядок обязателен: база, миграции, всё остальное.

```bash
git clone <репозиторий> mtl-horizon && cd mtl-horizon
git checkout <commit этапа 06>
cp .env.example .env            # задать POSTGRES_PASSWORD, MTL_HORIZON_NOTIFIER_KEYS, MTL_HORIZON_ADMIN_SECRET
docker compose build
docker compose up -d db
docker compose run --rm api alembic upgrade head     # довести схему до 0012
docker compose run --rm api alembic check            # No new upgrade operations detected.
docker compose up -d                                # db, api (webhook, админка, исторический API), worker и history
curl -s http://127.0.0.1:8000/ready                   # 200
```

Теперь откройте `http://127.0.0.1:8000/admin` (через ваш HTTPS-прокси, если
работаете не с самого сервера) и войдите секретом админки — раздел 14.

На базе без миграций API жив, но не готов (`/ready` — 503), а `worker` и
`history` выходят с кодом 1, не начав работать, — в логе написано, чего не
хватает и какая команда нужна. Обновление с этапа 03, 04 или 05: замените образы
(`docker compose build`), **остановите службы** (`docker compose stop`),
примените миграции — `0004`–`0012` не трогают историю — и поднимите снова.
`0007` переименовывает источник у чекпоинтов и покрытия в `horizon:pool`: до
этого не переставляйте серверы в `MTL_HORIZON_URLS` со старым кодом. Старый
`.env` с одним `MTL_HORIZON_URL` продолжает работать.

PostgreSQL не публикуется вовсе, API публикуется только на `127.0.0.1:8000`,
worker и history портов не имеют. `docker compose up` поднимает базу, API,
worker и history; коллектор в этот набор не входит (раздел 9).

Если процесс службы умер сам, Docker возвращает её примерно за секунду
(`restart: unless-stopped`). `docker compose stop` и `docker compose kill` —
это явная остановка: после них службу поднимаете вы (`docker compose up -d`).

## 3. Свой список

Всё, что в разделах 3–8 делается командами, делается и из админки
(раздел 14) — страницы зовут те же функции. Команды остаются для случая без
браузера; файл списка — для больших списков, которые удобнее держать в
репозитории.

Скопируйте пример в игнорируемый каталог и заполните:

```bash
mkdir -p local
cp local-tracking.example.yaml local/tracking.yaml
```

- `accounts`: `address` (G-адрес), `enabled`, `reason`.
- `assets`: `code` и `issuer` (или `native: true`); `enabled` — читать ли
  историю актива; `discover: true` — искать ли держателей его trustline
  (раздел 7). Флаг отдельный: актив может быть только для discovery.
- `markets`: пара активов (`base`/`counter`); обе ориентации — один и тот же
  рынок.
- `reason` обязателен: почему аккаунт в списке.

```bash
alias bf='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.backfill'

bf import-config --file local/tracking.yaml --dry-run     # проверить: все ошибки сразу, ничего не записано
bf import-config --file local/tracking.yaml
```

Повторный импорт того же файла ничего не меняет. Записи, которых в новом
файле нет, не удаляются. Флаг меняется только с `--apply-changes`. Аккаунт,
добавленный файлом или включённый заново, получает границу начала, импорт
истории и подписку — той же жизнью, что и добавленный командой (раздел 8).
Аккаунты, которые были в базе до этапа 05, помечены `legacy` и своего импорта
не получают: их история — та, что уже собрана, и backfill на нужное окно.

Три списка — аккаунты, активы, рынки — независимы и объединяются по **ИЛИ**:
уведомление становится заданием, если совпал хотя бы один включённый аккаунт,
актив или рынок (или актив, помеченный для discovery). Отключённый аккаунт не
отключает активы и рынки и не удаляет собранное. Эмитент актива может остаться
выключенным: он слишком активен, чтобы грузить целиком.

Файл этапа 03 с полем `mode` читается так: `FULL` — как `enabled: true`,
остальные режимы — как `enabled: false`, с пометкой. Аккаунт, который был
неактивен, молча не включится — поставьте `enabled: true` сами и импортируйте
с `--apply-changes`.

### Добавить или выключить аккаунт руками

```bash
alias wa='docker compose run --rm api python -m app.watch'

wa add-account G… --reason "…"        # включён; границу, импорт и подписку сделает worker в свой следующий проход
wa add-account G… --reason "…" --no-pass   # или `wa run` сразу
wa disable-account G…                 # импорт на паузу, подписка уходит, история остаётся
wa enable-account G…                  # снова: от последнего леджера; время выключения дочитается
wa status                             # где каждый аккаунт в своей жизни; серверов не спрашивает
```

## 4. Проверить пул

```bash
alias pl='docker compose run --rm api python -m app.pool'

pl check        # каждый сервер отдельно, до 6 запросов на сервер; ничего в истории не меняет
pl status       # то, что сохранено о серверах; серверов не спрашивает
```

`check` спрашивает каждый сервер сам, без перенаправления на резервный:
сеть, версию, последний и старейший леджер, отставание от самого свежего,
медиану времени ответа root и одного запроса истории, HTTP-статус и те
rate-limit заголовки, что сервер прислал. Запросы идут в общем темпе: пока
worker занят событиями, проверка может подождать.

Запускайте чтение на сервере, где всё `ok`: сеть — та, что у базы (иначе
`/ready` отвечает 503), отставание — в нескольких леджерах, время ответа —
сотни миллисекунд. `unavailable` у резервного — не беда, если основной
работает; беда, если основной. Ничего из `check` не решает, кто активен:
пул решает сам при каждом запросе. Начало истории пула считается по всем
серверам, включая временно недоступные: леджеры, которые держит только
молчащий сервер, не помечаются недоступными насовсем — они ждут его.

## 5. Подписки Notifier и ключ

В `.env`:

```dotenv
MTL_HORIZON_NOTIFIER_KEYS=G...     # publicKey из GET /api/status вашего Notifier; несколько — через запятую
```

Без ключа webhook отвечает 503 и ничего не принимает — это нормальное
состояние до того, как подписки настроены.

Подписки можно вести двумя способами. В обоих `reaction_url` каждой подписки
этой установки — один и тот же адрес:

```text
https://<ваш домен>/webhooks/notifier
```

### Автоматически — через API Notifier

Проверено только на встроенном Notifier (`tests/fake_notifier_api.py`,
список правил в `docs/architecture.md`, раздел 27), не на настоящем.

```dotenv
MTL_HORIZON_NOTIFIER_API_URL=http://127.0.0.1:4021
MTL_HORIZON_NOTIFIER_CALLBACK_URL=https://<ваш домен>/webhooks/notifier
MTL_HORIZON_NOTIFIER_API_TOKEN=<его токен>       # если у Notifier авторизация выключена — не задавать
```

Поддержаны режимы Notifier `disabled` (без токена) и `token` (административный
или пользовательский токен). Режим с ed25519-подписью каждого запроса
клиентом не поддерживается — ведите подписки вручную.

Worker по спискам наблюдения сам регистрирует по подписке на каждый
включённый аккаунт, на каждый включённый или discovery-актив и по одной на
рынок, и сам же снимает лишние. Чужие подписки — с другим `reaction_url` —
не читаются, не меняются и не удаляются.

```bash
alias sb='docker compose run --rm api python -m app.subscriptions'

sb status              # что хотят списки, что зарегистрировано, что не вышло; Notifier не спрашивает
sb reconcile --dry-run # что сделал бы проход
sb reconcile           # один проход руками; worker делает его сам, когда есть что делать
```

**Лимит подписок.** У Notifier по умолчанию не больше 100 активных подписок
на пользователя (`MAX_ACTIVE_SUBSCRIPTIONS_PER_USER`), и в режиме `disabled`
он тоже считается — там все подписки принадлежат анонимному администратору.
Для тысячи аккаунтов владелец Notifier должен поднять лимит в его конфиге.
Иначе строки останутся в `error` с причиной `refused, 400: Forbidden. Max
active subscriptions exceeded.` и будут пробовать снова с растущей паузой —
это стоит времени, ничего не теряется.

**`ambiguous`** — у Notifier больше одной подписки подходит под то, что
регистрирует установка (обычно дубликат активной подписки: для активов
Notifier повторный запрос не сливает с существующей). Установите, какая
именно ваша: удалите лишнюю в самом Notifier и примите нужную:

```bash
sb adopt --kind account --key G… --id <id подписки у Notifier>     # или --kind asset --key CODE:ISSUER
```

### Вручную — через интерфейс Notifier

Оставьте `MTL_HORIZON_NOTIFIER_API_URL` пустым: ничего не регистрируется и не
снимается. Подписки создайте сами — по аккаунту, по активу или с фильтрами —
и укажите здесь, какие из них ваши:

```bash
sb adopt --kind account --key G… --id <id подписки у Notifier>
sb release --id <строка>       # забыть: у Notifier она остаётся, удалите её там сами
```

С адресом API подписка перед принятием читается у Notifier и сверяется с
тем, что регистрирует установка; без адреса — принимается на слово. Принятая
вручную подписка помечается `manual` и установкой **не удаляется никогда**:
сделал человек — удаляет человек. Пока подписка аккаунта не принята (или не
подтверждена), граница его импорта истории остаётся незавершённой — `hi
status` показывает такие задания.

Подсказка по правилам Notifier (по его коду на v0.12.0–v0.13.0): подписка на
аккаунт совпадает по `account` и `destination` (а в правилах v2 — ещё по
`from`, `trustor`, `sponsoredId`, claimants и продавцу в сделках); подписка на
актив — по `asset` и `source_asset` (в v2 — ещё по `path` и ассетам сделок,
а с v0.13.0 — и с операциями пула ликвидности, в паре которого этот актив);
подписка без фильтров совпадает со всем. Новые подписки регистрируются с
правилами v2 (`filter_version: 2`). Подписка на актив — наблюдение новых
событий с ним, а не полная история актива. Сама доля пула имени здесь не
имеет: такие доставки читаются с пометкой об этом и всё равно попадают в
очередь.

Первая настоящая доставка:

```bash
alias wk='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.worker'

wk status        # очередь, журнал, наибольший леджер среди уведомлений
wk events        # последние доставки: что совпало, что вышло
```

Пришла — у неё `state = queued` и номер задания. Пришла, а задания нет —
читайте `diagnosis`. Присланное тело лежит в таблице `notifier_event` целиком:
первую доставку стоит открыть и сверить с тем, что описано в
`docs/architecture.md`, раздел 21.

## 6. Worker

```bash
docker compose logs -f worker
docker compose run --rm -T worker python -m app.worker once      # одно задание — ближайшее по времени
docker compose run --rm -T worker python -m app.worker status    # где очередь, что сдалось
docker compose run --rm -T worker python -m app.worker retry     # всё, что сдалось, — обратно в очередь
docker compose run --rm -T worker python -m app.worker retry --id 17
docker compose run --rm -T worker python -m app.worker events --state unmatched
```

Служба `worker` перезапускается сама (`restart: unless-stopped`). Два
worker на одну базу не мешают друг другу: каждый берёт то, что успел
заблокировать.

Каждое задание: воркер спрашивает Horizon о транзакции, её операциях,
эффектах и, если они были, сделках — 3–4 запроса на транзакцию, плюс root
сервера раз в `MTL_HORIZON_HEALTH_CHECK_INTERVAL` секунд на процесс. Уже
сохранённое не спрашивается. Ни один аккаунт не опрашивается: нет
уведомлений — нет запросов к Horizon.

В своём фоновом потоке worker каждые `MTL_HORIZON_PROVISION_INTERVAL`
секунд делает проход по списку — события ждут или нет: новому аккаунту —
границу и импорт, подписки — регистрирует и подтверждает (и перечитывает
список у Notifier, чтобы заметить подписку, удалённую там), выключенному —
ставит импорт на паузу. Когда всё в шаге, проход не спрашивает ни Horizon,
ни Notifier. Там же, в фоне, воркер выполняет задачи из админки (раздел
14) и проходы discovery по расписанию.

Неудача повторяется с растущей паузой до 8 раз; затем задание становится
`partial` (что-то сохранено) или `dead` (ничего), и его видно в `status`:
`retry` берёт такие обратно в очередь. Транзакции, которой пока нет ни на
одном сервере, — та же неудача: о ней могут сообщить через секунды после
закрытия леджера. `dead` — только когда кончились попытки. Недоступность
серверов попыток не тратит: задание ждёт десять минут и спрашивает снова.

## 7. Discovery

Актив помечается отдельно от чтения его истории: `discover: true` в файле
списка (с `--apply-changes`) или командой. Проход читает держателей trustline
через пул — `/accounts?asset=CODE:ISSUER`, страницы по 200 — и добавляет
новые адреса включёнными; дальше они живут как добавленные руками.

```bash
alias ds='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.discovery'

ds on EURMTL:GA… --reason "держатели евромарки"
ds run --dry-run --max-requests 5      # посмотреть первые страницы; ничего не меняет
ds run                                  # пройти и добавить; один проход — до 1000 запросов (около 200 тысяч держателей)
ds run --resume                         # продолжить недошедший до конца
ds status                               # активы, последние проходы, происхождение аккаунтов
```

Что знать:

- Один проход не ограничен сам собой ничем, кроме `--max-requests` (по
  умолчанию 1000): на публичном Horizon актив с 4 721 держателем — это 25
  запросов и 24 секунды. Для первого знакомства ставьте `--max-requests`.
- Считается trustline, а не баланс: держатель с нулевым балансом попадает в
  список. Эмитент не добавляется.
- Уже наблюдаемый аккаунт проход не меняет: отключённый вами не включится,
  закрытая trustline ничего не отключает. Повторный проход безопасен.
- Проход — не снимок: он занимает время, о каждой странице хранится, какой
  сервер и когда ответил. Кто открыл линию в ходе прохода, найдётся следующим.
- Между проходами открытие trustline видно по эффекту `trustline_created` в
  успешной транзакции, которая попала в базу: для этого у discovery-актива
  есть своя подписка — даже если сам актив не включён для истории.
- Расписание по умолчанию выключено. `MTL_HORIZON_DISCOVERY_INTERVAL=86400` —
  и worker запускает проход раз в сутки, в тишине между событиями.

## 8. История: очередь импорта

Каждый добавленный или включённый заново аккаунт получает задание: прочитать
всю доступную историю — четыре потока, с неудачными транзакциями — от начала
истории пула до верхней границы. Служба `history` (`python -m app.history
run`) работает по срезам: ограниченный кусок работы над одним субъектом,
потом следующий. У события приоритет: пока они идут потоком, история получает
один запрос из десяти; в тишине — весь темп.

```bash
alias hi='docker compose run --rm api python -m app.history'

hi status                                  # очередь: что ждёт, что не покрыто, что не гарантируется
hi pause --account G… --because "…"        # остановить; hi resume --account G… — продолжить
hi retry                                   # сдавшиеся задания — обратно в очередь
hi enqueue --market native EURMTL:GA…      # сделки пары — в очередь (для рынка это его backfill)
```

Что знать:

- **Прогресс переживает рестарт.** Он лежит в покрытии и чекпоинтах, а не в
  задании; повторное планирование ничего не сбрасывает.
- **Ниже истории пула.** То, что не хранит ни один сервер пула, помечается
  `unverifiable` и называется в результате задания (`unavailable_ledgers`) —
  это не «история начинается здесь», и прочитанным оно не считается.
- **Замолчавший сервер держит низ окна.** Если у одного из серверов самая
  глубокая история и он недоступен, задание не станет `done` на укороченном
  окне: оно в `waiting` и в `last_error` назван сервер. Сервер вернётся —
  дочитается. Мёртвый адрес — уберите из `MTL_HORIZON_URLS`.
- **`partial` и `error`** — поток (или всё) не читается после многих попыток
  (например, сделки очень активного аккаунта — 503 на публичном сервере);
  `retry` возвращает в очередь, когда причина ушла.
- **Контекст.** По умолчанию `parents`: читаются все четыре потока аккаунта,
  а для записи подтягивается только необходимое. `MTL_HORIZON_HISTORY_CONTEXT=full`
  — полный контекст каждой транзакции, дороже. Живые события всегда целиком.
- **Аккаунт без подтверждённой подписки** держит границу незавершённой
  (`boundary_final = false`): пока Notifier не принял подписку, импорт не
  считает, что дальше всё увидят события.

Одно окно руками — по-прежнему backfill (раздел 9): у него границы и бюджет
задаются явно, и он годится для сверки.

## 9. Коллектор и backfill: восстановление и контрольные сверки

Коллектор (`python -m app.collector`) читает **вперёд** каждый поток списка —
это стоит запросов даже когда ничего нет, поэтому в штатный набор он не
входит. Запускайте, когда нужно закрыть известный пропуск или свериться.

```bash
alias lc='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.collector'

lc once --report local/reports/recover.json     # один цикл: дочитать потоки до последнего леджера
lc status                                       # где стоят потоки; сервера не спрашивает
docker compose --profile collector up -d collector   # только если нужна регулярная сверка
docker compose --profile collector stop collector
```

Граница потока фиксируется один раз (первый цикл) и при рестарте не
сдвигается; `--start-ledger L` задаёт её явно. Один коллектор на базу.

### История до границы: backfill

Backfill — отдельная команда с обязательными границами и бюджетом. Она
может идти одновременно с worker: темп у них общий, у событий приоритет, а
backfill не голодает — пока события идут потоком, ему достаётся один запрос
из десяти, как только очередь пуста — весь темп.

```bash
bf estimate --from-ledger L1 --to-ledger L0                       # сколько страниц и запросов
bf run --from-ledger L1 --to-ledger L0 --max-requests 2000         # бюджет обязателен
bf run --full-retention --max-requests 5000 --max-seconds 3000     # вся история, которую хранит пул
bf status
bf verify --from-ledger L1 --to-ledger L0 --aggregations           # сверка с сервером
```

Без границ, без `--full-retention` или без бюджета `run` и `reimport`
откажутся, не сделав ни одного запроса. Остановленный запуск продолжается с
чекпоинта. `--context parents` читает в 2,7 раза меньше запросов, но без
контекста встреченных транзакций (раздел 15 `docs/architecture.md`).

## 10. Что смотреть

| Где | Что значит |
| --- | --- |
| `wk status`, `queue:` | сколько заданий в каждом состоянии; `partial` и `dead` ждут `retry` |
| `wk status`, `jobs that gave up` | какие задания сдались, что уже сохранено и почему |
| `wk status`, `highest ledger among notifications` | наибольший леджер среди уведомлений — **не фронтир**: из него не следует, что всё ниже увидено |
| `wk events` | последние доставки: `queued`, `unmatched` (ни одно правило здесь не совпало), `unsupported` (не операция или без транзакции), и диагноз |
| `hi status` | очередь истории: сколько ждёт, идёт, готово, `partial`, `error`, на паузе; что не покрыто; задания с незавершённой границей |
| `wa status` | где каждый аккаунт в своей жизни: без границы, без подписки, с незавершённой границей импорта |
| `sb status` | что хотят списки против того, что есть у Notifier; `error` с причиной и следующей попыткой; `ambiguous` — решать вам |
| `ds status` | активы для discovery, последние проходы (`complete`/`incomplete`), сколько аккаунтов найдено |
| `pl check`, `pl status` | что делает каждый сервер пула; сохранённое состояние |
| дашборд `/admin` | обе службы: работают / на паузе / «не слышно» — так пустая очередь не сойдёт за остановленную службу; подписки, discovery, задачи, размер базы |
| `docker compose ps` | `api`, `worker` и `history` вверх; упавшие перезапустятся |
| `curl :8000/health`, `curl :8000/ready` | живость API и готовность базы (это API, не worker) |
| `docker compose logs worker`, `logs history` | `try N failed` с состоянием; `is left alone for Ns` — сервер пула оставлен на время; `did not say of itself just now` — задание ждёт замолчавший сервер |
| журнал Notifier | повторы и брошенные доставки — на его стороне |

Тревожиться стоит, если очередь событий растёт от просмотра к просмотру,
`partial` и `dead` не разбираются, сервер пула подолгу `unavailable` (и
история из-за него стоит), `sb status` показывает `error` или `ambiguous`,
которые не уходят, а у Notifier растёт счётчик брошенных доставок.


Восстановление проверяйте не на рабочей базе, а на черновой, и сверяйте

```bash

docker compose exec -T db pg_restore -U mtl_horizon -d mtl_horizon_restore_check --no-owner < mtl-horizon-YYYYMMDD.dump
# слепки рабочей и восстановленной за одно окно должны совпасть:

docker compose exec -T db psql -U mtl_horizon -d postgres -c 'DROP DATABASE mtl_horizon_restore_check'
```

Проверено на этапе 04 на копии базы этапа 03: дамп в 1,15 МБ, восстановленная
равна оригиналу по всем семи таблицам окна — и после наката миграций до

## 12. На что рассчитывать

- **Тишина бесплатна.** Тысяча включённых аккаунтов и ни одного события —
  0 запросов к Horizon; очередь истории и discovery-расписание выключены —
  тоже 0.
- **Одна транзакция** — 3–4 запроса (плюс root раз в пять минут на процесс).
  121 транзакция, о которой пришло 366 уведомлений (для двух подписок, с
  повторами), — 364 запроса и 2,5 секунды работы воркера.
- **Discovery.** Страница — 200 держателей, один запрос: актив с 4 721
  держателем на публичном Horizon — 25 запросов за 24 секунды.
- **Очередь истории.** Тысяча заданий планируется за две секунды, пять
  тысяч — за пятнадцать; каждый срез — до
  `MTL_HORIZON_HISTORY_SLICE_REQUESTS` запросов и короче
  `MTL_HORIZON_HISTORY_SLICE_SECONDS`; субъекты обслуживаются по очереди.
  Сама очередь на 5000 заданий стоит срезу около 0,2 с — доли процента от
  среза при темпе 1 запрос в секунду. Пустая очередь не спрашивает ничего.
- **Админка.** Открытие страницы ничего не спрашивает у серверов. Дашборд
  на тысяче аккаунтов считается за 20 мс, страница активности за 50 — за
  135 мс; дорогие счётчики кэшируются на пять минут.
- **Backfill при работающих событиях** — не быстрее, чем один запрос из
  десяти, пока события идут; в тишине — полный темп.
- **Журнал** — около 3 КБ на доставку с индексами (на фейковых уведомлениях);
  из него ничего не удаляется.
- **Проверка пула** — до 6 запросов на сервер.
- **Место под историю**: строка операции — около 1,7 КБ с индексами, эффект —
  1,4 КБ, сделка — 2,4 КБ, транзакция с XDR — 8–12 КБ; считать надо от
  операций и эффектов.

## 13. Чего не делать

- Не публиковать `/webhooks/notifier` без TLS-прокси и не задавать
  `MTL_HORIZON_NOTIFIER_KEYS` наугад: без правильного ключа всё,
  что придёт, получит 401, а Notifier будет повторять и в итоге бросит.
- Не запускать `ds run` без `--max-requests`, если не уверены, что хотите
  прочитать актив целиком: проход идёт до конца или до 1000 запросов.
- Не оставлять мёртвый сервер в `MTL_HORIZON_URLS`: задания истории, которым
  нужны его леджеры, будут ждать его вечно.
- Не запускать коллектор как штатную службу при большом списке.
- Не поднимать темп выше 1–2 запросов в секунду к публичному серверу и не
  добавлять серверы ради темпа: темп один на всё.
- Не читать историю без бюджета (backfill) — и не ждать от очереди истории,
  что она ускорится в обход лимитов: она может идти неделю.
- Не деплоить и не менять существующие сервисы, в том числе Notifier, без
  отдельного решения. Поднимать его лимит подписок — тоже его конфиг,
  решение за его владельцем.
- Не открывать админку в интернет без HTTPS-прокси: секрет уходит в cookie
  и в форме входа по открытой сети. За прокси задайте
  `MTL_HORIZON_PUBLIC_ORIGIN`.
- Не ставить `MTL_HORIZON_API_ACCESS=open`, если API доступен не только
  вам: читать историю сможет любой.
- Не запускать смоук-тест Notifier (раздел 16) без транспортного предела
  (`MTL_HORIZON_LIVE_BUDGET`) и не оставлять тестовую подписку: прогон
  кончается `unsubscribe`.

## 14. Админка: управлять из браузера

`/admin` на адресе API. Вход — секретом из `MTL_HORIZON_ADMIN_SECRET`. Сессия
живёт 12 часов (`MTL_HORIZON_ADMIN_SESSION_SECONDS`). Пять неверных входов
подряд блокируют адрес на 15 минут.

| Страница | Что делать там |
| --- | --- |
| Дашборд | состояние установки одним взглядом; обновляется сама, пока вкладка открыта; ничего не спрашивает у Horizon и Notifier |
| Аккаунты | добавить адрес (можно несколько), включить, выключить, изменить причину; для аккаунта, который был здесь до этапа 05 (origin `legacy`), — кнопка поставить историческую загрузку и проверку подписки |
| Активы | добавить актив; два флага порознь: `enabled` — новые события с активом, `discover` — искать держателей его trustline |
| Рынки | добавить пару, включить, поставить загрузку всей доступной истории сделок |
| Discovery | активы с флагом, последние проходы; «Предпросмотр» (сухой проход, ничего не меняет) и «Запустить проход» с явным бюджетом; один проход — один запрос на 200 держателей |
| Импорт истории | что прочитано по аккаунтам и по рынкам порознь, почему что-то ждёт; каждое задание: четыре потока, покрытие, счётчики прочитанного и добавленного; пауза, возобновление, повтор, приоритет, расширение окна, сверка с пулом и перечитывание окна |
| Активность | операции, транзакции, эффекты и сделки аккаунтов за период — по времени леджера |
| Notifier | что хотят списки и что подтверждено у Notifier; «Что там сейчас?», «Сверить», принять подписку, сделанную вручную |
| Horizon | серверы пула из настроек и их состояние; «Проверить все» |
| Задачи | что запущено из админки и как идёт; остановить |
| График | цена и объём сделок пары за период из того, что собрано |
| Обозреватель | по запросу: текущие trustlines и балансы аккаунта, активы эмитента; прочитанное не сохраняется |

Что занимает время — проход discovery, проверка пула, сверка, перечитывание
окна, сверка с Notifier, — никогда не выполняется в самом запросе: страница
ставит задачу, её делает воркер в фоне, и на странице «Задачи» видно, как она
идёт. Для этого должен работать `worker`.

Открытие любой страницы ничего не спрашивает у Horizon и у Notifier.
Единственное исключение — обозреватель, и только когда вы сами просите
прочитать аккаунт или эмитента.

Первая настройка discovery из браузера: «Активы» → добавить актив с флагом
discovery → на странице актива «Предпросмотр» с бюджетом, скажем, 20 →
посмотреть на странице «Задачи», что найдено → «Запустить проход» с бюджетом
по числу держателей → новые аккаунты появятся в «Аккаунтах», воркер сам даст
им подписки и поставит импорт истории.

## 15. Исторический API: доступ

Те же пути, что у Horizon (`/accounts/{id}/transactions`, `/operations/{id}`,
`/trades`, `/trade_aggregations`…), но из **вашего архива** и только из него:
пустой список значит «в этом архиве ничего нет», а не «в сети ничего не
было». Полный перечень маршрутов, форматы и отличия от upstream — в
[`history-api.md`](history-api.md).

- По умолчанию читают только с токеном: `Authorization: Bearer <токен>` из
  `MTL_HORIZON_API_TOKENS`. Без заданных токенов не читает никто (403).
- `MTL_HORIZON_API_ACCESS=open` открывает чтение всем, кто достаёт до API.
  Ставьте только за прокси с собственной авторизацией.
- Ссылки в ответах указывают на `MTL_HORIZON_PUBLIC_ORIGIN`, если он задан.

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  'http://127.0.0.1:8000/accounts/G…/transactions?limit=5' | head -c 600
```

## 16. Живой Notifier: смоук-тест (выходной барьер)

Это единственная проверка этапа 06, которую здесь не запускали: она трогает
настоящий сервис. Запускайте, только когда готовы, с тестовой конфигурацией:
адрес API Notifier и токен в `.env`, ключ подписи Notifier в
`MTL_HORIZON_NOTIFIER_KEYS`, `api` и `worker` запущены, а вебхук доступен
Notifier по `MTL_HORIZON_NOTIFIER_CALLBACK_URL`.

Тест делает **одну** подписку на названный вами аккаунт, ждёт доставку для
неё и удаляет её. Всё остальное у Notifier только читается.

```bash
export MTL_HORIZON_LIVE_BUDGET=20        # не больше 20 HTTP-попыток на весь прогон, все процессы вместе
alias sm='docker compose run --rm -T api python -m app.smoke'

sm status                               # что Notifier говорит о себе; ключ подписи должен быть среди наших (2 запроса)
sm subscribe --account G…               # одна тестовая подписка на этом аккаунте (1–2 запроса)
# сделайте транзакцию с этого аккаунта (или дождитесь любой)
sm watch --timeout 900                  # ждёт доставку и конец её задания; читает наш журнал, ни одного запроса
sm unsubscribe                          # удаляет тестовую подписку и видит, что её нет (2 запроса)
```

`watch` выходит с кодом 0, когда доставка пришла, прошла проверку подписи и
её транзакция внесена целиком. Это доказывает **одну** доставку, а не то, что
доставки не теряются. После `unsubscribe` загляните в интерфейс Notifier и
убедитесь, что тестовой подписки там нет.

Каждый новый прогон начинайте со сброса счётчика запросов:

```bash
docker compose exec -T db psql -U mtl_horizon -d mtl_horizon \
  -c "DELETE FROM service_state WHERE name = 'live_budget'"
```

Без сброса второй прогон упрётся в использованный предел.

## 17. Живые проверки Horizon и предел запросов

Проверки пула и чтение в обозревателе ходят к настоящему Horizon. Чтобы
прогон не вышел за предел, поставьте транспортный лимит: с
`MTL_HORIZON_LIVE_BUDGET=N` ни один запрос установки не уходит наружу сверх
N — ни из worker, ни из history, ни из команд, ни из админки, включая
проверки серверов и повторы. Счёт общий для всех процессов и переживает
рестарт. Когда предел исчерпан, в ошибках написано `the live budget is used
up`. Сброс — той же командой, что в разделе 16.

```bash
docker compose up -d worker history api          # пересоздать службы с новым .env
docker compose exec -T db psql -U mtl_horizon -d mtl_horizon -Atc \
  "SELECT value FROM service_state WHERE name = 'live_budget'"   # сколько израсходовано
```
