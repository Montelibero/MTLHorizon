# Инструкция владельцу: свой список и регулярный сбор

Это инструкция, а не деплой: здесь написано, *как* подключить собственный
список аккаунтов и запустить регулярный сбор на сервере. Сам скрипт выкладки и
решение о запуске — за владельцем. Все команды проверены на пилотной выборке
этапа 03 (`docs/stage-03-report.md`).

## 1. Что понадобится

- Сервер с Docker и Docker Compose v2, немного места под PostgreSQL
  (прикидка — раздел 9) и исходящий HTTPS к Horizon.
- Решение о режиме: **публичный** `https://horizon.stellar.org` (1 запрос в
  секунду, сделки самых активных аккаунтов недоступны — 503) или **свой**
  Horizon (свой `MTL_HORIZON_URL`, свои лимиты).

## 2. Поднять

```bash
git clone <репозиторий> mtl-horizon && cd mtl-horizon
git checkout <commit этапа 03>
cp .env.example .env            # задать POSTGRES_PASSWORD
docker compose build
docker compose up -d db api
docker compose run --rm api alembic upgrade head     # довести схему до 0003
docker compose run --rm api alembic check            # No new upgrade operations detected.
curl -s http://127.0.0.1:8000/ready                   # 200
```

API публикуется только на `127.0.0.1:8000`, PostgreSQL не публикуется вовсе.
Регулярный сбор — отдельная служба `collector` (раздел 5); `docker compose up`
её не стартует.

## 3. Свой список

Скопируйте пример в игнорируемый каталог и заполните:

```bash
mkdir -p local
cp local-tracking.example.yaml local/tracking.yaml
```

- `accounts`: `address` (G-адрес), `mode`, `reason`. История и регулярный
  сбор ведутся только для `FULL`; `CANDIDATE`, `ASSETS_ONLY`, `DISABLED`
  сохраняются как есть и не читаются. Эмитент актива может остаться
  `CANDIDATE`: он слишком активен, чтобы грузить целиком.
- `markets`: пара активов (`base`/`counter`), обе ориентации — один и тот же
  рынок.
- `reason` обязателен: почему аккаунт в списке.

```bash
alias bf='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.backfill'

bf import-config --file local/tracking.yaml --dry-run     # проверить: все ошибки сразу, ничего не записано
bf import-config --file local/tracking.yaml
```

Повторный импорт того же файла ничего не меняет. Записи, которых в новом
файле нет, не удаляются. Режим аккаунта меняется только с `--apply-changes`.
Добавить аккаунт можно в любой момент: коллектор перечитывает список перед
каждым циклом.

## 4. Проверить источник

Одна команда, около десяти запросов, ничего не пишет:

```bash
alias lc='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.collector'
lc check
```

Она читает вперёд пять потоков одного аккаунта и рынок и показывает:
начинает ли сервер чтение ровно выше заданной позиции, не повторяется ли
запись на стыке страниц и начинает ли сервер с самой старой записи, когда
позиция ниже хранимой истории. Всё `ok` — можно запускать. `FAIL` — не
запускайте на этом источнике, разберитесь сначала.

## 5. Первый старт и граница

Один цикл руками, чтобы увидеть, что получается:

```bash
lc once --report local/reports/first-cycle.json
```

Что произойдёт: каждый поток списка получит стартовый леджер — последний
леджер сервера в этот момент, — и с этого места начнётся новая история.
Прежнее не читается и не стирается: это работа backfill (раздел 6). Чтобы
продолжить сразу после загруженного backfill и не оставить дыры, назовите
его верхнюю границу:

```bash
lc once --start-ledger L        # L — последний леджер, загруженный backfill
lc status                       # где стоит каждый поток и насколько отстал
```

Граница фиксируется один раз и при рестарте не сдвигается. Аккаунт,
добавленный позже, получит свою границу в первом цикле после добавления.

## 6. Регулярный сбор

```bash
docker compose --profile collector up -d collector        # раз в MTL_HORIZON_COLLECTOR_INTERVAL секунд (по умолчанию 900)
docker compose --profile collector logs -f collector
docker compose --profile collector stop collector         # SIGTERM: цикл дописывает страницу и выходит
```

Служба перезапускается сама (`restart: unless-stopped`), порт не публикует.
На одну базу — один коллектор: второй откажется стартовать.

Каждый цикл: спросить сервер о последнем леджере и дочитать каждый поток до
него. Рынок читается первым. Поток, который не удалось прочитать, не мешает
остальным и спрашивается снова с растущей паузой. Цикл ограничен бюджетом
(`MTL_HORIZON_COLLECTOR_MAX_REQUESTS`, время — девять десятых интервала);
недочитанное достаётся следующему циклу.

Если коллектор не работал дольше, чем сервер хранит историю (у публичного —
около 408 дней), пропуск помечается `unverifiable`, а не закрывается как
полный.

### История до границы

Backfill и коллектор никогда не читают источник одновременно; у живого сбора
приоритет — backfill уступает, как только коллектору пора в цикл.

```bash
bf estimate --from-ledger L1 --to-ledger L0                       # сколько страниц и запросов
bf run --from-ledger L1 --to-ledger L0 --max-requests 2000         # бюджет обязателен
bf run --full-retention --max-requests 5000 --max-seconds 3000     # вся история сервера, тоже с бюджетом
bf status
bf verify --from-ledger L1 --to-ledger L0 --aggregations           # сверка с сервером
```

Без границ, без `--full-retention` или без бюджета `run` и `reimport`
откажутся, не сделав ни одного запроса. Остановленный запуск продолжается с
чекпоинта. `--context parents` читает в 2,7 раза меньше запросов, но без
контекста встреченных транзакций (раздел 15 `docs/architecture.md`).

## 7. Что смотреть

| Где | Что значит |
| --- | --- |
| `lc status` | `frontier` и `lag` каждого потока; `global frontier` — минимум по всем: ниже него дыр нет; `no collector is running` — служба не работает |
| `failures`, `error` в `status` | сколько циклов подряд поток сбойнил и почему; `503` у очень активного аккаунта — ограничение публичного Horizon |
| `docker compose --profile collector ps` | служба up; упавшая — перезапустится |
| `curl :8000/health`, `curl :8000/ready` | живость API и готовность базы (это API, не коллектор) |
| журнал коллектора | `cycle failed` с нарастающей паузой — источник или база недоступны; `rate limited` — сервер просит подождать |

Тревожиться стоит, если `lag` растёт от цикла к циклу, `failures` не
обнуляется или `no collector is running` при запущенной службе.

## 8. Резервное копирование

```bash
docker compose exec -T db pg_dump -U mtl_horizon -Fc -d mtl_horizon > mtl-horizon-$(date -u +%Y%m%d).dump
```

Восстановление проверяйте не на рабочей базе, а на черновой, и сверяйте
слепок:

```bash
docker compose exec -T db psql -U mtl_horizon -d postgres -c 'CREATE DATABASE mtl_horizon_restore_check'
docker compose exec -T db pg_restore -U mtl_horizon -d mtl_horizon_restore_check --no-owner < mtl-horizon-YYYYMMDD.dump
# слепки рабочей и восстановленной за одно окно должны совпасть:
docker compose run --rm -T api python -m app.backfill fingerprint --from-ledger L1 --to-ledger L0
docker compose run --rm -T -e MTL_HORIZON_DATABASE_URL=<url восстановленной> api python -m app.backfill fingerprint --from-ledger L1 --to-ledger L0
docker compose exec -T db psql -U mtl_horizon -d postgres -c 'DROP DATABASE mtl_horizon_restore_check'
```

Проверено на пилоте: база в 26 МБ сжимается в 1,15 МБ, восстановленная
совпала со слепком по всем семи таблицам окна.

## 9. На что рассчитывать

- **Один пустой цикл** по 17 потокам выборки — 18 запросов (root и по
  странице на поток). При интервале 15 минут это около 1 700 запросов в
  сутки. Для тысячи аккаунтов (4 000+ потоков) так нельзя: нужен свой Horizon
  или сигнал «где что-то было».
- **Цикл с новыми записями**: +2 запроса на каждую неизвестную транзакцию
  сделки рынка, +3–4 на транзакцию аккаунта (полный контекст).
- **Место**: строка операции — около 1,7 КБ с индексами, эффект — 1,4 КБ,
  сделка — 2,4 КБ, транзакция с XDR — 8–12 КБ. Считать надо от операций и
  эффектов, а не от транзакций: в пилоте медиана — 70 операций на
  транзакцию, в окне 7 дней — 5.

## 10. Чего не делать

- Не запускать второй коллектор на ту же базу и не держать коллектор и
  backfill на разных базах против одного Horizon: блокировки действуют в
  пределах одной базы, темп сложится.
- Не поднимать темп выше 1–2 запросов в секунду к публичному серверу.
- Не читать историю без бюджета.
- Не деплоить и не менять существующие сервисы без отдельного решения.
