# Архитектура MTL Horizon: этапы 01–06

Проект — read-only индексатор истории Stellar для Montelibero. Он бессрочно
хранит историю явно выбранных аккаунтов и сделки выбранных активов и рынков.
Это не Stellar Core и не форк Horizon: текущее состояние сети и отправка
транзакций сюда не входят.

4e13b1be`, `go-stellar-sdk @ 35ebe09e`) и по ответам живого сервера
`30.0.1-6f7cff39` (раздел 10 того файла).

## 2. Модули и границы между ними

```
app/
  api/         HTTP: проверка живости и готовности, webhook Notifier
  storage/     PostgreSQL: схема, правила записи, покрытие, блокировки, привязка к сети,
               очередь заданий (jobs), журнал доставок (events), общий темп (pace),
               состояние серверов пула (pool_state)
  sources/     Horizon снаружи: HTTP-клиент одного сервера (horizon.py), пул (pool.py),
               курсоры, REST → строки, конвертации
  notifier/    форма webhook Operations Notifier (format.py) и проверка подписи (signature.py);
               ни Horizon, ни SQL не знает
  worker/      событийный сбор: берёт задания и приносит транзакции целиком
  pool/        проверка пула (check.py — та же функция для будущей админки) и команды check, status
  collector/   чтение вперёд: цикл, CLI, проверка источника — для восстановления и сверок
  backfill/    загрузка окна леджеров: CLI, списки наблюдения, проверки
  cli_common.py  общее командным строкам: журнал, база, клиент пула, таблицы
alembic/       миграции
tests/         тесты; каждому тесту — своя база; Horizon и Notifier заменены фейками
scripts/       вспомогательные проверки (sdk_probe.py, replay_window.py)
```

Направление зависимостей строго в одну сторону:
`worker` / `pool` / `collector` / `backfill` → `sources` → значения →
`storage`. Модуль `storage` не знает ни Horizon, ни HTTP; единственное, что
он берёт не из себя и не из настроек, — тип прочитанной доставки (`Notice`)
модуля `notifier`, а тот ни от чего не зависит. Модуль `sources` не знает
SQL: пулу общий темп передают объектом с тремя методами (`reserve`, `again`,
`pause`). `worker`, `collector` и `backfill` решают, *что* и *когда* писать,
`storage` — *как* это ложится без дублей. `backfill` — команда, которую
запускают руками. `worker` — служба (`run`): задание за заданием, пока её не
остановят. `collector` — команда для восстановления.

## 3. Схема базы данных

15 таблиц. Миграции: [`0001_history_schema.py`](../alembic/versions/0001_history_schema.py)
(схема целиком) и [`0002_backfill_bookkeeping.py`](../alembic/versions/0002_backfill_bookkeeping.py)
(три добавления, которые понадобились загрузке истории: перечислены в
разделе 12).
Модели — [`app/storage/models.py`](../app/storage/models.py); тест

### Идентичность: естественные ключи

| Сущность | Ключ | Примечание |
| --- | --- | --- |
| Аккаунт | `history_accounts.account_id` — G-адрес | M-адрес хранится рядом в `*_muxed`, участником всегда является G-адрес |
| Актив | `history_assets.asset_id` = `native` или `CODE:ISSUER` | Колонки `asset_type`, `asset_code`, `asset_issuer` хранятся тоже; CHECK следит, что они согласованы с ключом |
| Леджер | `history_ledgers.sequence` | |
| Транзакция | `history_transactions.id` — Total Order ID | Хеши — отдельные уникальные колонки |
| Операция | `history_operations.id` — Total Order ID | |
| Эффект | `history_effects.id` — id эффекта из REST | `paging_token` хранится отдельно; CHECK: оба кодируют одну пару (операция, номер) |
| Сделка | `history_trades.id` = `<operation_id>-<trade_order>` | Не зависит от того, какая сторона base |

Horizon использует суррогатные `id` для аккаунтов и активов. Они зависят от
порядка вставки в конкретной базе и ничего не значат вне её. Когда появится
второй источник (архив), он должен отображаться в те же объекты, а не
приносить свои id. Поэтому ключи естественные, а чужие идентификаторы
хранятся как атрибуты источника и эквивалентными не считаются.

### Типы

- **Суммы** — `BIGINT` в строопах. На сети суммы — 64-битные целые, так что
  преобразование строки вида `"123.0000456"` в строопы точно; строка с числом
  знаков после точки больше семи отвергается, а не округляется.
- **Цена** — `price_n`, `price_d` (`BIGINT`), точная дробь, как её отдаёт
  Horizon. Десятичная строка цены не хранится: она выводима.
- **Время** — `TIMESTAMPTZ`, UTC, с микросекундами. У Horizon время без
  таймзоны; здесь тип выбран так, чтобы значение не зависело от настроек
  сессии.
- **Типы операций и эффектов** — `TEXT` (`type`) и `INTEGER` (`type_i`), без
  enum. Неизвестный тип сохраняется.
- **XDR** — `TEXT` с base64. `result_meta_xdr` и `fee_meta_xdr` nullable:
  NULL означает «не получено», а не «пусто».
- **`raw`** — `JSONB`, содержимое JSON ответа (не побайтовая копия HTTP-ответа).

### Избыточность, принятая сознательно

`ledger_close_time` продублирован в транзакциях, операциях, эффектах и
сделках. Время закрытия леджера неизменно, а запросы по времени и
совместимый с Horizon вывод (`created_at`) нужны везде; без этого каждый
такой запрос требовал бы соединения с `history_ledgers`.

### Согласованность идентификаторов проверяет база

Total Order ID и курсоры вычисляются из частей, и база следит, что записаны
они согласованно:

- `history_transactions`: `id = (ledger_sequence << 32) | (application_order << 12)`
- `history_operations`: `id = transaction_id + application_order`
- эффекты и сделки: `id` и `paging_token` соответствуют (`operation_id`, номер)

Ошибка загрузчика, перепутавшего леджер или номер операции, отвергается
базой, а не обнаруживается по неверной сортировке спустя месяц.

## 4. Правила записи

Реализация — [`app/storage/upsert.py`](../app/storage/upsert.py).

**Повторная запись не создаёт дублей и не ухудшает запись.** Запись ищется по
ключу под блокировкой. Если её нет — вставляется (значения должны быть
полной строкой). Если есть — заполняются только те колонки, где в базе NULL.
Колонка, у которой известное значение отличается от приходящего, — ошибка
`ContentConflict`. Это не «последняя запись выигрывает»: два источника
расходятся либо парсер ошибается, и то и другое должен увидеть человек.

**`raw` сливается по ключам.** Ключ, который есть только у одной из сторон,
добавляется; ключ, имеющийся у обеих сторон, должен иметь равное значение.
Более полный ответ дополняет неполный в любом направлении.

**Сделка, полученная с переставленной парой, — та же сделка.** Horizon
отвечает на запрос рынка в обратном порядке перестановкой base и counter.
`upsert_trade` распознаёт это по идентификатору `<operation_id>-<order>` и
согласованной перестановке всех сторонних колонок и не создаёт вторую строку.
Ориентация сохраняется у первой записи; индексы есть для обоих направлений.

**Чекпоинт пишется в той же транзакции, что и данные страницы.** Сборщик
получает страницу по HTTP вне транзакции, затем одной транзакцией пишет
родителей, записи и `set_checkpoint`. Откат отменяет и данные, и прогресс;
страница будет прочитана заново.

**Внешние ключи включены.** У Horizon их нет — он пишет большими пакетами и
не может ждать родителей. При наших объёмах (порядка тысячи аккаунтов)
стоимость FK незаметна, а фиктивная «полная» запись без родителя становится
невозможной на уровне базы.

## 5. Покрытие и политики отбора

### `tracked_*` — списки наблюдения

- `tracked_accounts`: `enabled` (с этапа 04, раздел 20; до него — `mode` ∈
  FULL, ASSETS_ONLY, CANDIDATE, DISABLED), `reason`, даты; с этапа 05 —
  `origin` (откуда аккаунт: `legacy`, `yaml`, `manual`, `discovery`),
  `discovered_by`, `watch_since_ledger` и `boundary_due` (раздел 28).
  Признак не входит в ключ: аккаунт включается и выключается простым
  `UPDATE`, накопленное не удаляется.
- `tracked_assets`, `tracked_markets`: независимые списки с признаком
  `enabled`. Сделка отслеживаемого рынка собирается независимо от того, есть
  ли её участники в списке аккаунтов (проверено тестом). У актива с этапа 05
  есть отдельный флаг `discover` — правило обнаружения держателей его
  trustline, не смешиваемое с `enabled` (раздел 26).
- Рынок — **неупорядоченная** пара: всегда `base_asset_id < counter_asset_id`,
  поэтому пара, названная в любом порядке, — одна строка. Какая сторона
  считается base при выводе, решает запрос.

Попадание аккаунта в `history_accounts` не означает, что он отслеживается:
это реестр всех встреченных аккаунтов.

### `sync_coverage` — что именно проверено

Покрытие — утверждение о диапазоне, а не следствие наличия строк.

| Поле | Смысл |
| --- | --- |
| `subject_type`, `subject_key` | аккаунт, актив, рынок или `global` |
| `data_type` | transactions, operations, effects, trades |
| `selection_policy`, `policy_version` | политика отбора и её версия, с которой собран диапазон |
| `from_ledger`, `to_ledger` | диапазон включительно |
| `source` | откуда собрано: `horizon:pool` — логический источник, один на весь пул (до этапа 05 — `horizon:<первый сервер списка>`; переименовано миграцией `0007`, раздел 25) |
| `state` | `pending` — не проверено; `complete` — проверено, есть записи; `empty` — проверено, записей нет; `unverifiable` — источник уже не может ответить за диапазон (он ниже хранимой истории) |
| `verified_at` | момент проверки; NULL только у `pending` (проверяется CHECK) |

Для одного набора (субъект, тип данных, политика, версия политики) диапазоны
**не пересекаются** — это ограничение `EXCLUDE` в PostgreSQL. Поэтому
проверенный набор леджеров — простое объединение диапазонов, а «пустой
проверенный» всегда отличим от «непроверенного». Разделение диапазона — это
замена его строки на части в одной транзакции. Соседние части одного
состояния сливаются в одну строку, так что страница за страницей таблица не
растёт. `detail` хранит причину у `unverifiable`.

`complete` и `empty` означают только одно: этот поток был прочитан до конца
в этих границах у этого источника. Не «вся жизнь аккаунта» и не «все XDR на
месте».

Политика и её версия входят в ключ непересечения: один и тот же диапазон может
быть собран дважды — под разными политиками (в базе этапа 03 — под ASSETS_ONLY
и затем под FULL; сейчас у потоков аккаунта одна политика, `FULL`). Диапазон
считается покрытым для политики только по её собственным строкам.

## 6. Порядок сохранения: родители раньше детей

Эффекты и сделки ссылаются на операцию, операция — на транзакцию, та — на
леджер и аккаунты. База требует, чтобы родитель существовал. Порядок записи:

```
history_ledgers, history_accounts, history_assets
  → history_transactions
    → history_operations (+ участники)
      → history_effects, history_trades
```

Загрузчик, встретивший эффект или сделку без сохранённой операции, обязан
сначала:

1. найти операцию в базе по `operation_id`; транзакция — тот же id с
   обнулёнными 12 битами;
2. если её нет — догрузить `/operations/{id}` и её транзакцию
   `/transactions/{hash}`, сохранить их в указанном порядке, и только затем
   — эффект или сделку, в одной транзакции.

Если родитель недоступен (404, запись за границей удержания Horizon),
эффект и сделка **не сохраняются**: поток останавливается с ошибкой, его
страница не записывается, курсор и покрытие не двигаются. После исправления
причины запуск продолжается с того же места. Таблица для «сирот» не
создаётся (решение и его альтернатива — в разделе 12).

Хранится ли контекст транзакции целиком, говорит не наличие её строки, а
колонка `history_transactions.context_loaded` (раздел 11).

| `history_transactions (transaction_hash)` U, `(inner_transaction_hash)` U | поиск по хешу, в том числе по внутреннему хешу fee-bump |
| `history_transactions (ledger_sequence, application_order)` | транзакции леджера |
| `history_transaction_participants (account_id, transaction_id)` | история транзакций аккаунта, уже отсортированная по времени: TOID растёт хронологически |
| `history_operation_participants (account_id, operation_id)` | история операций аккаунта |
| `history_operations (source_account, type_i, id)` | операции аккаунта по источнику; с фильтром по типу (`manage_data` — `type_i = 10`) |
| `history_operations (type_i, id)`, `history_effects (type_i, operation_id, effect_order)` | «тип + идентификатор»: все операции или эффекты типа, по порядку |
| `history_effects (account_id, operation_id, effect_order)` | эффекты аккаунта по порядку |
| `history_trades (base_asset_id, counter_asset_id, ledger_close_time)` и `(counter_asset_id, base_asset_id, ledger_close_time)` | рынок + время в любой ориентации пары |
| `history_trades (operation_id, trade_order)` U | сделки операции; хронологический порядок сделок — по TOID операции, а не по текстовому `id` |
| `history_trades (base_account_id, operation_id)`, `(counter_account_id, operation_id)` | сделки аккаунта с каждой из сторон |
| `history_assets (asset_issuer)` | все активы эмитента |
| `sync_coverage (subject_type, subject_key, data_type)` | покрытие субъекта |

Чего намеренно нет: индексов по времени в транзакциях, операциях, эффектах и
сделках, кроме рыночных (время → леджер даёт `history_ledgers`); отдельного
индекса по `type` текстом (известный тип ищется по `type_i`, неизвестный —
тоже по `type_i`); партиционирования и кэширования. Horizon сам удалил
большую часть аналогичных индексов как неиспользуемые (миграция 67).

## 8. Сеть, секреты, доступ

- **Одна сеть на базу.** Таблица `network_identity` с одной строкой; миграция
  создаёт её с passphrase public network. `assert_network()` вызывается при
  проверке готовности и перед записью: база testnet с конфигурацией pubnet
  (и наоборот) не используется.
- **Секреты — только через окружение.** Файла Compose два. На сервере —
  `compose.yaml`: образ приложения из GitHub Packages, в файле нет ни
  переменных, ни сборки, ни файла настроек — каждое значение вписано в него
  как есть; в репозитории лежит копия с заглушками, копия на сервере с
  настоящими секретами в репозиторий не возвращается. На машине разработки —
  `compose.dev.yaml` (образы из исходников, сервис тестов), значения читаются
  из `.env` (файл в `.gitignore`); в репозитории только `.env.example` с
  заглушкой. Строка соединения в репозиторий не пишется, `alembic/env.py`
  берёт её из `MTL_HORIZON_DATABASE_URL`.
- **PostgreSQL не публикует порт.** База доступна только внутри сети
  Compose. Тесты тоже выполняются внутри этой сети (`docker compose --profile
  test run --rm tests`, файл `compose.dev.yaml`) на отдельной временной базе.
- **API — только localhost.** `127.0.0.1:8000` на хосте. В контейнере процесс
  слушает все интерфейсы: иначе порт не опубликовать. Вне контейнера
  значение по умолчанию — `127.0.0.1`.
- **Образ** запускается от непривилегированного пользователя; healthcheck —
  `curl`, без запуска интерпретатора.
- **Внешнего трафика нет.** В этапе 01 нет ни одного обращения к Horizon или
  Core; тесты ходят только в локальную базу.

## 11. Загрузка окна леджеров (этап 02)

Код: [`app/backfill/`](../app/backfill) — `cli.py` (команды), `jobs.py`
(какие потоки читать), `loader.py` (чтение и запись), `store.py` (запись в
базу), `config.py` (список наблюдения), `verify.py`, `probe.py`; клиент —
[`app/sources/horizon.py`](../app/sources/horizon.py), REST → строки —
[`app/sources/horizon_records.py`](../app/sources/horizon_records.py).

### Что читается

| Субъект | Потоки | Что означает `complete` |
| --- | --- | --- |
| Включённый аккаунт (`enabled`) | `transactions` (с `include_failed=true`), `operations` (тоже с неудачными), `effects`, `trades` | четыре потока аккаунта прочитаны до конца окна |
| Рынок (`tracked_markets`, `enabled`) | `trades` пары, в одной ориентации — вторая возвращает те же сделки | все сделки пары в окне прочитаны |
| Выключенный аккаунт | не читается; его задание в очереди истории стоит на паузе (раздел 29) | — |

Вторая ориентация пары даёт те же сделки с обменянными сторонами
(проверено на живом сервере), поэтому читается одна.

У очень активных аккаунтов публичный сервер на поток `trades` не отвечает
(503); такой поток останавливается с ошибкой и остаётся `pending` — раздел
13, пункт 7.

### Как читается поток

Задом наперёд, от верхней границы окна к нижней, страницами по 200:

1. страница читается с `order=desc` и курсором; первая — от курсора
   «после леджера L0», так что записи новее L0 не попадают;
2. записи страницы проверяются на порядок: каждая строго ниже предыдущей и
   строго ниже курсора. Страница не по порядку — сломанный ответ: она не
   сохраняется, поток останавливается с ошибкой;
3. **сеть**: для каждой записи страницы догружается недостающий контекст
   её транзакции (ниже);
4. **одна транзакция в базе**: контексты, записи страницы, покрытие,
   чекпоинт.

Непроверенный диапазон может быть шире окна — если окно до этого
планировалось шире или `reimport` слил строки покрытия. Читается только часть
внутри окна, остальное остаётся `pending`.

Остановка в любой момент оставляет согласованное состояние: записанная
страница отмечена, следующая начнётся с чекпоинта. Чекпоинт — курсор
последней записи страницы в `sync_state` с направлением `desc`; он
используется только если его леджер — верх всё ещё непроверенного диапазона.
Когда поток дочитан, чекпоинт остаётся как запись о том, где поток
кончился; проверенным диапазонам он не мешает.

### Контекст транзакции

Запись, встреченная в потоке, тянет за собой родителей: операцию,
транзакцию, леджер (заглушка: номер и время закрытия). Дальше — всё, что
Horizon отдаёт о транзакции:

| Часть | Откуда | Запросов |
| --- | --- | --- |
| операции | `/transactions/{hash}/operations` | 1 |
| эффекты | `/transactions/{hash}/effects` | 1 |
| сделки | глобальный `/trades` от позиции транзакции, до начала следующей: у Horizon нет маршрута сделок под транзакцией или операцией | 1, только если в операциях есть способные торговать |

Колонка `context_loaded` перечисляет сохранённые части. Уже сохранённый
контекст узнаётся по ней и не качается повторно — ни другим потоком, ни
следующим запуском.

### Покрытие при чтении

Страница, закончившаяся на записи в леджере L, доказывает только леджеры
выше L: в самом L могут быть ещё не прочитанные записи. Поэтому
`[L + 1, верх]` закрывается (`complete` или `empty`), а `[низ, L]` остаётся
`pending` с чекпоинтом. Когда поток исчерпан, закрывается и остаток.

Перед закрытием остатка читается текущая нижняя граница истории
источника (`history_elder_ledger`). Она движется вверх, и может пройти
сквозь ещё не прочитанные леджи — **410 при этом не обязательно будет**:
сервер может просто вернуть пустую страницу. Поэтому всё, что ниже текущей
границы, помечается `unverifiable`, а не `complete`.

Если сервер ответил 410, непрочитанный остаток диапазона — от его низа до
леджера последней сохранённой записи включительно — становится
`unverifiable`: 410 говорит, что курсор лежит ниже хранимой истории, но не
говорит, были ли ещё записи ниже. Одно исключение: транзакция, на чей курсор
пришёл 410 в самом старом хранимом леджере, — первая в нём, так что этот
леджер дочитан и закрывается `complete`. Если история ушла между страницей
и загрузкой контекста её записей, поток падает с ошибкой, ничего не записав;
следующий запуск дочитывает остальное.

### Клиент Horizon

Один HTTPX-клиент на процесс; соединения переиспользуются. Темп задаёт сам
клиент (по умолчанию 1 запрос/с). Публичный Horizon ограничивает запросы по
IP и сообщает об этом только отказом: 429 с заголовками `X-RateLimit-*`
(лимит 3000, время ожидания в `X-RateLimit-Reset`), без `Retry-After`.
Клиент ждёт столько, сколько просит сервер (до 15 минут), а если просят
дольше — останавливает запуск с ясной ошибкой; его продолжат позже.

Повторяются только GET и только при временных ошибках (обрыв, таймаут, 408,
429, некоторые 5xx), с экспоненциальной паузой и jitter; попыток не больше
заданного числа. 404 и 410 — окончательные ответы, у каждого свой тип
ошибки.

У запроса есть жёсткий дедлайн (60 с). Соединение, на котором сервер
замолчал, бросается, запрос повторяется на новом. Четыре одинаковых
ответанных запроса подряд — ошибка: так ловится зацикливание страниц.

`_links.next` не доверяют: ссылка должна вести на тот же origin и тот же
запрос; из неё берётся только курсор, параметры фильтра сохраняются
запрошенные. Ссылка читается только у полной страницы — Horizon ставит
`next` на каждую страницу, в том числе на последнюю и пустую.

### Участники при загрузке

| Кто назвал аккаунт участником | Что пишется |
| --- | --- |
| Сам Horizon: запись возвращена в потоке этого аккаунта | участник транзакции (и операции — если запись операция) |
| Источник транзакции, источник операции | всегда участник |
| Тело операции: адресат платежа, trustor, claimant, спонсируемый, спонсор парного `begin_sponsoring`, владелец записи в `revoke_sponsorship` | участник операции (и транзакции) |
| Изменение записи аккаунта в meta транзакции | **не пишется**: публичный Horizon meta не отдаёт |

Четвёртая строка — известное неполное место: для ненаблюдаемых аккаунтов
множество участников может быть меньше, чем у Horizon. Аккаунты из списка
наблюдения от этого не страдают: об их участии говорит сам Horizon.

## 13. Что осталось открытым после этапа 02

1. **`result_meta_xdr` недоступен** с публичного Horizon (не отдан ни в одной
   проверенной транзакции). Если meta понадобится — только другой источник.
2. **Участники по изменениям записей** не восстанавливаются без meta
   (раздел 11).
3. **Полнота внутри удержания.** `verify` сверяет сохранённые ID с ново
   прочитанными страницами сервера; внутренние «ямы» самого Horizon так не
   видны.
4. **Граница backfill и live.** У `sync_state` уже есть направление; правило
   передачи фронтира от `desc` к `asc` — следующий этап.
5. **Ориентация сделок при выводе.** Хранится в ориентации источника.
6. **`httpx` в тестовом клиенте** (предупреждение Starlette).
7. **Сделки очень активных аккаунтов недоступны** с публичного Horizon:
   `/accounts/{id}/trades` отвечает 503 (`docs/horizon-schema.md`, раздел
   10). Поток такого аккаунта останавливается с ошибкой и остаётся
   `pending`. Решение за владельцем: свой Horizon; согласиться с
   неполнотой по сделкам таких аккаунтов; собирать их сделки из других
   потоков. В последнем варианте сделки их собственных транзакций уже
   приходят с контекстом, а сторона стоящих и пассивных офферов — через
   `/offers/{id}/trades`; это не реализовано и не проверено.

## 14. Регулярный сбор (этап 03)

Код: [`app/collector/`](../app/collector) — `loader.py` (цикл и чтение
вперёд), `cli.py` (`once`, `run`, `status`, `check`), `check.py`; состояние —
[`app/storage/collector_state.py`](../app/storage/collector_state.py)
(таблицы `collector_source` и `collector_stream`, миграция `0003`).

### Цикл

1. Запрос к корню источника: последний леджер H, старейший леджер, сеть
   (не та сеть — отказ до любой записи).
2. **Одной транзакцией базы:** каждый поток, которого коллектор видит впервые,
   получает стартовый леджер L0 — это H (или `--start-ledger`, чтобы продолжить
   после backfill), — и запоминается, что источник показал в этом цикле.
3. Потоки читаются по очереди (рынок первым) до H; рынок — с одними
   родителями сделки, аккаунты — как backfill, с полным контекстом.
4. Состояние каждого потока: где он остановился, когда последний раз
   дошёл до H, сколько раз подряд сбойнул и почему.

Список наблюдения перечитывается перед каждым циклом. Добавленный аккаунт
получает свою границу в первом цикле после добавления; всё, что старше, —
история, её планирует backfill. Существующее покрытие и границы других
потоков не трогаются.

### Чтение вперёд

Поток читается страницами с `order=asc` от позиции «после всего в леджере
L», где L — его граница. Страница — одна транзакция базы: записи, их
родители или контекст, покрытие, чекпоинт и новая граница потока.

Страница, начавшаяся с записи в леджере X, доказывает, что в леджерах от
низа диапазона до X−1 записей нет: они закрываются `empty`. От X и выше —
`complete`. Страница, оборвавшаяся внутри леджера Y, доказывает только до
Y−1: чекпоинт ставится на последнюю запись, граница потока — на Y−1, и
следующая страница читается строго после этой записи. Запись выше H
(в следующем леджере) или исчерпанный поток закрывает диапазон до H.

Чекпоинт вперёд (`sync_state.direction = 'asc'`) доверяется только если его
леджер — первый непрочитанный: он был записан в той же транзакции, что и
граница под ним.

### Что коллектор не читает и что помечает

- **Уже проверенное backfill.** Если покрытие потока выше его границы уже
  `complete` или `empty`, граница переезжает туда без чтения.
- **Вышедшее из истории.** Если граница потока ниже старейшего леджера
  источника, промежуток до него закрывается `unverifiable` с пояснением, и
  чтение продолжается со старейшего леджера. Сервер при чтении вперёд
  молча начинает с самой старой записи: ни 410, ни пустой страницы, по
  которой это можно было бы узнать.

### Сбой, темп и бюджеты

Поток, который не удалось прочитать, не мешает остальным. Его граница
остаётся, счётчик неудач растёт, следующая попытка — через паузу, которая
удваивается с каждой неудачей (от интервала до суток). 429 с просьбой
подождать дольше, чем клиент позволяет (15 минут), останавливает цикл: ни
один поток больше ничего не спрашивает. Цикл ограничен числом запросов и
временем (девять десятых интервала); недочитанное достаётся следующему.

Защита клиента от зацикливания (одна и та же страница четыре раза подряд)
действует в пределах одного цикла: цикл, которому нечего читать, спрашивает
только корень — каждый цикл, годами.

### Что значит `complete`

Полнота **относительно ответов источника**: поток прочитан до конца в
границах, которые источник держит, и источниковые страницы сошлись. Это не
независимая проверка всей сети: внутренних «ям» самого Horizon и того, что
он когда-то не проиндексировал, отсюда не видно. `empty` — то же, но
записей не было. `unverifiable` — источник уже не может ответить.

### Смена политики

Покрытие хранится под версией политики: если смысл FULL изменится (например,
решат не догружать контекст), версия растёт, и старое покрытие остаётся
правдивой записью того, что было собрано раньше. Границы коллектора —
свойство потока, а не политики: при смене версии политики их надо
перепланировать вместе с покрытием, а не оставлять как есть.

## 15. Только родители (режим `parents`)

Режим чтения для backfill и для сделок рынка в коллекторе. Записи потоков
сохраняются как пришли; из источника дополнительно берётся только то, без
чего запись не сохранится:

| Запись | Что догружается |
| --- | --- |
| транзакция из потока аккаунта | ничего: запись — это уже транзакция |
| операция | её транзакция, если строки ещё нет |
| эффект | операция и её транзакция |
| сделка | операция и её транзакция |

Участники — те, кого назвал Horizon (запись возвращена в потоке аккаунта),
источники и то, что выводится из тел самих этих записей. Контекст
транзакции не загружается, и `context_loaded` остаётся пустым: по нему
видно, что операция, эффект или сделка этой транзакции могут быть не все.
Неполнота обозначена, сырых записей не потеряно.

Это даёт ту же историю аккаунта и тот же рынок (по ID и полям — на окне
выборки, раздел отчёта этапа 03) за 37 % запросов. Чего нет — полного
контекста встреченных транзакций: соседних операций, чужих эффектов и
сделок внутри них. Для графика рынка это не нужно; для «всё, что произошло
в транзакции» — нужно, и тогда читают `full` или дочитывают контекст
позже.

## 16. Кто читает источник

*(Пересмотрено в этапе 04. Исключающие блокировки `source` и `demand` сняты:
общий ограничитель темпа, которого не хватало в этапе 03, теперь есть.
Ниже — как теперь.)*

Читать источник могут несколько процессов сразу — worker, backfill,
collector, проверки — и сколько угодно серверов в пуле, но темп один на всю
установку: столько запросов в секунду, сколько сказано в
`MTL_HORIZON_REQUESTS_PER_SECOND`. Он держится не в процессе, а в самой
базе: одна строка `http_pace`, и каждый запрос прежде, чем уйти, берёт в ней
слот — одним выражением `INSERT … ON CONFLICT DO UPDATE … RETURNING`, под
блокировкой строки, так что два процесса никогда не берут один слот
([`app/storage/pace.py`](../app/storage/pace.py)). Упавший процесс оставляет
после себя не больше нескольких слотов в будущем — каждый не длиннее
интервала; ничего не висит.

У событий право дороги, но читающий историю не голодает. Каждый процесс
говорит ограничителю, зачем спрашивает: `events` (worker) или `background`
(всё остальное). Пока события идут потоком — последнее было не раньше трёх
интервалов назад, и не раньше двух секунд, — фоновый читатель получает **один
слот из десяти**: остальные разы он слота не берёт и спрашивает снова. Как
только события стихли, фон идёт в полный темп: worker простаивает почти всё
время, и backfill тогда ничего не теряет. Серверов в пуле больше — темп тот
же.

429 ставит паузу в ту же строку — на столько, сколько сервер просит
(`Retry-After`, `X-RateLimit-Reset`; не сказал — пять секунд), — и она
действует на все процессы: лимит у адреса, а не у процесса. Другой сервер
пула вместо не спрашивается: обойти лимит провайдера сменой алиаса — не то,
что здесь делается.

Один коллектор на базу остаётся за advisory-блокировкой `instance`
([`app/storage/locks.py`](../app/storage/locks.py)).

Запись в историю — одна за раз, и теперь во всех процессах: каждая
транзакция базы, которая пишет историю, первым выражением берёт
transaction-level advisory lock
([`app/storage/writer.py`](../app/storage/writer.py)). Правила «вставить или
дополнить» читают строку и потом пишут её, и два писателя в двух процессах
могли бы оба решить вставить. Читателей никто не держит; блокировка умирает
вместе с транзакцией. Webhook в историю не пишет и за писателями не ждёт.
Задание на транзакцию, уже сохранённую другой процессом, не спрашивает
источник: что сохранено, говорит база (`context_loaded`).

## 19. Пул Horizon (этап 04)

Всё, что читает Horizon, читает через пул
([`app/sources/pool.py`](../app/sources/pool.py)): worker, backfill,
collector, probe, verify, проверки пула, очередь истории и discovery. Пул —
это клиент одного сервера
([`horizon.py`](../app/sources/horizon.py)) с несколькими заменёнными
хуками: кто ответит на попытку, что делать с ошибкой ответа, у кого спросить
после 404/410, origin какого сервера ждать в `_links.next`. Всё остальное —
темп, повторы, дедлайн, проверка порядка записей и ссылок — общее и не
зависит от того, кто ответил. Поэтому переключение сервера внутри чтения
ничего не теряет: страница спрашивается по курсору и проверяется на порядок,
кто бы её ни ответил.

**Кто отвечает.** Первый подходящий сервер списка — активный, пока
отвечает. Сбой — переход к следующему по кругу; следующий за ним — когда
сбоят и они; первый — снова, когда выйдет cooldown. Ничего не прыгает между
серверами без причины.

**Сбой запроса — не всегда сбой сервера.** После сбоя (нет ответа, 5xx) пул
спрашивает у того же сервера его root — маленький запрос под коротким
дедлайном. Root отвечает — сервер жив, и сбой был делом запроса (тяжёлый
поток, 503 у активного аккаунта): сервер остаётся в строю, а запрос
повторяется один раз на каждом следующем сервере и дальше как всегда. Root не
ответил — сервер оставляется на `MTL_HORIZON_FAILOVER_COOLDOWN` секунд, с
удвоением за каждую неудачу подряд (до часа). Число попыток у запроса то же,
что было: `max_attempts` на все серверы вместе.

**429 — не повод менять сервер.** Пауза ставится общая (раздел 16), и запрос
остаётся на том же сервере.

**Что делает сервер подходящим** (`_unfit`):

| Условие | Откуда известно |
| --- | --- |
| не в cooldown | сам пул |
| сказал о себе недавно: сеть, старейший и последний леджер | root; спрашивается **перед первым использованием** и когда знанию больше `MTL_HORIZON_HEALTH_CHECK_INTERVAL` секунд — никогда по расписанию сам по себе |
| обслуживает сеть установки | `network_passphrase` root против `MTL_HORIZON_NETWORK_PASSPHRASE`; сервер чужой сети не спрашивается никогда |
| хранит леджер запроса и дошёл до него | `history_elder_ledger`, `history_latest_ledger`; леджер запроса — из пути (`/ledgers/N`), из курсора или из id операции; верх — из `client.scope` |

`scope` — то, о чём последовательность чтения: от какого леджера и до
какого. Backfill ставит его окном (`--full-retention` — без низа: низ там,
где кончается история пула), collector — от самой низкой границы потока до
последнего леджера цикла, worker — леджером транзакции. Отстающий сервер не
спрашивается о том, чего у него ещё нет; **404 отстающего сервера ничего не
доказывает** — поэтому он и не спрашивается.

`history()` — то, что пул хранит **сейчас**: спрашивает root у каждого
доступного сервера, не полагаясь на свежесть. Последний леджер — у самого
свежего из ответивших. Старейший — наименьший среди всех серверов, которые
сказали, что хранят, включая те, что в этот момент недоступны: история
сервера со временем только укорачивается снизу, так что его последнее
слово — не ниже того, что он хранит на самом деле. Иначе выход из строя
сервера с самой глубокой историей молча поднимал бы начало истории пула:
окно чтения обрезалось бы, а леджеры ниже помечались бы `unverifiable`
насовсем, хотя их держит просто временно недоступный сервер (раздел 30,
пункт 2). `silent()` называет серверы, которые сейчас о себе не сказали,
— про них пул не знает ничего, и задание истории, чьё окно зависит от
этого, не заканчивается, пока такой есть (раздел 29). Чтение
последовательности начинается от `history()`.

**404 и 410.** Спрашиваются остальные серверы, которым есть что сказать о
запросе (хранят леджер и дошли до него), по одному разу. 200 — он и ответ.
Иначе: 410 от всех — `BeforeHistory` с границами, которые они только что
назвали; 404 от сервера, который хранит леджер, — `NotFound`; а если хоть
один, кому было что сказать, не смог ответить (cooldown, нет ответа) —
`RequestFailed`: **ничего не утверждается**, запрос будет повторён. После 410
границы серверов спрашиваются заново: retention движется, и то, что сервер
говорил о себе раньше, уже неверно.

**Происхождение данных.** `Page.served_by` — кто ответил;
`sync_coverage.served_by` — кто прочитал диапазон (несколько через запятую,
если соседние диапазоны слились). Отчёты команд считают ответы по серверам
(`by_server`) и число переходов (`failovers`). Имя источника у чекпоинтов и
покрытия — одно на весь пул, `horizon:pool` (раздел 25): с этапа 05 оно не
зависит от того, какой сервер стоит в списке первым.

**Передача окна.** Страница backfill кончилась там, где начинается история
ответившего сервера, а ниже окна ещё есть что читать и другой сервер это
хранит: прочитанное сохраняется как проверенное от этой границы и выше, а
остаток спрашивается с курсора на границе — у того, у кого оно есть. Без
запроса вслепую к серверу с короткой историей и без `unverifiable` там, где
история есть у другого. `unverifiable` ставится, только когда **ни один**
сервер пула это не хранит (`lacks()`); пока один может хранить, но
недоступен, диапазон остаётся `pending`.

**Проверка пула** ([`app/pool/check.py`](../app/pool/check.py)): каждый
сервер сам, без перенаправления на резервный — root и один небольшой запрос
истории (`/ledgers/{latest−1}`), до трёх повторов каждого (и не третий раз
после двух таймаутов подряд), медиана успешных, ошибки и таймауты отдельно,
HTTP-статус и те rate-limit заголовки, что сервер прислал (не прислал — так
и сказано). Измеряется время всего HTTP-ответа, а не ping. Ничего в истории и
в курсорах не меняет; решение о том, кто активен, принимает сам пул при
каждом запросе. Результат — `horizon_node_state`: половина от проверки,
половина от работающих процессов (последний ответ, последняя ошибка, до
какого времени сервер оставлен) — для будущей админки, где пул — только
просмотр и проверка.

Чего здесь **нет**: отдельного темпа на провайдера (пул из публичного сервера
и своего делит один темп — консервативно); режимов adaptive и round robin;
адресов через API и админку.

## 20. Независимые правила наблюдения (этап 04)

Три списка — `tracked_accounts`, `tracked_assets`, `tracked_markets` — и у
каждой записи свой флаг `enabled`. У аккаунта больше нет режимов: только
включён или выключен. Правила объединяются по **ИЛИ**: событие приходит, если
совпал хотя бы один включённый аккаунт, актив или рынок. Отключение аккаунта
не трогает активы и рынки и не удаляет собранное. Контрагентов никто не
включает.

Миграция `0004`: `FULL` → `enabled = true`; `ASSETS_ONLY`, `CANDIDATE`,
`DISABLED` → `enabled = false` (они и раньше не собирались). Причина, даты и
старое покрытие остаются, история не удаляется. Какой именно из трёх
неактивных режимов был у аккаунта, не хранится; откат до `0003` пишет
`DISABLED`.

YAML этапа 03 с полем `mode` читается явно: `FULL` — как `enabled: true`,
остальные — как `enabled: false`, с пометкой. `mode` и `enabled` в одной
записи вместе — ошибка; неизвестный `mode` — ошибка. Флаг меняется только с
`--apply-changes`. `parents` остаётся настройкой глубины контекста backfill и
к правилам отношения не имеет. Имя политики у покрытия (`selection_policy`
= `FULL` для потоков аккаунта) осталось прежним: покрытие, собранное при
старых правилах, не потеряло счётчиков.

Что называет операция — берётся из полей, которые кладёт туда сам Notifier
(`logic/stream-processor.js`): аккаунты — `account`, `destination`,
`trustor`, `from`, `sponsoredId`, `claimants[].destination`,
`trades[].seller_id` (и `value` у `manage_data`, если там адрес); ассеты —
`asset`, `source_asset`, `path[]`, `claimants[].asset`,
`trades[].asset_sold`, `trades[].asset_bought`; рынок — пара ассетов сделки в
любой ориентации.

## 21. События: приём и обработка (этап 04)

### Что присылает Notifier

По коду `Montelibero/operations-notifier` на ревизии `cea7e51` (v0.12.0);
webhook и подпись там те же, что на изученной раньше `a474e9c` (v0.11.0).
Пока шёл этап 05, этот коммит переписали в `e4039fb` (та же v0.12.0), и
вышла `0fb6050` (v0.13.0). Обе сверены по diff и учтены читателем: рядом с
базовым адресом аккаунта появился его muxed-вид (`<поле>_muxed`,
`<поле>_muxed_id` — базовый `G…` остаётся, и читается он); доля пула
ликвидности пишется как `asset_type` 3 с `liquidity_pool_id` (до v0.13.0 её
записывали как XLM) — имени у неё здесь нет, и в `problems` сказано именно
это, а доставка всё равно ставится в очередь; пара активов пула читается из
`assets` операции. В сделке пула активы названы в `asset_sold` и
`asset_bought`, как в любой сделке.
Пример — не гарантия поведения установленной версии.

- Одно уведомление — одна операция; одна и та же операция уходит отдельным
  POST каждой совпавшей подписке:
  `{id, subscription, type: "operation", created, sent, operation, transaction}`.
- `operation.id` — TOID операции строкой: `paging_token` транзакции плюс
  номер операции с единицы.
- Ассеты записаны цифрами, не словами Horizon:
  `{asset_type: 0 | 1 | 2, asset_code, asset_issuer}` (с v0.13.0 — ещё 3,
  доля пула ликвидности). `operation.account` —
  базовый `G…`-адрес источника операции (или транзакции). `trades[]` —
  сделки, разобранные из `result_xdr`: `order_book` с `seller_id` либо
  `liquidity_pool` с `pool_id`.
- `transaction`: `hash` (у fee-bump — hash конверта, как в Horizon),
  `paging_token`, `source` (внутренней транзакции), `result_xdr`,
  `envelope_xdr`, `memo`, `time_bounds`.
- Подпись: ed25519 через stellar-sdk над байтами `JSON.stringify(data)`,
  заголовок `X-Request-ED25519-Signature` (base64). Ключ — Stellar-пара;
  публичный ключ Notifier публикует как `publicKey` в своём `/api/status`.
- Успех — любой ответ 2xx. Иначе и при таймауте (`reactionResponseTimeout`
  20 с) — повтор через `retries³` секунд (плюс до 0,1 с), пока уведомлению не
  исполнится 7 дней (`maxNotificationAgeSeconds` 604800) или не накопится 100
  неудач (`maxDeliveryFailures`); затем доставка бросается, а после 10
  брошенных подряд подписка выключается.

Адаптер [`app/notifier/format.py`](../app/notifier/format.py) — единственное
место, знающее эту форму. Читает то, что есть; чего нет — не выдумывает, а
называет в `problems`. Леджер — из `paging_token` транзакции (TOID) и
сверяется с леджером `operation.id`. Проверка подписи —
[`signature.py`](../app/notifier/signature.py): по телу как пришло, до того
как из него читается что-либо.

### Приём

`POST /webhooks/notifier` ([`app/api/app.py`](../app/api/app.py)):

| Ответ | Когда |
| --- | --- |
| 2xx | сохранено — сейчас или более ранней доставкой того же уведомления; после commit |
| 401 | не подписано известным ключом; из тела не читается ничего |
| 413 | тело больше 2 МиБ; не читается |
| 400 | подписано, но не JSON-объект или без `id` и `subscription`: не по чему отличить одну доставку от другой |
| 503 | нет ключей (`MTL_HORIZON_NOTIFIER_KEYS`) или нет базы: ничего не принимается |
| 500 | сбой базы: ничего не подтверждается, Notifier пришлёт ещё раз |

Подтверждается только сохранённое. Подписанное, но в другой форме, чем
читается, сохраняется (`unsupported` или с диагнозом), а не отвергается:
терять подписанное Notifier из-за того, что читатель не понял, не стоит.
Horizon внутри webhook не спрашивается, никакая работа не делается.

`receive` ([`app/storage/events.py`](../app/storage/events.py)) — одна
транзакция базы: журнал и задание вместе или никак. Повтор доставки узнаётся
по `(id, subscription)`; две одинаковые доставки одновременно — одна
сохраняется, вторая видит уже сохранённую. Доставку, которую не прочитать
(тип операции читателю неизвестен, поле не читается), не отбрасывают:
транзакция ставится в очередь с диагнозом — Notifier совпал, иначе бы
доставки не было. Не совпало ни одно включённое правило, и это можно сказать
наверняка, — сохраняется без задания (`unmatched`), с диагнозом. Тип не
`operation` или нет хеша транзакции — `unsupported`.

С этапа 05 у приёма есть ещё два повода поставить транзакцию в очередь,
какие бы поля из неё ни прочитались. Доставка пришла от подписки, которую
эта установка держит активной или взяла вручную (`watch_subscription`,
раздел 28), — значит, это её подписка и решение уже принято, и неполный
набор полей не повод её отвергать. И операция называет актив, помеченный
для discovery (раздел 26): у правила discovery своя подписка, и от `enabled`
самого актива оно не зависит.

### Журнал и задания

`notifier_event` — каждая доставка как пришла: тело, что прочитано, что
совпало, что вышло, когда пришла и что Notifier говорит о том, когда создал и
отправил её. Не удаляется никогда. `processing_job` — одно задание на
транзакцию (`transaction_hash` уникален), сколько бы уведомлений о ней ни
пришло. Состояния задания: `pending`, `running`, `done`, `partial`, `dead`.
Ничего не удаляется.

### Worker

[`app/worker/loader.py`](../app/worker/loader.py) берёт `FOR UPDATE SKIP LOCKED`
ближайшее по времени задание, чьё время пришло, под аренду (`lease_seconds`,
по умолчанию 120 с). Перед каждым запросом — но не чаще трети аренды — аренда
продлевается, и только у задания, которое всё ещё его: если задание у
забрали, воркер бросает работу, ничего не записав. Упавший воркер задания не
теряет: тот, кто встретит задание с истёкшей арендой, возвращает его в
очередь, пока остались попытки, а когда их нет — переводит в `partial` или
`dead`, как всякую неудачу. Остановленный сигналом воркер отдаёт задание как
было, и попытка не считается.

Транзакция приносится по частям, в фиксированном порядке: транзакция,
операции, эффекты, сделки (эффекты и сделки ссылаются на операции). Каждая
часть хранится короткой транзакцией базы сразу по получении; открытой
транзакции базы во время HTTP нет. Последняя часть хранится **в одной
транзакции** с пометкой «готово»: записи и слово о том, что они все здесь,
появляются вместе или никак. Что уже сохранено, не спрашивается — об этом
говорит база (`context_loaded`): повтор приносит только недостающее, а
уведомление о уже принесённой транзакции не вызывает ни одного запроса. Если
операции показывают, что транзакция не могла совершить сделок, поток `trades`
закрывается вместе с операциями.

Запись — правилами backfill ([`store.py`](../app/backfill/store.py)):
естественные ключи, «вставить или дополнить», участники из тел операций и
источников. Записи идемпотентны, поэтому worker и backfill, работающие
одновременно, не дают дублей (проверено: слепок базы после их совместной
работы равен слепку одного backfill). Fee-bump узнаётся по обоим хешам,
неуспешная транзакция приносится как любая.

Неудача — повтор с паузой 5 с · 2ⁿ⁻¹ (до 10 минут), до `--max-attempts`
попыток (8); затем `partial`, если что-то сохранено, иначе `dead`. Оба ждут
`python -m app.worker retry` — или нового уведомления о транзакции: оно
берёт задание обратно в очередь, до трёх раз, дальше только человек.

Транзакции нет ни на одном сервере (404 везде) — тоже неудача, а не сразу
`dead`: о транзакции могут сообщить через секунды после закрытия леджера,
и сервер, у которого леджер есть, ещё не успел её проиндексировать; 404
одного сервера ничего не доказывает. `dead` — только когда кончились
попытки, с причиной «the transaction is on none of the servers» (с этапа
05, раздел 30). А вот когда серверы недоступны — ни один не может
ответить (`Unavailable`), или они просят подождать (`RateLimited`) — это
не попытка: задание откладывается на десять минут, попытки не тратятся,
уже сохранённое не спрашивается.

### Время и фронтир

У доставки хранится, когда она пришла (`received_at`), и что Notifier
говорит о том, когда создал и отправил её. Наибольший леджер среди
уведомлений — это наибольшее увиденное, и `worker status` печатает его
вместе с этими словами: **не фронтир**; из него не следует, что все леджеры
ниже или все транзакции в них были увидены. Состояние очереди видно по
каждому заданию.

## 22. Что не обещано: полнота (этап 04)

Воркер приносит то, о чём ему сказали, целиком. То, что всё будет услышано,
не обещается. По коду Notifier на `cea7e51` и по устройству доставки известны
такие границы:

| Чего может не быть в уведомлениях | Почему |
| --- | --- |
| Операции типа, которого не знает его SDK | такая операция пропускается с предупреждением, уведомления нет |
| Транзакции, которые у него не разбираются | считаются и показываются в `GET /api/status` (`stream.skippedTransactions`, `stream.lastSkippedTransaction`), но не доставляются |
| Доставки, на которые не успели ответить | 20 секунд на ответ; неудача — повтор через `retries³` секунд; после 7 дней или 100 неудач доставка бросается; 10 брошенных подряд — подписка выключается |
| Неявные изменения, которые не являются операцией | Notifier матчит операции; то, что происходит без операции, не покрыто |
| Пассивный оффер, исполненный чужой транзакцией (до v0.12.0) | сделка пассивного оффера не разбиралась в `trades`: владелец узнавал, только если был подписан ещё и на актив; с v0.12.0 в `trades` есть `seller_id` |
| Всё вне подписок и их правил | подписки этой установки регистрируются по спискам наблюдения с правилами v2 (раздел 27), чужие — какие есть; правила v1 у подписок, созданных до v0.12.0, уже, чем v2 (не совпадали `from`, `trustor`, `sponsoredId`, claimants, промежуточные ассеты пути и ассеты сделок; memo не работал); подписка без фильтров совпадает со всем |

Ещё одно наблюдение по коду, не гарантия: в наблюдателе на этой ревизии нет
фильтра по успеху транзакции — операции неуспешных транзакций матчатся так
же.

Курсора прогресса доставки у Notifier нет: `lastIngestedTx` в `/api/status` —
позиция его собственного чтения, а не граница доставленного. Повтора по
запросу тоже нет. Поэтому **доставка без потерь не обещается**. Известные
промежутки — момент добавления аккаунта, время его выключения, окно
регистрации подписки — с этапа 05 закрываются очередью исторического
импорта (раздел 29). Остальное — backfill на окно или collector, сверка —
`backfill verify`. Опроса аккаунтов по расписанию по-прежнему нет. Полную историю актива через подписку на актив не
получить: по коду такая подписка матчится по полям операции (`asset`,
`source_asset`, с v2 — `path` и `trades`), а не по самому факту сделок с
активом.

## 23. Решения этапа 04 и расхождения с заданием

| Пункт задания | Как сделано | Почему |
| --- | --- | --- |
| Защита webhook | подпись ed25519 (`X-Request-ED25519-Signature`) по ключам из `MTL_HORIZON_NOTIFIER_KEYS`; без ключей endpoint ничего не принимает | Notifier подписывает каждую доставку; секретного заголовка у него нет |
| Endpoint наружу | API по-прежнему на `127.0.0.1`; HTTPS-прокси — за владельцем | не выставлять без подтверждённой защиты |
| Сохранение до ответа | журнал и задание одной транзакцией, ответ после commit; сбой базы — 500 | подтверждать можно только сохранённое |
| Журнал и задания | две таблицы; ключ доставки `(id, subscription)` | одна операция уходит каждой подписке отдельным POST |
| Каноническая транзакция | хеш, как в Horizon (у fee-bump — конверт); TOID и леджер — из `paging_token` | в уведомлении нет внутреннего хеша; выдумывать нечего |
| Догрузка | `/transactions/{hash}`, `/operations`, `/effects`, глобальный `/trades` от позиции транзакции — методы backfill | не выдумывать endpoints; `result_meta_xdr` публичный Horizon не отдаёт |
| Что считается совпадением | три списка по ИЛИ; не сказать наверняка — всё равно в очередь | Notifier совпал, иначе бы доставки не было |
| Пул: настройки | только окружение (`.env` на машине разработки, `compose.yaml` на сервере); `MTL_HORIZON_URLS` главнее `MTL_HORIZON_URL`, конфликт — ошибка | флаги `--horizon-url` и `--rate` сняты |
| Ошибка запроса против сбоя сервера | проверка root после сбоя | 503 у активного аккаунта — не повод уходить с сервера |
| 429 | общая пауза, сервер не меняется | лимит провайдера по адресу |
| 404/410 | спросить подходящие резервные; утверждать — только когда все, кому есть что сказать, ответили | недоступность всех — не доказанная пустота |
| Смена сервера в окне | проверка покрытия (`scope`, леджер запроса); передача нижней части окна другому серверу | не создавать ложных диапазонов; не объявлять `unverifiable`, пока у кого-то история есть |
| Общий бюджет | ограничитель в PostgreSQL, события с приоритетом, 1 из 10 фону | не допускать голодания исторического импорта |
| Проверка пула | каждый сервер сам, до трёх повторов на тип, медианы, HTTP-время | диагностика не должна зависеть от отказоустойчивости |
| Collector | остался в профиле `collector`, в штатный набор не входит | не запускать регулярный опрос в новой конфигурации |
| Подписки Notifier | не создавались, репозиторий не менялся | без разрешения владельца |

Отдельно о флагах: `--horizon-url`, `--rate` и `--wait-lock` команд backfill
и collector сняты. Адреса и темп — только через окружение; ждать больше нечего,
источник никто не держит.

## 24. Что осталось открытым после этапа 04

1. **Живой Notifier.** Проверка шла с уведомлением, собранным здесь по
   записи Horizon и подписанным одноразовым ключом; рабочий Notifier ничего
   не присылал. Форму нужно сверить с первой настоящей доставкой — она целиком
   лежит в `notifier_event.payload`.
2. **Общий темп между базами.** В пределах одной базы есть; две установки с
   разными базами на один адрес по-прежнему не согласованы.
3. **Полнота.** Границы — раздел 22. Инструмента, который по журналу и
   покрытию сказал бы, где именно пропуск, нет. *(Discovery и очередь истории
   сделаны в этапе 05 — разделы 26 и 29; инструмента «где именно пропуск»
   это не дало.)*
4. **Темп на провайдера.** Пул из публичного и своего сервера делит один
   темп.
5. **Подписки вручную.** Автоматической регистрации по спискам наблюдения
   нет (следующий этап). *(Сделано в этапе 05 — раздел 27.)*
6. **Рост журнала.** Из `notifier_event` ничего не удаляется, и он растёт —
   около 3 КБ на доставку с индексами на фейковых уведомлениях; политики
   хранения нет.
7. **`result_meta_xdr`** недоступен; участники по изменениям записей не
   восстанавливаются.
8. **`parents` как основной режим** — решение за владельцем. *(С этапа 05 —
   режим исторического импорта по умолчанию, раздел 29; живые события
   по-прежнему приносятся целиком.)*
9. **Сделки очень активных аккаунтов** — 503 на публичном Horizon; с пулом
   запрос повторится на другом сервере, если он есть.
10. **`httpx` в тестовом клиенте** (предупреждение Starlette).

## 25. Логический источник и порядок запуска (этап 05)

До этапа 05 чекпоинты (`sync_state`), покрытие (`sync_coverage`) и состояние
коллектора называли источник именем первого сервера списка — например,
`horizon:horizon.stellar.org`. С пулом это стало неверным: читает не первый
сервер, а пул, и порядок адресов в `MTL_HORIZON_URLS` не должен иметь
значения для уже собранного. С этапа 05 источник один — `horizon:pool`.

Миграция `0007` переименовывает `horizon:%` в `horizon:pool` в четырёх
таблицах: `sync_coverage`, `sync_state`, `collector_source`,
`collector_stream`. Если в базе было несколько имён (список в разное время
начинался с разных серверов), строки одного ключа сливаются в одну. Для
состояния потока дальше та строка, у которой курсор продвинулся: у чтения
назад — ниже, вперёд — выше; при равенстве побеждает строка, уже названная
`horizon:pool`. Что было переименовано и когда — остаётся в
`source_identity`. Откат восстанавливает прежнее имя, если в базе оно было
ровно одно; если их было несколько, строки остаются под `horizon:pool` —
какой сервер был первым, откат знать не может и не выдумывает.

От адресов не зависит ничего, что уже записано: записи лежат по
естественным ключам, курсоры — по позиции. Порядок адресов влияет только на
то, кого пул спросит первым.

**Порядок запуска.** Миграции — отдельной командой, до всего, что работает
со схемой:

```bash
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose up -d        # db, api, worker и history
```

`worker` и `history` проверяют схему при старте: не на голове цепочки
миграций или база другой сети — работа не начинается, выход с кодом 1, а в
логе — что именно не готово и какая команда нужна. API в этом состоянии жив
(`/health` 200), но не готов (`/ready` 503). Ни одна служба не применяет
миграции сама.

## 26. Discovery (этап 05)

[`app/discovery/`](../app/discovery/) — правило, отдельное от включённого
наблюдения: актив помечается для обнаружения (`tracked_assets.discover`:
`python -m app.discovery on CODE:ISSUER` или `discover: true` в файле
списка), и держатели его trustline попадают в список аккаунтов. Это не то,
что `enabled` актива: актив может быть включён для истории без
обнаружения и помечен для обнаружения, не будучи включён. Эмитент и список
адресов нигде не зашиты; активов может быть несколько.

**Проход** ([`scan.py`](../app/discovery/scan.py)): `GET /accounts?asset=CODE:ISSUER&limit=200`
через пул, страницы по порядку адреса (`cursor` — последний адрес страницы;
порядок записей и фильтр каждой страницы проверяются, как во всяком чтении).
Считается линия, а не баланс: запись с балансом 0 — всё равно держатель.
Каждая запись проверяется на линию именно этого актива (код и эмитент), до
того как будет посчитана; эмитент не добавляется.

Проход — не снимок сети: он занимает время, сервер может смениться, и у
каждого свой последний леджер. Поэтому о каждой странице хранится, кто
ответил, когда и какой леджер был у него последним (`discovery_run.servers`),
а проход, не дошедший до конца, помечен `incomplete`, а не выглядит целым;
`--resume` продолжает с адреса, где он остановился. Повторный проход
безопасен: аккаунт добавляется один раз, уже наблюдаемый не меняется.

**Добавление** ([`app/watch/accounts.py`](../app/watch/accounts.py)) — один
путь для всех источников: файла списка, команды, обнаружения. Новый адрес
попадает в `tracked_accounts` с `enabled = true`, `origin = discovery`,
причиной, списком активов, по которым он найден (`discovered_by`), и
`boundary_due = true` — дальше его жизнь такая же, как у добавленного
вручную (раздел 28). Источники объединяются без дублей: ключ — адрес.
Отключённый вручную аккаунт повторным проходом не включается; закрытие
trustline ничего не отключает и ничего не стирает. Контрагентов никто не
включает.

**Между проходами — момент открытия линии**
([`events.py`](../app/discovery/events.py)). Воркер приносит транзакцию
целиком, операции и эффекты в том числе, и открытие trustline читается из
сохранённого: эффект `trustline_created` в **успешной** транзакции на актив,
помеченный для обнаружения. Ни намерению из уведомления, ни одной операции
`change_trust` не доверяется: неудачная транзакция ничего не изменила,
удаление линии и смена лимита на существующей — не открытие. Пока эффектов
транзакции в базе нет, решение не принимается — она будет рассмотрена,
когда её задание завершится. Момент, до которого дочитано, хранится в
`service_state` (`discovery_events`), и каждый проход читает сохранённое с
него с запасом в пять минут: повторное чтение ничего не добавляет, а падение
между сохранением транзакции и проходом ничего не теряет — следующий
начинается с той же точки.

У правила своя подписка (раздел 27): уведомления об операциях с таким
активом приходят независимо от того, включён ли актив для истории, и приём
всегда ставит такую транзакцию в очередь.

**Dry-run** перечисляет найденные, новые, уже включённые, отключённые и
ошибки и ничего не меняет — даже записи о проходе. **Расписание** по
умолчанию выключено (`MTL_HORIZON_DISCOVERY_INTERVAL = 0`): включённое — и
воркер запускает проход, когда истекает интервал; выключенное — только
командой.

## 27. Подписки Operations Notifier (этап 05)

### Что изучено

По коду `Montelibero/operations-notifier` на ревизии `e4039fb` (v0.12.0).
Следующая ревизия, `0fb6050` (v0.13.0), маршруты, валидацию запроса и версию
правил не меняет (сверено по diff: она добавляет пары активов пулов
ликвидности и в правилах v2 делает фильтр XLM настоящим фильтром). Где README
Notifier расходится с кодом, верен код.

| | |
| --- | --- |
| Маршруты | `GET /api/status`; `GET /api/subscription` — список; `POST /api/subscription` — один объект или массив; `GET /api/subscription/:id`; `DELETE /api/subscription/:id`. Изменения нет: `PUT` отвечает 405 |
| Авторизация | режим `disabled` — без токена; `token` — токен в `X-Access-Token` или `Authorization`; режим с ed25519-подписью каждого запроса по nonce клиентом **не поддерживается**. Токен администратора действует в любом режиме |
| Фильтры | аккаунт, контракт, memo, типы операций, актив (`asset_code` + `asset_issuer`; для XLM — `asset_code: XLM`). Внутри одной подписки — **И** |
| `filter_version` | 1 — правила до v0.12.0; 2 — полные (совпадают `from`, `trustor`, `sponsoredId`, claimants, промежуточные ассеты пути, ассеты сделок). Регистрируется с 2 |
| Идентичность | владелец + `reaction_url` + фильтры + `filter_version`; повторный POST того же возвращает существующую. **Для актива — нет**: идентичность считается по запросу до валидации, а тип актива дописывает сам сервис, поэтому второй POST подписки на актив создаёт дубликат |
| Лимиты | общий (`MAX_ACTIVE_SUBSCRIPTIONS`) и на пользователя (`MAX_ACTIVE_SUBSCRIPTIONS_PER_USER`, по умолчанию 100). Ответ — **400** с телом `Forbidden. Max active subscriptions exceeded.`, хотя код ошибки в Notifier — 403. Лимит на пользователя действует и в режиме `disabled`: там все подписки принадлежат анонимному администратору |
| Отказы | на POST — всегда 400 с JSON `{"error": …}`; остальные (401, 403, 404 на `DELETE`) — без тела |
| Чужие | список администратор видит весь; `DELETE` чужой — 403, несуществующей — 404; `GET /api/subscription/:id` с неизвестным id не отвечается вовсе — у обработчика нет ветки для отсутствующей подписки (на Node процесс, скорее всего, падает). Поэтому каждый запрос клиента идёт с таймаутом, и нет ответа — `NotifierUnavailable` |

Клиент — [`app/notifier/client.py`](../app/notifier/client.py); встроенный
Notifier для тестов — `tests/fake_notifier_api.py`, написанный по тем же
файлам и повторяющий эти правила, включая 400 на лимит и отсутствие
слияния для активов.

### Желаемое состояние

[`desired.py`](../app/subscriptions/desired.py) читает списки наблюдения и
ничего больше:

- по подписке на каждый включённый аккаунт;
- по подписке на каждый актив, который включён для истории **или** помечен
  для обнаружения;
- рынок покрывается подпиской на **один** из его активов: в каждой сделке
  пары есть оба, а правила v2 матчат операцию по её активам. Native для
  рынка не подписывается никогда — почти каждая операция сети имеет дело с
  XLM. Берётся меньший из двух не-native, так что выбор не зависит от
  порядка сторон.

Две подписки на активы рынка не были бы логическим И — они означали бы
«операции с активом A **или** с активом B». Подписка на актив — наблюдение
новых событий, а не полнота истории актива (раздел 22).

Одна подписка — на вид и ключ, какие бы правила её ни хотели; правила
хранятся при ней (`subscriptions status` говорит, почему она есть), и уходит
она, только когда её не хочет ни одно. Выключение аккаунта отнимает только
его подписку.

### Сверка

[`reconcile.py`](../app/subscriptions/reconcile.py); строки —
`watch_subscription`; состояния `wanted` → `active` | `error` | `ambiguous`,
`retiring` → `retired`, и `manual`.

- **Только своё.** Трогаются только подписки с `reaction_url` этой
  установки. Чужие — даже с тем же аккаунтом — не меняются и не удаляются.
- **Сначала список.** Прежде чем создать, читается список у Notifier:
  подписка с адресом установки и теми же фильтрами — та же, что ответил бы
  на POST. Создание, таймаут которого случился **после** того, как оно
  удалось, находится и берётся, а не создаётся второй раз. Подходящих больше
  одной — `ambiguous`, и ничего не делается ни с одной: решает человек.
- **Активность — только после подтверждения.** Ответ POST ничего не
  значит: строка получает id и состояние `error` («registered, not confirmed
  yet»); активной она становится, когда найдёт себя в списке Notifier с
  нужным адресом и фильтрами.
- **Неудачи хранятся.** Строка говорит, что не так и когда будет следующая
  попытка; пауза растёт от 30 секунд до часа. Недоступный Notifier или отказ
  (лимит) стоит только времени: ничего не забывается.
- **Один проход на базу** (блокировка в PostgreSQL): два одновременных могли
  бы оба не найти и оба создать, а для активов дубликат не сливается. За
  проход — не больше 50 действий.
- **Вручную.** Подписку, созданную человеком, принимают (`adopt`): она
  читается у Notifier, сверяется с тем, что регистрирует установка, и
  получает состояние `manual`. Такую установку никогда не удаляет
  (`managed = false`): сделал человек — удаляет человек. `release` забывает
  её здесь, у Notifier она остаётся.
- **Приём прежде регистрации.** Ничего не регистрируется, пока вебхуки
  этого Notifier не пройдут собственную дверь установки: его ключ должен
  быть в `MTL_HORIZON_NOTIFIER_KEYS`, а
  `MTL_HORIZON_NOTIFIER_CALLBACK_URL` — задан; иначе проход говорит об этом
  и откладывает.

Без адреса API (`MTL_HORIZON_NOTIFIER_API_URL` пуст) ничего не
регистрируется: подписки делаются вручную и принимаются командой `adopt`.

## 28. Жизненный цикл аккаунта (этап 05)

[`provision.py`](../app/watch/provision.py) — один проход. Воркер делает
его в своём фоновом потоке по расписанию (по умолчанию каждые 60 секунд;
до этапа 06 — только пока очередь событий пуста, раздел 34);
`python -m app.watch run` — руками. Каждый шаг читается из базы, а не
помнится между проходами: аккаунт, которому нужен шаг, — тот, чья строка это
говорит. Падение где угодно ничего не теряет: следующий проход находит те же
строки.

| Шаг | Что сделано | Что записано |
| --- | --- | --- |
| 1. Намерение и граница начала | аккаунт добавлен (`boundary_due = true`); проход спрашивает пул о последнем леджере L и **сначала** ставит импорт истории до L, и только потом пишет `watch_since_ledger = L` и снимает флаг | задание `history_job` с `boundary_final = false`; `watch_since_ledger` |
| 2. О нём говорят | подписка регистрируется и подтверждается чтением (раздел 27) | `watch_subscription.state = active` или `manual` |
| 3. Верхняя граница — после подтверждения | последний леджер спрашивается снова (L′), и граница задания поднимается до него | `history_job.to_ledger = L′`, `boundary_final = true` |
| 4. Отключение | импорт становится на паузу, подписка уходит, история остаётся | `history_job.state = paused`; `watch_subscription.state = retiring` → `retired` |
| 5. Включение снова | новая граница начала; импорт, который за этим следует, покрывает время выключения | как шаг 1 |

Порядок шага 1 выбран так, что падение между его половинами оставляет
аккаунт «ждущим границы»: следующий проход планирует импорт снова, а
планирование никогда не сбрасывает прогресс. В обратном порядке падение
оставило бы границу без импорта, и никто бы не заметил.

Промежуток регистрации перекрывается: импорт идёт до L′, а события
принимаются с того момента, как подписка начала действовать. Пересечение
стоит ничего — запись сохраняется один раз. Задерживается подписка или
неоднозначна — граница остаётся незавершённой (`boundary_final = false`):
это и есть явно сохранённый непроверенный диапазон, и `history status`
такие задания показывает.

Проход спрашивает Horizon, только когда есть аккаунт, которому нужна
граница или верхняя граница, и Notifier — только когда есть что
регистрировать. В тишине — ноль запросов.

## 29. Очередь исторического импорта (этап 05)

[`history_jobs.py`](../app/storage/history_jobs.py) — очередь;
[`runner.py`](../app/history/runner.py) — воркер; служба —
`python -m app.history run` (compose-сервис `history`).

**Задание** — вся история одного субъекта: четыре потока аккаунта или
сделки рынка, от начала истории пула (или заданного леджера) до верхней
границы. Хранится в `history_job`: границы, контекст (`parents` или
`full`), состояние, счётчики запросов, страниц и записей, число срезов и
попыток, аренда, последняя ошибка и результат последнего среза. Состояния:
`waiting`, `running`, `done`, `partial`, `error`, `paused`.

**Срез** — один ограниченный запуск backfill над теми же покрытием и
чекпоинтами (`MTL_HORIZON_HISTORY_SLICE_REQUESTS`,
`MTL_HORIZON_HISTORY_SLICE_SECONDS`). У задания нет собственного прогресса:
что срез сохранил — сохранено, что бы дальше ни случилось, и следующий срез
идёт от покрытия. Бюджет проверяется перед страницей, а не внутри неё:
взятая страница читается с контекстом и сохраняется целиком — иначе страница
дороже бюджета держала бы свой субъект вечно, каждый срез тратя запросы
впустую. Срез стоит не больше бюджета плюс контекст одной страницы.
Остановленный сигналом срез заканчивается перед следующим запросом.

**Справедливость.** Берётся задание, которое дольше всех не обслуживалось
(никогда не обслуживавшееся — прежде всех): каждый субъект получает срез,
прежде чем кто-то получит второй. Тысяча аккаунтов с разной глубиной
истории движется вместе.

**Аренда и восстановление.** Срез идёт под арендой (по умолчанию 300
секунд; продлевается перед запросом не реже трети срока — и только у
задания, которое всё ещё его). Воркер, умерший в срезе, ничего не забирает:
встретивший задание с истёкшей арендой возвращает его в очередь, но считает
это неудачей — субъект, у которого всё умирает воркер, надо смотреть, а не
повторять вечно.

**Неудачи** считаются по срезу, а не по запросу, и только когда сервер
ответил. Несколько неудачных срезов подряд (по умолчанию 10) — `partial`
(что-то прочитано) или `error` (ничего); оба ждут `retry`. Срез, который
продвинулся, начинает счёт заново.

**Состояние серверов — не неудача.** Ни один сервер не может ответить
(`Unavailable`) или они просят подождать (`RateLimited`): срез не считается,
задание ждёт две минуты (не больше `retry_cap`) и спрашивает снова — сервер
возвращается через минуту, а не через час.

**Низ окна.** Задание, чей низ — «насколько хватает истории пула», берёт
окно от `history().elder` (раздел 19). Пока хоть один сервер не сказал о
себе (`silent()`), задание не заканчивается: что прочитано — сохранено, а
задание ждёт и называет молчащий сервер — его нижние леджеры могут быть
именно у него. Иначе выход из строя самого глубокого сервера превращался
бы в молчаливое «готово» на укороченном окне. Явно заданный низ, которого
ни один доступный сервер не держит, а молчащий может держать, остаётся
`pending` до его возвращения. `unverifiable` ставится, только когда **ни
один** сервер пула этого не хранит; такие леджеры названы в результате
задания (`unavailable_ledgers`) и прочитанными не считаются.

**Контекст.** По умолчанию `parents` (`MTL_HORIZON_HISTORY_CONTEXT`): все
четыре потока аккаунта читаются, с неудачными транзакциями, а для записи
подтягиваются только родители, без которых её не сохранить. Это полнота
четырёх потоков аккаунта, а не полный контекст каждой транзакции; живые
события по-прежнему приносятся целиком. Raw/XDR не выбрасываются, записи
идемпотентны по естественным ключам — пересечение с worker и backfill
дублей не даёт.

**Приоритет.** Общий темп в PostgreSQL (раздел 16): пока события идут
потоком, история получает один запрос из десяти; очередь событий пуста —
история получает весь темп. Ускорения в обход лимитов нет.

**Управление.** `pause`, `resume`, `retry` — с причиной. Отключение аккаунта
ставит его задание на паузу (`paused_because`), история остаётся.
Планирование заново и `enqueue` только расширяют границы и никогда не
сбрасывают прогресс. Для рынков — постановка существующего импорта сделок
пары в очередь (`enqueue --market`); исторической загрузки операций
произвольного актива через REST нет и не обещается: у Horizon такого
endpoint нет.

## 32. Что осталось открытым после этапа 05

1. **Живая интеграция с Notifier.** Ни одна подписка не создавалась и ни
   одно настоящее уведомление не принималось: регистрация, подтверждение и
   снятие проверены на встроенном Notifier, написанном по коду настоящего,
   а не на нём самом. Первая настоящая установка: `subscriptions reconcile
   --dry-run`, затем `reconcile`, и сверка `status` с тем, что видно в самом
   Notifier.
2. **Режим ed25519-подписи запросов** у Notifier клиентом не поддерживается —
   только `disabled` и `token`.
3. **Лимит подписок.** По умолчанию 100 на пользователя, и в режиме
   `disabled` он тоже считается. Тысяча аккаунтов требует поднятого лимита у
   владельца Notifier; иначе строки останутся в `error` с причиной и будут
   пробовать с растущей паузой.
4. **Замолчавший сервер держит низ окна.** Задание с низом «до начала
   истории пула» не завершается, пока хоть один сервер не сказал о себе.
   Навсегда мёртвый адрес в `MTL_HORIZON_URLS` остановит такие задания в
   `waiting` — адрес нужно убрать. Это намеренно: видимое ожидание лучше
   молчаливого «готово» на укороченной истории.
5. **Полная история произвольного актива** через REST невозможна — у Horizon
   нет такого endpoint. Записано для будущего внешнего импорта.
6. **Discovery — не снимок.** Проход занимает десятки секунд на тысячи
   держателей; кто открыл линию в ходе прохода, найдётся следующим проходом
   или чтением `trustline_created`.
7. **Открытие линии видно, только если транзакция попала в базу** — по
   подписке discovery-актива или через историю наблюдаемого аккаунта. Аккаунт,
   открывший линию до того, как актив был помечен, найдётся только проходом.
8. **Журнал `notifier_event`** по-прежнему растёт без политики хранения
   (раздел 24, пункт 6).
9. **Общее с этапом 04:** темп в пределах одной базы и один на провайдера;
   живая форма уведомления не сверена; `httpx` в тестовом клиенте.

## 33. Админка (этап 06)

[`app/admin`](../app/admin) — страницы под `/admin`, серверные шаблоны Jinja2,
одна таблица стилей и один небольшой скрипт своего производства; без
отдельного frontend-стека, без внешних библиотек и без внешних запросов при
открытии страницы. Слова на страницах — русские, время — UTC с явной зоной
(читатель может включить свою зону: меняется только показ).

**Дверь** ([`auth.py`](../app/admin/auth.py),
[`door.py`](../app/admin/door.py)). Установка открывается одним секретом из
среды (`MTL_HORIZON_ADMIN_SECRET`); без него админка закрыта для всех, и
страница входа так и говорит (fail closed). Сессия — строка в
`admin_session` с хешем случайного токена и собственным секретом; токен
живёт только в cookie: `HttpOnly`, `SameSite=Strict`, `Secure`, когда задан
`MTL_HORIZON_PUBLIC_ORIGIN` (установка за HTTPS-прокси), и отдаётся только
для пути `/admin`. В базе нет ничего, чем сессию можно открыть снова.

Вторая защита — токен в каждой форме, вычисленный из секрета сессии
(HMAC): POST без верного токена отклоняется с 403, и ничего не меняется.
С заданным публичным origin ещё проверяется заголовок `Origin`: запрос,
меняющий состояние, обязан прийти от установки. Формы читаются только как
`application/x-www-form-urlencoded` и не больше 64 КБ — файлов админка не
принимает. **GET ничего не меняет.**

Входы, которые не удались, считаются в `admin_login_throttle` — по адресу
(в виде хеша) и по всем сразу — за окно в 15 минут. Пятый неудачный вход
блокирует адрес на 15 минут; повторное блокирование в следующем окне дольше,
до 8 часов; час тишины снимает счёт. Пока адрес заблокирован, секрет даже не
сравнивается. За прокси процесс видит адрес прокси: с точки зрения счётчика
все читатели за одним прокси — один адрес (раздел 41).

**Страницы** ([`areas/`](../app/admin/areas)) — группы по одному модулю,
каждый строит свой router (`build(door)`); [`web.py`](../app/admin/web.py)
ставит их на приложение по имени. Общее для них — в
[`support.py`](../app/admin/support.py): шаблоны и фильтры, пагинация,
перенаправление с заметкой после действия.

| Группа | Что показывает и что делает |
| --- | --- |
| Дашборд `/admin` | службы живого сбора и истории по их heartbeat — работа / пауза / «не слышно: не работает или застряла», так что пустая очередь не сходит за остановленную службу; очереди, подписки, discovery, размер PostgreSQL, счётчики записей (точно / оценка, с временем измерения); обновляется из базы |
| Аккаунты | список с поиском и фильтрами, происхождение, причина, граница, подписка, импорт, последние события; добавить, включить, выключить, изменить причину; для legacy — поставить историческую загрузку и проверку подписки |
| Активы | два флага порознь — `enabled` (новые события) и `discover` (держатели trustline); добавление, смена флага, «Найти / обновить держателей» — предпросмотр (dry run) или проход с явным бюджетом, оба как задача |
| Рынки | каноническая пара, включение, постановка всей доступной истории сделок; текст о том, что покрывает подписка рынка |
| Discovery | помеченные активы, последние проходы, задачи, расписание (показано, не редактируется) |
| Импорт истории | агрегаты по аккаунтам и рынкам **порознь**, причины ожидания, доля завершённых субъектов (с знаменателем), окно и низ пула на момент последней проверки; таблица заданий; страница задания с четырьмя потоками, покрытием, пробелами, счётчиками прочитанного и добавленного порознь; пауза / возобновление / повтор / приоритет / расширение окна / сверка и перечитывание (задачи); общая пауза очереди |
| Активность | по времени леджера за сутки / неделю / месяц / период, изменение против предыдущего равного окна, доля операций со своими и чужими активами (или «неизвестно»), приблизительный объём с предупреждением об общих записях; общие уникальные цифры и скорость импорта — отдельно |
| Notifier | желаемое против подтверждённого, причины, следующая попытка; «Что там сейчас?» (dry run), «Сверить», «Повторить» (строка в `error` берётся проходом сразу, без ожидания паузы; `ambiguous` — только взгляд, проход такую строку не трогает), принять вручную сделанную подписку и забыть её; лимиты сервиса — как требование, а не как факт |
| Horizon | серверы из настроек (без учётных данных) и то, что о них сохранено; «Проверить все» — задача |
| Задачи | состояние задач, остановка, «ещё раз» |
| График | пара и период → SVG, нарисованный установкой из сохранённых сделок; полоса покрытия рядом, чтобы ровная линия не сошла за тихий рынок |
| Обозреватель | по явному запросу: текущие trustlines и балансы аккаунта, активы эмитента по страницам — с временем чтения и ошибкой, ничего прочитанного не хранится |

Каждое действие страницы — та же сервисная функция, что зовёт команда
предыдущего этапа. Что занимает время, никогда не делается в запросе: это
задача (раздел 34).

## 34. Задачи и фон воркера (этап 06)

[`service_job`](../app/storage/service_jobs.py) — долговечная очередь того,
что запускается из админки (или расписанием) и занимает время: проход
discovery, проверка пула, сверка или перечитывание окна одного субъекта,
проход с Notifier (и его dry run). Запрос только ставит задачу и сразу
отвечает; состояние читается из базы. Частичный уникальный индекс не даёт
двум задачам одного вида и одного ключа стоять или идти одновременно (два
скана одного актива невозможны).

[`TaskRunner`](../app/tasks/runner.py) — исполнитель в фоновом потоке
воркера: берёт задачу под аренду, продлевает аренду, пока та идёт (отдельный
поток), и кончает её там, где она стоит, если задачу отменили или аренда
потеряна. Потерявшийся исполнитель ничего не дописывает: встретивший
просроченную аренду возвращает задачу в очередь, после трёх раз — `failed`.
Отмена — между двумя запросами; прочитанное до отмены остаётся. У каждой
задачи — предел запросов к Horizon, посчитанный **до** отправки
(`Budget`), а у сверки и перечитывания — то же окно и те же формулы, что у
backfill.

**Фон воркера** ([`background.py`](../app/worker/background.py)) — два
потока: provisioning по расписанию и задачи. До этапа 06 проход
provisioning шёл только при пустой очереди событий: под постоянным потоком
событий новый аккаунт мог ждать границу и подписку неопределённо долго.
Теперь проход идёт по расписанию — события ждут или нет, — один на базу
(advisory lock), и спрашивает Horizon, только когда есть кому нужна
граница. Расписание discovery, когда оно включено, тоже кладёт проходы в
очередь задач: проход — задача со состоянием, как любая другая.

**Heartbeat.** Воркер событий, служба истории, поток provisioning и поток
задач пишут в `service_state`, что живы и что делают, — не реже чем раз в 15
с. Дашборд отличает по нему пустую очередь от остановленной службы.
Записи пишутся через upsert: два процесса одного и того же не конфликтуют.

## 35. Исторический API (этап 06)

[`app/history_api`](../app/history_api) — совместимое подмножество REST
Horizon, читаемое только из архива: маршруты аккаунта, транзакции (fee-bump
по обоим хешам), операции и их эффекты, сделки пары, агрегаты,
`/v1/coverage`. Полное описание, отклонения от upstream и EXPLAIN — в
[`history-api.md`](history-api.md). Здесь — принципы:

- **Доступ отдельный.** Это публичный архив: в `compose.yaml` задан
  `MTL_HORIZON_API_ACCESS=open` — читать может всякий, кто достаёт до API.
  Режим `token` (`MTL_HORIZON_API_TOKENS`, `Authorization: Bearer`) закрывает
  чтение: без заданных токенов — 403, с неверным — 401; он же остаётся
  значением самого приложения без настройки. Дверь админки сюда не относится.
- **Ссылки свои.** `_links` указывают на эту установку (`public_origin` или
  базу запроса), а не на upstream.
- **Честный охват.** Ответ говорит, что он из этого архива (`scope`);
  пустой список не значит, что в сети ничего не было; отсутствие поля не
  заполняется выдумкой. Coverage отдаёт неполноту явно.
- **Ограниченно по стоимости.** Только чтение, транзакция только для чтения,
  `statement_timeout` 10 с; страница ограничена; агрегаты за длинный период
  могут не успеть — тогда 503, а не подмена.

## 36. Очередь истории: счётчики, приоритет, пауза (этап 06)

Миграция `0012` добавила `history_job` durable-счётчики: `inserted` и
`repeated` по типам записей (что задание вставило первым и что уже лежало),
`failed_slices`, `time_spent_ms`, `last_progress_at`, `last_slice_outcome`,
`priority`. Счётчики хранящейся страницы пишутся **в той же транзакции, что
и страница** (хук `Backfill(on_page_stored=…)`); счётчики среза — в конце
среза. Считаются только срезы заданий истории: живой сбор в них не входит.
Один срез — одна структурированная строка лога (job, subject, потоки,
курсор, длительность, счётчики, исход).

**Приоритет** — число очков: субъект с N очками выглядит обслуженным на
N×10 минут раньше, чем он был. Приоритетный получает больше срезов, но
никто не голодает: как только другой ждёт дольше, чем длится приоритет,
срез достаётся ему.

**Общая пауза** (`service_state.history_paused`) останавливает взятие
заданий всей очередью, живой сбор не трогает, переживает рестарт; срез в
работе останавливается перед следующим запросом и продолжается после снятия.

**Прерванный срез.** Если база оборвала срез (deadlock, отмена сериализации),
он не считается неудачей предмета: срез спрашивается снова через 2 с,
попытка при этом всё же считается — чтобы не повторяться вечно.

## 37. Сверка подписок по факту и Notifier v0.13.0 (этап 06)

`reconcile.plan()` читает у Notifier его список и отвечает, что сделала бы
сверка и что там действительно есть — без единой записи. Это кнопка «Что там
сейчас?» на странице Notifier и dry run команды.

**Аудит подтверждённых.** Раз в 10 минут и при ручной сверке список
читается снова, и каждая подписка, зарегистрированная здесь как активная,
отыскивается в нём. Удалённая или выключенная самим Notifier (после десяти
непроотвеченных доставок) оттуда исчезает молча — никто об этом не сообщает. Такая
подписка становится снова желаемой и регистрируется заново один раз (список
читается до создания), с растущей паузой: подписку, которую Notifier
выключает раз за разом, не плодят в тесном цикле. Сделанная вручную и
пропавшая — помечается `ambiguous`: решает человек, взамен ничего не
создаётся.

## 39. Живые проверки: транспортный предел и смоук-тест (этап 06)

[`app/sources/live.py`](../app/sources/live.py). С `MTL_HORIZON_LIVE_BUDGET=N`
ни один HTTP-запрос установки не уходит наружу сверх N за весь прогон — ни
к Horizon, ни к API Notifier: root-пробы, повторы, failover и диагностика
считаются на транспортном уровне **до** отправки. Счёт хранится в
`service_state.live_budget` — общий для всех процессов и переживает
рестарт; между попытками не меньше секунды. Исчерпание звучит как «the live
budget is used up», а не как лежащий сервер. Новый прогон начинают с
удаления этой строки.

[`app/smoke`](../app/smoke) — смоук-тест живого Notifier: `status` (2
запроса), `subscribe --account G…` (одна тестовая подписка, запоминается в
`service_state.smoke_subscription`), `watch` (ждёт доставку и конец задания,
читая журнал, без запросов), `unsubscribe` (удаляет только её и смотрит
список, что её нет). Запускать только с разрешения владельца, под
транспортным пределом. На этапе не запускался.

## 41. Что осталось открытым после этапа 06

1. **Живая интеграция с Notifier — выходной барьер.** Проверена на
   встроенном Notifier, не на настоящем. Пока смоук-тест не пройден, код
   готов к пилотному запуску, не к production (раздел 39).
1. **Адреса за прокси.** Счётчик входов видит адрес прокси. Если админку
   будут открывать с разных мест за одним прокси — пять неудачных входов
   заблокируют всех на 15 минут. Читать ли `X-Forwarded-For` — решение
   владельца (заголовок подделывается, доверять можно только известному
   прокси).
1. **Стоимость среза растёт с размером списка.** 218 мс на 5000 субъектов;
   прирост линейный. Лечится выборкой потоков одного субъекта за срез.
   Не сделано: доля от среза в 50 запросов — доли процента.
1. **Скорость импорта по времени записи** идёт по `created_at` без индекса:
   таблицы больше 256 МиБ пропускаются и говорят об этом. Индекс
   `(created_at)` на четырёх таблицах записей добавит следующий этап.
1. **Кэш дорогих счётчиков дашборда** — в пределах процесса: у каждого
   процесса свой.
1. **Русские подписи к цифрам статистики** — в модулях страниц; источник
   английских формулировок — `app/stats`, они могут разойтись.
1. **`docker compose kill/stop` не перезапускает службу** — это явная
   остановка. Процесс, умерший сам, возвращается за секунду; но SIGKILL
   PID 1 изнутри контейнера ядро игнорирует, так что «упал с 137» показан
   только на мягком завершении.
1. **Страницы очереди событий в админке нет** — ошибки видны блоком на
   дашборде и командой `python -m app.worker events`.
1. **График** рисуется сервером из сохранённых сделок; внешней
   библиотеки нет — интерактивности (масштаб, наведение) тоже.
1. **Период графика** ограничен 2000 корзин; агрегаты за длинный период
   могут не успеть за `statement_timeout` 10 с — тогда 503.
1. **Поля `account`, `ledger`, `base`, `counter` в `_links`** исторического
   API ведут путями upstream к ресурсам, которых здесь нет: переход даёт 404
   приложения, а не problem+JSON.
1. **Живые ответы Notifier v0.13.0** не сверялись: форма читателя обновлена по
   его коду и его же примерам, не по настоящим доставкам.
1. **Фильтр по состоянию для переходов с дашборда** (`?state=`) у страниц
   импорта, Notifier и discovery не сделан — дашборд ведёт на страницу
   целиком.
1. **Доля завершённых** считается по включённым субъектам; задания
   выключенных показываются отдельно (`not_counted`) и в долю не входят.
