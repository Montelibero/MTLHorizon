# Архитектура MTL Horizon: этап 01

Проект — read-only индексатор истории Stellar для Montelibero. Он бессрочно
хранит историю явно выбранных аккаунтов и сделки выбранных активов и рынков.
Это не Stellar Core и не форк Horizon: текущее состояние сети и отправка
транзакций сюда не входят.

Факты о Horizon, на которые опираются решения ниже, — в
[`horizon-schema.md`](horizon-schema.md) (проверено по исходникам
`stellar-horizon @ 4e13b1be`, `go-stellar-sdk @ 35ebe09e`).

## 1. Границы проекта

| В этапе 01 | Вне этапа 01 |
| --- | --- |
| Схема исторической базы (миграция `0001`) | Загрузка данных: клиент Horizon, collector, backfill |
| Правила записи без дублей и затирания | Бизнес-API, совместимый с Horizon |
| Разбор курсоров и точные конвертации величин | Графики, агрегации |
| `GET /health`, `GET /ready` | Текущее состояние сети, отправка транзакций |
| Тесты на настоящем PostgreSQL | Импорт из архивов (BigQuery, AWS), интеграция с Notifier |

Ограничение, принятое без обсуждения: **сеть одна — public**. База создаётся
для pubnet и не может быть использована для другой сети (раздел 8).

## 2. Модули и границы между ними

```
app/
  api/         HTTP: только проверка живости и готовности
  storage/     PostgreSQL: схема, правила записи, привязка к сети
  sources/     внешний формат: курсоры Horizon, точные конвертации
  collector/   живой сбор потоков            (не реализован)
  backfill/    догрузка истории за пределами потока (не реализован)
alembic/       миграции
tests/         тесты; каждому запуску — своя база на сервере PostgreSQL
scripts/       вспомогательные проверки (sdk_probe.py)
```

Направление зависимостей строго в одну сторону:
`collector` / `backfill` → `sources` → значения → `storage`. Модуль `storage`
не знает ни Horizon, ни HTTP. Модуль `sources` не знает SQL. `collector` и
`backfill` решают, *что* и *когда* писать, `storage` — *как* это ложится без
дублей. Оба пока существуют как описание границы (docstring пакета), без
работающего кода: пустых сервисов, которые запускаются и ничего не делают,
нет.

## 3. Схема базы данных

15 таблиц, миграция [`alembic/versions/0001_history_schema.py`](../alembic/versions/0001_history_schema.py).
Модели — [`app/storage/models.py`](../app/storage/models.py); тест
`tests/test_schema.py` сверяет с базой имена всех ограничений и индексов.

### Идентичность: естественные ключи

| Сущность | Ключ | Примечание |
| --- | --- | --- |
| Аккаунт | `history_accounts.account_id` — G-адрес | M-адрес хранится рядом в `*_muxed`, участником всегда является G-адрес |
| Актив | `history_assets.asset_id` = `native` или `CODE:ISSUER` | Колонки `asset_type`, `asset_code`, `asset_issuer` хранятся тоже; CHECK следит, что они согласованы с ключом |
| Леджер | `history_ledgers.sequence` | |
| Транзакция | `history_transactions.id` — Total Order ID | Хеши — отдельные уникальные колонки |
| Операция | `history_operations.id` — Total Order ID | |
| Эффект | `history_effects.id` — id эффекта из REST | `paging_token` хранится отдельно; CHECK: оба кодируют одну пару (операция, номер) |
| Сделка | `history_trades.id` = `<operation_id>-<trade_order>` | Не зависит от того, какая сторона base |

Horizon использует суррогатные `id` для аккаунтов и активов. Они зависят от
порядка вставки в конкретной базе и ничего не значат вне её. Когда появится
второй источник (архив), он должен отображаться в те же объекты, а не
приносить свои id. Поэтому ключи естественные, а чужие идентификаторы
хранятся как атрибуты источника и эквивалентными не считаются.

### Типы

- **Суммы** — `BIGINT` в строопах. На сети суммы — 64-битные целые, так что
  преобразование строки вида `"123.0000456"` в строопы точно; строка с числом
  знаков после точки больше семи отвергается, а не округляется.
- **Цена** — `price_n`, `price_d` (`BIGINT`), точная дробь, как её отдаёт
  Horizon. Десятичная строка цены не хранится: она выводима.
- **Время** — `TIMESTAMPTZ`, UTC, с микросекундами. У Horizon время без
  таймзоны; здесь тип выбран так, чтобы значение не зависело от настроек
  сессии.
- **Типы операций и эффектов** — `TEXT` (`type`) и `INTEGER` (`type_i`), без
  enum. Неизвестный тип сохраняется.
- **XDR** — `TEXT` с base64. `result_meta_xdr` и `fee_meta_xdr` nullable:
  NULL означает «не получено», а не «пусто».
- **`raw`** — `JSONB`, содержимое JSON ответа (не побайтовая копия HTTP-ответа).

### Избыточность, принятая сознательно

`ledger_close_time` продублирован в транзакциях, операциях, эффектах и
сделках. Время закрытия леджера неизменно, а запросы по времени и
совместимый с Horizon вывод (`created_at`) нужны везде; без этого каждый
такой запрос требовал бы соединения с `history_ledgers`.

### Согласованность идентификаторов проверяет база

Total Order ID и курсоры вычисляются из частей, и база следит, что записаны
они согласованно:

- `history_transactions`: `id = (ledger_sequence << 32) | (application_order << 12)`
- `history_operations`: `id = transaction_id + application_order`
- эффекты и сделки: `id` и `paging_token` соответствуют (`operation_id`, номер)

Ошибка загрузчика, перепутавшего леджер или номер операции, отвергается
базой, а не обнаруживается по неверной сортировке спустя месяц.

## 4. Правила записи

Реализация — [`app/storage/upsert.py`](../app/storage/upsert.py).

**Повторная запись не создаёт дублей и не ухудшает запись.** Запись ищется по
ключу под блокировкой. Если её нет — вставляется (значения должны быть
полной строкой). Если есть — заполняются только те колонки, где в базе NULL.
Колонка, у которой известное значение отличается от приходящего, — ошибка
`ContentConflict`. Это не «последняя запись выигрывает»: два источника
расходятся либо парсер ошибается, и то и другое должен увидеть человек.

**`raw` сливается по ключам.** Ключ, который есть только у одной из сторон,
добавляется; ключ, имеющийся у обеих сторон, должен иметь равное значение.
Более полный ответ дополняет неполный в любом направлении.

**Сделка, полученная с переставленной парой, — та же сделка.** Horizon
отвечает на запрос рынка в обратном порядке перестановкой base и counter.
`upsert_trade` распознаёт это по идентификатору `<operation_id>-<order>` и
согласованной перестановке всех сторонних колонок и не создаёт вторую строку.
Ориентация сохраняется у первой записи; индексы есть для обоих направлений.

**Чекпоинт пишется в той же транзакции, что и данные страницы.** Сборщик
получает страницу по HTTP вне транзакции, затем одной транзакцией пишет
родителей, записи и `set_checkpoint`. Откат отменяет и данные, и прогресс;
страница будет прочитана заново.

**Внешние ключи включены.** У Horizon их нет — он пишет большими пакетами и
не может ждать родителей. При наших объёмах (порядка тысячи аккаунтов)
стоимость FK незаметна, а фиктивная «полная» запись без родителя становится
невозможной на уровне базы.

## 5. Покрытие и политики отбора

### `tracked_*` — списки наблюдения

- `tracked_accounts`: `mode` ∈ FULL, ASSETS_ONLY, CANDIDATE, DISABLED,
  `reason`, даты. Режим не входит в ключ: аккаунт переходит из FULL в
  ASSETS_ONLY и обратно простым `UPDATE`, накопленное не удаляется.
- `tracked_assets`, `tracked_markets`: независимые списки с признаком
  `enabled`. Сделка отслеживаемого рынка собирается независимо от того, есть
  ли её участники в списке аккаунтов (проверено тестом).
- Рынок — **неупорядоченная** пара: всегда `base_asset_id < counter_asset_id`,
  поэтому пара, названная в любом порядке, — одна строка. Какая сторона
  считается base при выводе, решает запрос.

Попадание аккаунта в `history_accounts` не означает, что он отслеживается:
это реестр всех встреченных аккаунтов.

### `sync_coverage` — что именно проверено

Покрытие — утверждение о диапазоне, а не следствие наличия строк.

| Поле | Смысл |
| --- | --- |
| `subject_type`, `subject_key` | аккаунт, актив, рынок или `global` |
| `data_type` | transactions, operations, effects, trades |
| `selection_policy`, `policy_version` | политика отбора и её версия, с которой собран диапазон |
| `from_ledger`, `to_ledger` | диапазон включительно |
| `source` | откуда собрано, например `horizon:horizon.stellar.org` |
| `state` | `pending` — не проверено; `complete` — проверено, есть записи; `empty` — проверено, записей нет |
| `verified_at` | момент проверки; NULL только у `pending` (проверяется CHECK) |

Для одного набора (субъект, тип данных, политика, версия политики) диапазоны
**не пересекаются** — это ограничение `EXCLUDE` в PostgreSQL. Поэтому
проверенный набор леджеров — простое объединение диапазонов, а «пустой
проверенный» всегда отличим от «непроверенного». Разделение диапазона — это
замена его строки на части в одной транзакции.

Политика и её версия входят в ключ непересечения: один и тот же диапазон может
быть собран дважды — под ASSETS_ONLY и затем под FULL. Диапазон считается
покрытым для политики только по её собственным строкам.

## 6. Порядок сохранения: родители раньше детей

Эффекты и сделки ссылаются на операцию, операция — на транзакцию, та — на
леджер и аккаунты. База требует, чтобы родитель существовал. Порядок записи:

```
history_ledgers, history_accounts, history_assets
  → history_transactions
    → history_operations (+ участники)
      → history_effects, history_trades
```

Загрузчик, встретивший эффект или сделку без сохранённой операции, обязан
сначала:

1. найти операцию в базе по `operation_id`; транзакция — тот же id с
   обнулёнными 12 битами;
2. если её нет — догрузить `/operations/{id}` и её транзакцию
   `/transactions/{hash}`, сохранить их в указанном порядке, и только затем
   — эффект или сделку, в одной транзакции.

Если родитель недоступен (запись за границей удержания Horizon), эффект и
сделка **не сохраняются** как полноценные записи. Такой диапазон остаётся
непокрытым в `sync_coverage`. Таблица для «сирот» на этом этапе не создаётся:
если доля таких случаев окажется заметной, её добавят отдельной миграцией.

## 7. Индексы

| Индекс | Запрос, который он обслуживает |
| --- | --- |
| `history_ledgers (close_time)` | диапазон времени → диапазон леджеров; дальше все таблицы адресуются по `sequence` (PK) |
| `history_transactions (transaction_hash)` U, `(inner_transaction_hash)` U | поиск по хешу, в том числе по внутреннему хешу fee-bump |
| `history_transactions (ledger_sequence, application_order)` | транзакции леджера |
| `history_transaction_participants (account_id, transaction_id)` | история транзакций аккаунта, уже отсортированная по времени: TOID растёт хронологически |
| `history_operation_participants (account_id, operation_id)` | история операций аккаунта |
| `history_operations (source_account, type_i, id)` | операции аккаунта по источнику; с фильтром по типу (`manage_data` — `type_i = 10`) |
| `history_operations (type_i, id)`, `history_effects (type_i, operation_id, effect_order)` | «тип + идентификатор»: все операции или эффекты типа, по порядку |
| `history_effects (account_id, operation_id, effect_order)` | эффекты аккаунта по порядку |
| `history_trades (base_asset_id, counter_asset_id, ledger_close_time)` и `(counter_asset_id, base_asset_id, ledger_close_time)` | рынок + время в любой ориентации пары |
| `history_trades (operation_id, trade_order)` U | сделки операции; хронологический порядок сделок — по TOID операции, а не по текстовому `id` |
| `history_trades (base_account_id, operation_id)`, `(counter_account_id, operation_id)` | сделки аккаунта с каждой из сторон |
| `history_assets (asset_issuer)` | все активы эмитента |
| `sync_coverage (subject_type, subject_key, data_type)` | покрытие субъекта |

Чего намеренно нет: индексов по времени в транзакциях, операциях, эффектах и
сделках, кроме рыночных (время → леджер даёт `history_ledgers`); отдельного
индекса по `type` текстом (известный тип ищется по `type_i`, неизвестный —
тоже по `type_i`); партиционирования и кэширования. Horizon сам удалил
большую часть аналогичных индексов как неиспользуемые (миграция 67).

## 8. Сеть, секреты, доступ

- **Одна сеть на базу.** Таблица `network_identity` с одной строкой; миграция
  создаёт её с passphrase public network. `assert_network()` вызывается при
  проверке готовности и перед записью: база testnet с конфигурацией pubnet
  (и наоборот) не используется.
- **Секреты — только через окружение.** Пароль PostgreSQL задаётся в `.env`
  (файл в `.gitignore`); в репозитории только `.env.example` с заглушкой.
  Строка соединения в репозиторий не пишется, `alembic/env.py` берёт её из
  `MTL_HORIZON_DATABASE_URL`.
- **PostgreSQL не публикует порт.** База доступна только внутри сети
  Compose. Тесты тоже выполняются внутри этой сети (`docker compose --profile
  test run --rm tests`) на отдельной временной базе.
- **API — только localhost.** `127.0.0.1:8000` на хосте. В контейнере процесс
  слушает все интерфейсы: иначе порт не опубликовать. Вне контейнера
  значение по умолчанию — `127.0.0.1`.
- **Образ** запускается от непривилегированного пользователя; healthcheck —
  `curl`, без запуска интерпретатора.
- **Внешнего трафика нет.** В этапе 01 нет ни одного обращения к Horizon или
  Core; тесты ходят только в локальную базу.

| `sync_state`: «cursor/ledger checkpoint по источнику и потоку» | В ключ добавлен `resource_type`; курсор хранится как текст + вычисленный `cursor_ledger` | Курсор не число: его формат зависит от типа ресурса |

| — | Внешние ключи включены (у Horizon их нет) | Раздел 4 |
| — | `raw` nullable, а не NOT NULL | Будущий импорт может не иметь REST JSON |

## 10. Не сделано и открытые решения

Не реализовано намеренно (следующие этапы): клиент Horizon, collector,
backfill, бизнес-API, графики, импорт из архивов, работа с Soroban-данными
поверх сохранённого JSON.

Решения, которые нужно принять до или во время следующего этапа:

1. **Точность границы удержания.** Как именно фиксировать момент, когда
   Horizon отвечает `before_history`: по каждому ресурсу отдельно или один
   диапазон на источник.
2. **Ориентация сделок на выводе.** Хранится ориентация источника. Для
   API-совместимого вывода нужно решить, что показывать: как есть или
   переставлять под запрошенный порядок пары.
3. **`manage_data` и удаление записи.** По операции удаление неотличимо от
   пустого значения. Если понадобится различать без эффектов — разбирать
   `envelope_xdr` через SDK, с оговоркой про неизвестные типы операций.
4. **«Сироты».** Нужна ли таблица для эффектов и сделок без доступного
   родителя — решается по фактической доле таких случаев.
5. **Полнота в пределах удержания.** По REST нельзя увидеть внутренние «ямы»
   Horizon. Возможно, придётся сверять счётчики записей по леджерам.
6. **Зависимость от `httpx` в тестовом клиенте.** Starlette объявил
   `TestClient` поверх `httpx` устаревшим (предлагает `httpx2`). Пока это
   предупреждение; при обновлении FastAPI тесты `test_api.py` придётся
   перевести.
