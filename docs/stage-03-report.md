## 4. Команды запуска

Полная инструкция — `docs/owner-runbook.md`; кратко:

```bash
docker compose run --rm api alembic upgrade head              # 0003
alias lc='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.collector'
lc check                                   # что источник делает при чтении вперёд: ~10 запросов, ничего не пишет
lc once  --start-ledger L                 # один цикл; L — где закончился backfill (иначе — с последнего леджера)
lc status                                  # граница и отставание каждого потока; сервера не спрашивает
docker compose --profile collector up -d collector           # регулярно, раз в MTL_HORIZON_COLLECTOR_INTERVAL секунд (900)
```

Настройки: `MTL_HORIZON_COLLECTOR_INTERVAL` (900), `MTL_HORIZON_COLLECTOR_MAX_REQUESTS`
(2000), `MTL_HORIZON_COLLECTOR_MAX_SECONDS` (0,9 интервала). Служба без
портов, `restart: unless-stopped`, `stop_grace_period` 90 с, healthcheck
отключён (в образе он спрашивает API, который служба не запускает).
Коды возврата цикла: `0` — все потоки дочитаны; `1` — поток сбойнул; `2` —
остановлен лимитом или сигналом.

## 6. Эксперимент по числу запросов

`scripts/replay_window.py` отдаёт его обратно под правилами постраничного
чтения Horizon. Живых запросов нет: счётчик считает каждый запрос к replay.

прогона этапа 02 — разница ровно в те 17 root-запросов, которые backfill
теперь не делает; строки и слепок семи таблиц совпали с базой до записи.

меньше запросов с тем же результатом. Для «всё, что произошло в
транзакции» — нет; это либо `full`, либо дочитка контекста позже, которой
пока нет. Коллектор для рынка уже читает только родителей.

## 7. Сверка с агрегациями

`/trade_aggregations` по часам за 7 дней, обе ориентации: 167 корзин, в 73
есть сделки. **Во всех 73 совпали число сделок, оба объёма, avg, high, low,
open, close — в обеих ориентациях.**

Что при этом выяснилось о формулах сервера (`trade_aggregation.go` на
`4e13b1be`): `avg` — отношение объёмов, напечатанное семью знаками, точного
`avg_r` нет; high, low, open, close берутся из **цен сделок** (цен офферов),
а не из отношений сумм — у сделок через пул с комиссией это разные числа.
`verify --aggregations` теперь считает так же (`--bucket-hours` задаёт
длину корзины). Совпадение ID и сумм — не совпадение всех полей; здесь
сверялись поля.

## 8. Объём PostgreSQL и копии

Байты на строку с индексами и TOAST, по пилотным базам:

| Таблица | байт на строку |
| --- | --- |
| `history_effects` | 1 370–1 490 |
| `history_operations` | 1 700–1 840 |
| `history_trades` | 2 400 |
| `history_transaction_participants`, `history_operation_participants` | 390–410 |
| `history_transactions` | 7 600–12 100 (XDR в TOAST) |

Считать надо от операций и эффектов, а не от транзакций. В базе пилота
(384 МБ) медиана — **70 операций на транзакцию** (p90 — 100), в окне 7 дней —
5 (59 КБ на транзакцию против 269 КБ по таблицам с индексами). Крупных-одиночек нет: 14 самых
больших транзакций держат 1 400 из 56 253 операций. Поэтому «383 МБ на
1 383 транзакций» нельзя умножать на число транзакций: объём зависит от
того, массовые это транзакции или нет, и разброс — десятикратный.

Оценка для выборки за год (по числу записей из оценки этапа 02: 9 657
транзакций, 10 286 операций, 16 707 эффектов, 10 236 сделок рынка):

| | Если транзакции как в окне 7 дней | Если как в истории пилота |
| --- | --- | --- |
| `full` | около 0,5 ГБ | около 2,7 ГБ |
| `parents` | около 0,3 ГБ | около 0,3 ГБ |

`parents` от формы транзакций почти не зависит: контекст он не носит.

Это прикидка по байтам на строку, а не измерение.

**Копии.** `pg_dump -Fc` базы в 26 МБ — 1,15 МБ; восстановление в черновую
базу `pg_restore --no-owner`: слепки окна равны по всем семи таблицам,
служебные таблицы, ограничения (72) и индексы (36) на месте. Рабочие базы
не трогались; команды — в инструкции, раздел 8.

## 9. Notifier

Оценка по коду `operations-notifier` (`4da170e`, в рабочем дереве есть
незакоммиченные правки владельца; читал как есть, ничего не менял). Что он делает:
читает **все** транзакции сети из Horizon (страницами и живым потоком),
разбирает envelope SDK, сверяет с подписками (аккаунт, актив, memo, тип
операции) и кладёт уведомление каждому подписчику в очередь (MongoDB или
память) — HTTP POST на его URL.

Уведомление — **одна операция**: её поля в собственной схеме Notifier (не
JSON Horizon; типы активов числовые), сделка оффера — без ID и порядка,
сделки рынка целиком не видны, эффектов нет, леджера нет (только
`created_at`), у транзакции — хеш, комиссии, источник, `envelope_xdr`,
`result_xdr`. Доставка не гарантирована от потерь: после 100 неудач или
7 дней уведомление теряется. Хранит он только курсор ingestion и очереди.

Может ли он заменить чтение новых леджеров из Horizon — нет, и не должен:

| Что нужно для полноты | Из Horizon REST | Из Notifier |
| --- | --- | --- |
| транзакции, операции, эффекты, сделки аккаунта — в JSON источника | есть | нет: своя схема, только совпавшая операция |
| участие, как его утверждает Horizon (запись вернулась в потоке аккаунта) | есть | нет |
| сделки рынка с ID и порядком | есть | нет |
| родители записи | есть | только выжимка |
| `result_meta_xdr` | нет (публичный не отдаёт) | нет |
| сигнал «в леджере N что-то было для аккаунта X» | — | **есть** |

Где Notifier полезен: как **сигнал**, где что-то произошло, чтобы не
опрашивать впустую (сейчас пустой цикл по 17 потокам — 18 запросов). Для
этого ему нужна наша принимающая сторона (HTTP-endpoint — публичное API,
вне этапа) и гарантия, что после его простоя мы всё равно дочитаем с
границы — что коллектор и делает. Вторым источником записей его делать
не нужно: записей в нём нет.

## 10. Инциденты и мои ошибки

**Runaway старым образом.** В 09:54 UTC, проверяя новые правила
безопасности, я запустил `docker compose run api python -m app.backfill run`
без аргументов, **не пересобрав образ**: в контейнере был код этапа 02, где
`run` без границ читает всю историю сервера. Три минуты (до `SIGTERM` в
09:57:41) он читал публичный Horizon — не более 186 запросов — и писал в
базу разработки `mtl_horizon`: 2 транзакции, 98 операций, 238 эффектов и
строки покрытия на всё окно retention. Пересобрал, убедился, что все
небезопасные сочетания отклоняются до первого запроса; остатки в базе
разработки не удалял — это решение владельца. Пересчитывать бюджет не
стал: 278 из 300 — с ними.

**Ошибки в моих локальных сценариях.** Первый подсчёт агрегаций сравнивал
все сделки базы, а не пары, и не переводил stroops в единицы актива — 1 запрос впустую.
Второй обнаружил настоящее расхождение: крайние цены сервера — из цен
сделок, не из отношений сумм; исправлено в `verify --aggregations`.

**Найдено тестами и исправлено до живого.**

- Клиент отказывался после четырёх одинаковых ответов подряд, а пустой
  цикл коллектора спрашивает только root. На четвёртом пустом цикле
  коллектор падал бы с удваивающейся паузой. Защита от зацикливания теперь
  действует в пределах одной последовательности чтения.
- Поддельный сервер для тестов включал запись самого курсора при чтении
  вперёд (для транзакций и операций): клиент это отверг, тесты вскрыли.
- Backfill спрашивал корень источника на закрытии каждого потока: 18
  запросов на 17 страниц. Теперь один раз за запуск.
- Строка уровня журнала `httpx` была мёртвым кодом после `return` — запросы
  не гасились на уровне INFO. Исправлено: на DEBUG видны все запросы.

**Мелочи, ни на что не повлиявшие:** пара раз я записал в тестовый файл
мусор вместо теста и тут же переписал; в сценарий replay вставил
заглушку — переписал целиком.

## 11. Ограничения и открытые вопросы

1. **Общий ограничитель темпа нет.** Коллектор и backfill исключают друг
   друга; блокировки действуют в пределах одной базы PostgreSQL: две
   установки с разными базами против одного Horizon не согласованы.
2. **Тысяча аккаунтов не доказана.** Пустой цикл — 18 запросов на 17
   потоков; у тысячи аккаунтов это тысячи запросов каждые 15 минут. Нужен
   свой Horizon, или сигнал «где что-то было», или редкий цикл для тихих.
3. **Полная история выборки не загружена** — как и после этапа 02.
4. **Сделки самых активных аккаунтов** — 503 на публичном Horizon.
5. **`parents` как основной режим** — решение за владельцем: в 2,7 раза
   дешевле, но без контекста транзакций. Дочитки контекста позже нет.
6. **`result_meta_xdr`** недоступен; участники по изменениям записей не
   восстанавливаются.
7. **Полнота — относительно ответов источника.** Внутренние «ямы» Horizon
   через REST не видны.
8. **Живьём не проверено:** остановка `SIGTERM` ровно на потоке с
   чекпоинтом (в тестах есть), параллельность больше 1, окно больше трёх
   часов в `parents` (доведено replay), muxed-аккаунты и Soroban.
9. **Независимое ревью кода** этапов 01–03 не проводилось.
