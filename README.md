# MTL Horizon

Read-only индексатор истории Stellar для Montelibero: бессрочное хранение
истории выбранных аккаунтов и сделок выбранных активов и рынков. Не Stellar
Core и не форк Horizon.

**Статус: этап 06** — каркас, схема исторической базы, загрузка окна
леджеров, **событийный сбор**, **наблюдение за списком** и **админка**:
владелец управляет установкой из браузера (`/admin`) — списки аккаунтов,
активов и рынков, discovery, подписки Operations Notifier, импорт истории,
активность; Historical API — публичный архив, отдаёт собранную историю по
путям Horizon всем, кто до него достаётся; что занимает время, идёт
долговечными задачами с видимым состоянием.
Все обращения к Horizon идут через отказоустойчивый пул серверов с общим
темпом; живые запросы можно жёстко ограничить на транспортном уровне.
Регулярный опрос (`python -m app.collector`) остался для восстановления и
контрольных сверок. Полная годовая история даже пробной выборки не
загружена; полнота событий сети и массовый импорт не объявляются
доказанными. **Живая интеграция с Notifier не проверена** — всё проверено на
встроенных Horizon и Notifier; смоук-тест приготовлен и ждёт разрешения
владельца. До его прохождения установка готова к пилотному запуску, не к
production.

## Стек

Python 3.14, FastAPI, SQLAlchemy 2, Alembic, psycopg 3, HTTPX,
stellar-sdk 17, PostgreSQL 17. Версии зафиксированы в `uv.lock`.

## Развёртывание на сервере

На сервере нужен только Docker с Docker Compose v2 и один файл —
`compose.yaml`: образ приложения приходит из GitHub Packages
(`ghcr.io/montelibero/mtlhorizon:main`), всё остальное вписано в него же.
Ни сборки на сервере, ни файла переменных: каждое значение стоит в файле
как есть.

```bash
mkdir mtl-horizon && cd mtl-horizon
curl -fsSLO https://raw.githubusercontent.com/Montelibero/MTLHorizon/main/compose.yaml
docker login ghcr.io            # только если пакет приватный: токен с read:packages
docker compose pull
```

Откройте `compose.yaml` и впишите своё. Не закомментировано то, что каждая
установка задаёт под себя: пароль базы (в двух местах, одинаковый —
`POSTGRES_PASSWORD` у `db` и `MTL_HORIZON_DATABASE_URL`), ключи Notifier,
адрес и токен его API, адрес вебхука, секрет админки, адрес установки.
Исторический API в файле уже открыт — это публичный архив. Закомментированы
настройки со значением по
умолчанию — снимите `#` с тех, что меняете. В репозитории лежит копия с
заглушками; копия на сервере хранит настоящие секреты и в репозиторий не
возвращается.

```bash
docker compose up -d db                            # 1. база
docker compose run --rm api alembic upgrade head   # 2. миграции — до всего остального
docker compose up -d                               # 3. db, api (с webhook), worker и history

curl -s http://127.0.0.1:8000/ready                # 200
```

Обновление: возьмите свежий `compose.yaml`, перенесите в него свои значения,
затем `docker compose pull`, `docker compose stop`, миграции, `docker compose
up -d`. Подробности и всё, что дальше, — в
[`docs/owner-runbook.md`](docs/owner-runbook.md), раздел 2.

## Локальное окружение

Нужны Docker и Docker Compose v2. На машине разработки Compose читает
`compose.dev.yaml`: образы собираются из исходников, набор включает сервис
тестов, настройки читаются из `.env` (он не попадает в git). Файл выбирает
строка `COMPOSE_FILE=compose.dev.yaml` в `.env` — она есть в `.env.example`.
Все команды `docker compose` ниже рассчитаны на это; на сервере те же
команды работают с `compose.yaml`.

```bash
cp .env.example .env          # задайте POSTGRES_PASSWORD, MTL_HORIZON_NOTIFIER_KEYS и MTL_HORIZON_ADMIN_SECRET
docker compose build
docker compose up -d db                            # 1. база
docker compose run --rm api alembic upgrade head   # 2. миграции — до всего остального
docker compose up -d                               # 3. db, api (с webhook), worker и history

curl -s http://127.0.0.1:8000/health     # 200
curl -s http://127.0.0.1:8000/ready      # 200
```

Порядок обязателен: на базе без миграций API жив, но не готов (`/ready`
— 503, `migrations: not applied`), а `worker` и `history` не стартуют —
проверяют схему и выходят, называя причину. Если служба вышла с кодом 1
сразу после старта, сначала примените миграции.

| Адрес | Назначение |
| --- | --- |
| `GET /health` | живость процесса; базу не трогает |
| `GET /ready` | база отвечает, схема на голове цепочки миграций, база принадлежит настроенной сети; иначе 503 с именем сбоя |
| `POST /webhooks/notifier` | то, что присылает Operations Notifier; только с подписью известного ключа. Доставка сохраняется до ответа; Horizon здесь не спрашивается |

PostgreSQL не публикует порт: база доступна только внутри сети Compose. API
публикуется только на `127.0.0.1:8000`; чтобы Notifier доставал до
`/webhooks/notifier`, поставьте перед API свой HTTPS-прокси.

### Миграции

Цепочка из двенадцати миграций. `0001` — историческая схема целиком (таблица
`network_identity`, 9 таблиц `history_*`, 3 списка наблюдения,
`sync_coverage`, `sync_state`). `0002` — то, что понадобилось для загрузки
истории: признак загруженного контекста у транзакции, направление у
чекпоинта, состояние `unverifiable` у покрытия. `0003` — состояние
регулярного сбора: что коллектор видел у источника и где стоит каждый поток.
`0004` — независимые правила наблюдения: у аккаунта флаг `enabled` вместо
режима. `0005` — пул: кто прочитал диапазон покрытия (`sync_coverage.served_by`),
общий темп (`http_pace`) и состояние серверов (`horizon_node_state`).
`0006` — события: журнал доставок (`notifier_event`) и задания
(`processing_job`). `0007` — логический источник: у чекпоинтов и покрытия
`horizon:pool` вместо имени первого сервера, слияние строк, которые стали
одним ключом, и запись о переименовании (`source_identity`). `0008` —
discovery: `tracked_assets.discover`, происхождение и границы у аккаунтов
(`origin`, `discovered_by`, `watch_since_ledger`, `boundary_due`),
`discovery_run`, `service_state`. `0009` — очередь исторического импорта
(`history_job`). `0010` — подписки (`watch_subscription`). `0011` —
задачи (`service_job`) и дверь админки (`admin_session`,
`admin_login_throttle`). `0012` — счётчики и приоритет заданий истории
(`inserted`, `repeated`, `failed_slices`, `time_spent_ms`,
`last_progress_at`, `priority`). Все миграции только добавляют; прежние
не редактировались.

```bash
docker compose run --rm api alembic upgrade head    # применить
docker compose run --rm api alembic current         # 0012 (head)
docker compose run --rm api alembic check           # расхождения моделей со схемой
docker compose run --rm api alembic history
docker compose run --rm api alembic downgrade base  # удалить все таблицы проекта
```

Миграции запускаются отдельной командой, а не при старте служб: так момент
изменения схемы всегда явный, и ни worker, ни `history` не начинают
работать на неприменённой схеме. Строка соединения берётся из переменной
`MTL_HORIZON_DATABASE_URL`; в `alembic.ini` её нет.

## Загрузка истории (этап 02)

История читается из Horizon **назад**, от нового к старому, отдельными
потоками: у каждого включённого аккаунта четыре потока (транзакции,
операции, эффекты, сделки), у каждого включённого рынка — сделки пары.
Выключенные аккаунты не читаются. Поток можно остановить в любой момент и
продолжить.

Команды выполняются в контейнере `api`; файлы (список наблюдения, отчёты)
попадают в него через примонтированный каталог `local/`:

```bash
mkdir -p local
alias bf='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.backfill'
```

### Список наблюдения

Формат — [`local-tracking.example.yaml`](local-tracking.example.yaml). Скопируйте
его в `local/tracking.yaml` (каталог `local/` не попадает в git) и заполните.

```bash
bf import-config --file local/tracking.yaml --dry-run   # проверить и показать, ничего не записав
bf import-config --file local/tracking.yaml
bf import-config --file local/tracking.yaml --apply-changes   # сменить флаг записей, у которых он отличается
```

Три списка независимы, и объединяются они по **ИЛИ**: событие приходит в
базу, если совпал хотя бы один включённый аккаунт, актив или рынок. Флаг
`enabled` у актива и рынка — свой; отключение аккаунта не отключает активы и
рынки и не удаляет собранное. У актива есть отдельный флаг `discover` —
искать ли держателей его trustline (этап 05); включённый заново или
добавленный аккаунт получает импорт всей истории и подписку — их сделает
worker.

Ошибки в файле перечисляются все сразу, и ничего не импортируется. Повторный
импорт того же файла ничего не меняет. Записи, которых в новом файле нет, не
удаляются. Флаг записи меняется только с `--apply-changes`. Файл этапа 03 с
полем `mode` читается явно: `FULL` — как `enabled: true`, каждый из
остальных режимов — как `enabled: false`, с пометкой в выводе; прежде
неактивный аккаунт молча не включается.

### Один взгляд на сервер

```bash
bf probe --output local/reports/probe.json
```

Тридцать с небольшим read-only запросов: версия сервера и его сеть, границы
истории, обе ориентации рынка, цепочка сделка → операция → транзакция →
леджер, поведение курсоров. Никакой записи в базу.

### Оценка и загрузка окна

```bash
bf estimate --from-ledger L1 --to-ledger L0     # сколько страниц и записей в окне, сколько запросов понадобится
bf run       --from-ledger L1 --to-ledger L0 --max-requests 2000 --report local/reports/run.json
bf status
```

Леджеры считаются включительно. `run` и `reimport` никогда не выбирают окно
сами: нужно назвать обе границы — или явно попросить всю доступную историю
флагом `--full-retention` (от самого старого леджера, который хранит хоть
один сервер пула, до самого нового на момент старта) — и в любом случае
задать бюджет:
`--max-requests`, `--max-pages` или `--max-seconds`. Без этого команда
откажется, не сделав ни одного запроса.

`run` читает только то, что ещё не проверено: повторный запуск готового окна
не делает ни одного запроса к потокам. Остановить можно лимитами или
сигналом (`Ctrl-C`, `SIGTERM`); сохранённое остаётся, следующий запуск
продолжает с чекпоинта.

```bash
bf run --max-pages 50                                       # остановиться, достигнув любого из лимитов
bf run --subject GACKTN5DA --from-ledger L1 --to-ledger L0 --max-seconds 600   # только потоки, в имени которых есть эта строка
bf reimport --from-ledger L1 --to-ledger L0 --max-requests 2000              # забыть покрытие окна и прочитать заново
bf run --full-retention --max-requests 5000 --max-seconds 3000               # вся история, которую сервер хранит
bf run --from-ledger L1 --to-ledger L0 --context parents --max-requests 2000 # только история аккаунтов и рынка, без контекста транзакций
```

`--context parents` читает то же самое по потокам аккаунтов и рынка, но не
догружает контекст каждой транзакции — только родителей, без которых запись
не сохраняется (операцию и транзакцию сделки или эффекта). Это 37 % запросов
полного режима на окне выборки; контекст транзакций при этом остаётся
незагруженным, и `context_loaded` у них пуст. По умолчанию — `full`.

Коды возврата `run`: `0` — окно проверено; `1` — поток закончился ошибкой;
`2` — остановлен лимитом или сигналом; `3` — закончено, но часть окна
вышла из истории сервера и помечена `unverifiable`.

Темп по умолчанию — 1 запрос в секунду, и он один на всю установку: на все
процессы (worker, backfill, collector, проверки) и на все серверы пула.
Публичный Horizon ограничивает запросы по IP; ответ 429 несёт заголовки
`X-RateLimit-*`, и ждать столько, сколько сервер просит, будут все процессы.
Адреса серверов и темп задаются только через окружение — в `.env` на машине
разработки, в `compose.yaml` на сервере (`MTL_HORIZON_URLS`,
`MTL_HORIZON_REQUESTS_PER_SECOND`); флагов командной строки для них нет.
Журнал команды можно дублировать в файл — общие опции ставятся до
подкоманды:

```bash
bf --log-level INFO --log-file local/logs/run.log run --from-ledger L1 --to-ledger L0
```

### Проверка загруженного

```bash
bf verify      --from-ledger L1 --to-ledger L0                   # ID записей в базе против страниц сервера, поток за потоком
bf verify      --from-ledger L1 --to-ledger L0 --aggregations     # и рынок против /trade_aggregations: счёт, объёмы, avg, high, low, open, close
bf verify      --from-ledger L1 --to-ledger L0 --aggregations --bucket-hours 1   # корзины по часам вместо суток
bf fingerprint --from-ledger L1 --to-ledger L0                   # число строк и слепок каждой таблицы в окне
```

`fingerprint` двух баз совпадает тогда, когда в них одни и те же строки:
так сравнивают непрерывный запуск с остановленным и возобновлённым.

### Что попадает в базу

- Родителей догружаем всегда: сделка или эффект не хранится без своей
  операции, транзакции и леджера. Если родителя нет (404) — поток
  останавливается с ошибкой, страница не записывается, курсор не движется.
- Контекст транзакции (все её операции, эффекты, сделки) качается один раз;
  при повторной встрече берётся из базы.
- `result_meta_xdr` публичный Horizon не отдаёт — в базе будет `NULL`.
- Что вышло из истории сервера (окно ниже `history_elder_ledger`, ответ 410),
  помечается `unverifiable`, а не `complete`: код возврата `3` у `run`.
- У очень активных аккаунтов публичный Horizon на `/accounts/{id}/trades`
  отвечает 503. Такой поток останавливается с ошибкой (код возврата `1`) и
  остаётся непроверенным; остальные потоки загружаются.
- Участники: для наблюдаемого аккаунта — те, которых назвал сам Horizon
  (он вернул запись в потоке аккаунта); для остальных — то, что выводится из
  тела операции и источников транзакции. Участники по изменениям записей
  (это видно только из meta) не восстанавливаются.

Подробности — в [`docs/architecture.md`](docs/architecture.md).

### Тесты

Тестам нужна настоящая PostgreSQL. Они создают на указанном сервере свою
базу, применяют к ней миграции, прогоняют всё и удаляют базу; база
приложения не затрагивается. Сеть в тестах не используется: Horizon
заменён встроенным фейком (`tests/fake_horizon.py`), Notifier — фейком,
который подписывает как он (`tests/fake_notifier.py`), и его API — фейком,
написанным по коду сервиса (`tests/fake_notifier_api.py`); сервер, для
которого тест не предоставил фейк, отказывает в соединении
(`no_real_servers` в `tests/conftest.py`), а любой клиент — клиент API
Notifier включительно — не может открыть соединение с публичным адресом:
блокировка стоит на уровне сокетов (`no_outer_network`).

```bash
docker compose --profile test run --rm tests
```

То же с хоста (нужен [uv](https://docs.astral.sh/uv/) и доступ к базе —
порт у неё закрыт, поэтому одноразовый проброс только на localhost):

```bash
docker run -d --rm --name mtl-horizon-db-tunnel --network mtl-horizon_default \
  -p 127.0.0.1:55432:5432 alpine/socat \
  tcp-listen:5432,fork,reuseaddr tcp:db:5432

export MTL_HORIZON_TEST_DATABASE_URL="postgresql+psycopg://mtl_horizon:<пароль из .env>@127.0.0.1:55432/ignored"
uv sync --frozen
uv run --frozen pytest
docker rm -f mtl-horizon-db-tunnel
```

### Сборка в CI

`.github/workflows/ci.yml` (GitHub Actions) на каждый пуш в любую ветку, на
каждый pull request и по кнопке Run workflow собирает из чистого чек-аута
оба образа — приложения и тестов, — проверяет файлы Compose (`compose.yaml` и
`compose.dev.yaml`; в `compose.yaml` не должно быть ни `$`, ни слова
`build`, ни упоминания `.env`), поднимает API в собранном образе и ждёт,
пока его `HEALTHCHECK` скажет `healthy`, и собирает (не запускает) набор
тестов в тестовом образе. Тесты CI не гоняет: им нужна настоящая
PostgreSQL, команда выше.

Для `main` образ приложения после всех проверок выкладывается в GitHub
Packages — токеном самого воркфлоу, отдельных секретов заводить не нужно:

- `ghcr.io/montelibero/mtlhorizon:<хеш коммита>` — конкретный коммит;
- `ghcr.io/montelibero/mtlhorizon:main` — последняя сборка `main`.

```bash
docker pull ghcr.io/montelibero/mtlhorizon:main
```

Ветки и pull request только собираются и проверяются, в регистр не уходят.

```bash
docker compose down        # остановить; данные остаются в volume mtl-horizon_pgdata
docker compose up -d       # поднять обратно; схема и данные на месте
docker compose down -v     # УДАЛИТЬ базу вместе с данными
docker compose logs -f api
```

## Событийный сбор (этап 04)

Штатный способ, которым приходит новая история.
[Operations Notifier](https://github.com/Montelibero/operations-notifier) —
независимый сервис — подписан на аккаунты, активы и рынки и на каждую совпавшую
операцию присылает подписанный webhook. MTL Horizon сохраняет доставку,
ставит транзакцию в очередь, и worker приносит её **целиком**: транзакцию,
операции, эффекты и, если они были, сделки. Ни один аккаунт не опрашивается:
нет уведомления — нет запросов к Horizon.

- **Webhook** `POST /webhooks/notifier`. Тело проверяется по подписи ed25519
  (`X-Request-ED25519-Signature`) по ключам `MTL_HORIZON_NOTIFIER_KEYS` до
  того, как из него читается хоть что-то; без ключей endpoint ничего не
  принимает. Доставка сохраняется — и ставится задание — одной транзакцией
  базы, и только после commit отвечается `2xx`. Horizon внутри webhook не
  спрашивается. Повторная доставка (ответ потерян) узнаётся и ничего не меняет.
- **Журнал отдельно от заданий.** `notifier_event` хранит каждую доставку
  как пришла: тело, что из него прочитано, какое правило совпало, что из неё
  вышло. `processing_job` — одно задание на транзакцию, сколько бы
  уведомлений о ней ни пришло (другая операция, другая подписка, повтор).
  Ничего из журнала не удаляется.
- **Правила** — три независимых списка, объединённых по ИЛИ. Не совпало ни
  одно включённое правило, и это можно сказать наверняка — доставка
  сохраняется без задания (`unmatched`), с диагнозом. Сказать нельзя — тип
  операции неизвестен читателю, поле не читается — транзакция приносится всё
  равно (`queued`, с диагнозом): Notifier совпал, иначе бы доставки не было.
- **Worker** (`python -m app.worker run`) берёт задание в аренду и приносит
  транзакцию по частям; каждая часть — короткая транзакция базы (открытой
  транзакции во время HTTP нет), последняя — вместе с пометкой «готово».
  Упавший воркер задания не теряет: аренда истекает, задание возвращается в
  очередь. Неудача — повтор с растущей паузой, до 8 попыток; затем `partial`
  (что-то сохранено) или `dead` (ничего) — оба видны в `status` и ждут
  `retry`. Уже сохранённое заново не запрашивается.
- **Пул Horizon.** `MTL_HORIZON_URLS` — один или несколько серверов, первый
  основной. Пока первый отвечает, спрашивается он; перестал — спрашивается
  следующий по кругу, а отдохнувший (`MTL_HORIZON_FAILOVER_COOLDOWN` секунд,
  с удвоением за каждую следующую неудачу) — снова. Сервер чужой сети не
  спрашивается никогда; отстающий — не спрашивается о том, до чего он не
  дошёл; с короткой историей — о том, что ниже её (спрашивается тот, у кого
  она есть). Ошибка одного запроса (503 при живом root) — не сбой сервера:
  сервер остаётся, запрос повторяется на следующем. 429 ждут все процессы,
  и другой сервер вместо не спрашивается. Всё, что читает Horizon — worker,
  backfill, collector, probe, verify, проверки пула, очередь истории и
  discovery, — идёт через этот пул.

```bash
alias wk='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.worker'
alias pl='docker compose run --rm api python -m app.pool'

wk status          # очередь, журнал и последний леджер среди уведомлений; серверов не спрашивает
wk events          # последние доставки и что из них вышло, с диагнозом
wk retry           # задания, которые сдались, — обратно в очередь
wk retry --id 17   # одно задание
pl check           # каждый сервер отдельно: сеть, версия, latest/elder, отставание, время ответа, rate-limit заголовки
pl status          # то, что сохранено о серверах; серверов не спрашивает
```

`worker status` показывает наибольший леджер среди уведомлений — и прямо
говорит, что это **не фронтир**: из него не следует, что все леджеры ниже
или все транзакции в них были увидены. Успешная обработка уведомлений не
доказывает полноту: чего Notifier не прислал, того здесь нет. Гарантий
доставки без потерь у Notifier нет (повторы с растущей паузой, через неделю
или сто неудач доставка бросается). Восстановление — очередь истории (этап
05) для известных промежутков, backfill и collector для остального.

## Наблюдение: discovery, подписки и импорт истории (этап 05)

Аккаунт попадает в список тремя путями — файлом, командой, discovery — и
дальше живёт одной жизнью: граница начала → импорт всей доступной истории →
подписка в Notifier, подтверждённая чтением → верхняя граница. Отключённый
аккаунт не теряет историю; включённый снова дочитывает время выключения.
Подробности — в [`docs/architecture.md`](docs/architecture.md), разделы 25–29.

- **Discovery** (`python -m app.discovery`). Актив помечается отдельно от
  включённого наблюдения (`discover: true` в файле или `discovery on
  CODE:ISSUER`). Проход читает `/accounts?asset=…` через пул страницами по
  адресу: считается trustline, а не баланс. Новый адрес добавляется
  включённым, с причиной и источником; уже наблюдаемый не меняется,
  отключённый вручную не включается, эмитент не добавляется. Проход — не
  снимок: о каждой странице хранится, кто ответил и когда, а недошедший до
  конца помечен `incomplete` и продолжается с того же места. Между проходами
  открытия trustline видны по эффекту `trustline_created` успешной
  транзакции, которую принёс worker. Расписание по умолчанию выключено.
- **Подписки** (`python -m app.subscriptions`). Желаемое состояние — из
  списков наблюдения: включённые аккаунты, включённые и discovery-активы,
  одна подписка на рынок. Сверка сначала читает список у Notifier и только
  потом создаёт; активной подписка считается после того, как найдёт себя в
  этом списке. Чужие подписки не трогаются; сделанные вручную принимаются
  командой `adopt` и установкой не удаляются. Без
  `MTL_HORIZON_NOTIFIER_API_URL` ничего не регистрируется.
- **Очередь истории** (`python -m app.history`, служба `history`). Задание —
  вся доступная история аккаунта или сделки рынка до верхней границы;
  работает срезами над теми же покрытием и чекпоинтами, что и backfill, и
  справедливо: каждый субъект получает срез, прежде чем кто-то получит
  второй. Переживает рестарт — прогресс в покрытии. Ниже истории пула —
  `unverifiable`, а не «история начинается здесь». События имеют приоритет.

```bash
alias ds='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.discovery'
alias sb='docker compose run --rm api python -m app.subscriptions'
alias wa='docker compose run --rm api python -m app.watch'
alias hi='docker compose run --rm api python -m app.history'

ds on EURMTL:GA… --reason "держатели евромарки"   # или discover: true в файле списка
ds run --dry-run --max-requests 5        # что нашлось бы на первых страницах; ничего не меняет
ds run                                   # пройти и добавить новых; один проход — до 1000 запросов
ds run --resume                          # продолжить недошедший до конца проход
ds status                                # активы, последние проходы, происхождение аккаунтов

sb status                                # что хотят списки, что зарегистрировано, что не вышло
sb reconcile --dry-run                   # что сделал бы проход: ничего не создаёт и не пишет
sb reconcile                             # один проход: создать, подтвердить, снять лишнее
sb adopt --kind account --key G… --id <id у Notifier>   # подписку, сделанную вручную, — сюда
sb release --id <строка>                 # забыть принятую вручную; у Notifier она остаётся

wa add-account G… --reason "…"           # вручную: граница, импорт и подписка — той же жизнью
wa disable-account G…                    # импорт на паузу, подписка уходит, история остаётся
wa enable-account G…                     # снова: время выключения будет дочитано
wa status                                # где каждый аккаунт в своей жизни; серверов не спрашивает
wa run                                   # один проход того, что worker делает в тишине

hi status                                # очередь: что ждёт, что не покрыто, что не гарантируется
hi pause --account G… --because "…"      # hi resume --account G… ; hi retry [--id N]
hi enqueue --market native EURMTL:GA…    # сделки пары — в очередь
```

Порядок держит фоновый поток worker: каждые `MTL_HORIZON_PROVISION_INTERVAL`
секунд он делает проход — как `wa run`, события ждут или нет, — и не
спрашивает ни Horizon, ни Notifier, когда всё в шаге.

Чего здесь **не обещается**: автоматическая регистрация подписок проверена
на встроенном Notifier, а не на настоящем; подписка на актив — не полнота
истории актива; discovery находит держателя, только если он попал в проход
или линия открылась, когда транзакция уже могла попасть в базу.

## Админка, исторический API и задачи (этап 06)

**Админка** — `http://127.0.0.1:8000/admin` (за HTTPS-прокси, если работаете
не с самого сервера). Открывается секретом из `MTL_HORIZON_ADMIN_SECRET`;
без него закрыта для всех. Сессия — в cookie (`HttpOnly`, `SameSite=Strict`,
`Secure` при заданном `MTL_HORIZON_PUBLIC_ORIGIN`, только для `/admin`), в
базе — её хеш; у каждой изменяющей формы — свой токен; пять неверных входов
подряд блокируют адрес. Открытие страницы ничего не спрашивает у Horizon и
Notifier. Подробности — в [инструкции владельцу](docs/owner-runbook.md).

| Страница | Что там |
| --- | --- |
| Дашборд | службы по heartbeat: работает / пауза / «не слышно»; очереди, подписки, discovery, размер базы |
| Аккаунты, активы, рынки | списки, флаги, добавление; для актива — dry run и проход discovery с бюджетом |
| Discovery, импорт истории | проходы и их состояние; что прочитано по аккаунтам и рынкам порознь, почему что-то ждёт; пауза, приоритет, расширение окна, сверка |
| Активность, график | операции за период по времени леджера; цена и объём пары из архива |
| Notifier, Horizon, задачи | желаемое против подтверждённого, сверка по кнопке; состояние пула и его проверка; задачи и их остановка |

**Задачи.** Что занимает время — проход discovery, проверка пула, сверка или
перечитывание окна, сверка с Notifier, — ставится в очередь (`service_job`)
и выполняется фоновым потоком воркера; запрос только ставит задачу. У
каждой — аренда, предел запросов к Horizon, отмена между запросами; двух
задач одного вида на один предмет одновременно не бывает.

**Исторический API** — пути Horizon (`/accounts/{id}/transactions`,
`/operations/{id}`, `/trades`, `/trade_aggregations`, `/v1/coverage`…),
читаемые только из локального архива, по умолчанию открытые всем
(`MTL_HORIZON_API_ACCESS: open`; режим `token` с токенами
`MTL_HORIZON_API_TOKENS` закрывает чтение). Пустой список означает «в этом архиве ничего
нет», а не «в сети ничего не было». Перечень маршрутов и отличия от
upstream — в [`docs/history-api.md`](docs/history-api.md).

**Живые запросы** можно жёстко ограничить: `MTL_HORIZON_LIVE_BUDGET=N` — не
больше N HTTP-попыток за прогон на все процессы вместе, счёт до отправки на
транспортном уровне, общий и переживает рестарт. **Смоук-тест живого
Notifier** — `python -m app.smoke`: одна тестовая подписка, одна доставка,
удаление только её; запускать только с разрешения владельца.

## Коллектор: восстановление и контрольные сверки (этап 03)

`python -m app.collector` читает новые леджи **вперёд**: цикл спрашивает
сервер о последнем леджере H и доводит каждый поток до H. Рынок читается
первым; его сделки сохраняются с родителями (операция, транзакция), без
контекста. Аккаунты — включённые, с полным контекстом, как backfill. Это
больше не штатный способ: для тысячи аккаунтов цикл стоил бы тысячи
запросов. Запускайте его, когда нужно закрыть известный пропуск или
свериться, — не как службу.

```bash
alias lc='docker compose run --rm --user "$(id -u):$(id -g)" -v "$PWD/local:/app/local" api python -m app.collector'

lc check                       # что делает сервер при чтении вперёд: около 10 запросов, ничего не пишет
lc once --report local/reports/collector.json   # один цикл
lc status                      # где стоит каждый поток и насколько отстал; сервера не спрашивает

docker compose run -d --rm --name mtl-horizon-collector api python -m app.collector run   # по необходимости, раз в MTL_HORIZON_COLLECTOR_INTERVAL секунд; не как службу
docker logs -f mtl-horizon-collector
docker stop mtl-horizon-collector      # SIGTERM: цикл заканчивает страницу и выходит
```

В `compose.dev.yaml` коллектор остаётся отдельной службой профиля `collector`
(`docker compose --profile collector up -d collector`).

- **Первый старт.** Один цикл атомарно фиксирует для каждого потока стартовый
  леджер L0 — последний леджер сервера в этот момент; новая история начинается
  с L0+1. Чтобы продолжить после загруженного backfill, назовите его границу:
  `--start-ledger L`. Рестарт границу не двигает. Аккаунт, добавленный в
  список позже, получает свою границу в первом цикле после добавления; всё,
  что до неё, — история для backfill.
- **Страница, покрытие, чекпоинт и граница потока записываются одной
  транзакцией базы.** Цикл, остановленный лимитом, сигналом или сбоем,
  оставляет согласованное состояние; следующий продолжает.
- **Один поток не останавливает остальные.** Сбившийся поток спрашивается
  снова с паузой, которая удваивается с каждой неудачей (до суток). 429 с
  просьбой подождать дольше 15 минут останавливает цикл целиком.
- **Что сервер перестал хранить** (коллектор не работал дольше retention),
  помечается `unverifiable`: сервер при чтении вперёд молча начинает с
  самой старой записи и никакой ошибки не даёт.
- **Бюджет цикла** — `MTL_HORIZON_COLLECTOR_MAX_REQUESTS` запросов и девять
  десятых интервала по времени.
- **Кто читает источник.** Один коллектор на базу (блокировка в PostgreSQL).
  Коллектор, backfill и worker могут читать одновременно: темп у них один и
  держится в самой базе (`http_pace`), у событий приоритет, а читающий
  историю не голодает — пока события идут потоком, ему достаётся один
  запрос из десяти, а как только очередь пуста, достаётся весь темп. Темп
  действует в пределах одной базы: две установки с разными базами на одном
  сервере PostgreSQL никак не согласованы.

Коды возврата цикла: `0` — каждый поток дочитан до последнего леджера;
`1` — поток сбойнул; `2` — остановлен лимитом или сигналом.

| `MTL_HORIZON_DISCOVERY_INTERVAL` | нет | `0` | секунд между discovery-проходами; `0` — никогда, только командой |
| `MTL_HORIZON_PROVISION_INTERVAL` | нет | `60` | секунд между проходами worker по аккаунтам, их импорту и подпискам, пока события молчат |
| `MTL_HORIZON_HISTORY_SLICE_REQUESTS` | нет | `50` | сколько запросов может потратить один срез исторического импорта |
| `MTL_HORIZON_HISTORY_SLICE_SECONDS` | нет | `60` | сколько может длиться один срез |
| `MTL_HORIZON_ADMIN_SECRET` | для админки | — | секрет, которым открывается `/admin`; без него админка закрыта для всех |
| `MTL_HORIZON_ADMIN_SESSION_SECONDS` | нет | `43200` | сколько живёт сессия админки |
| `MTL_HORIZON_PUBLIC_ORIGIN` | нет | — | адрес, по которому установка доступна снаружи (`https://host`): cookie `Secure`, проверка `Origin` изменяющих запросов, ссылки исторического API |
| `MTL_HORIZON_API_ACCESS` | нет | `token`; в `compose.yaml` — `open` | кто читает исторический API: `open` — все (публичный архив), `token` — только с токеном |
| `MTL_HORIZON_API_TOKENS` | нет | — | токены исторического API через запятую; в режиме `token` без них API не читает никто |
| `MTL_HORIZON_LIVE_BUDGET` | нет | `0` | потолок HTTP-попыток к внешним серверам за прогон, общий для всех процессов; `0` — без предела |
| `MTL_HORIZON_HISTORY_CONTEXT` | нет | `parents` | что подгружается для записи при импорте истории: `parents` или `full`; живые события всегда приносятся целиком |

База создаётся для сети **public**. Если passphrase в настройках отличается,
`/ready` отвечает 503, а запись в базу отказывает: pubnet и testnet в одной
базе не смешиваются.

## Структура

```
app/
  api/          /health, /ready, /webhooks/notifier; подключает админку и исторический API
  storage/      схема (models), правила записи (upsert), покрытие (coverage),
                единственный писатель (writer, одна запись за раз — во всех процессах),
                привязка к сети, очередь заданий (jobs), журнал доставок (events),
                общий темп (pace), состояние серверов пула (pool_state),
                очередь исторического импорта (history_jobs), общее состояние служб (service_state)
  sources/      Horizon снаружи
    horizon.py             HTTP-клиент одного сервера: темп, повторы, дедлайн, проверка _links.next
    pool.py                пул серверов поверх клиента: кто отвечает, круг, cooldown, 404/410 у резервных
    horizon_records.py     REST-записи → строки базы, участники
    horizon_cursors.py     Total Order ID и курсоры по типам ресурса
    horizon_format.py      точные суммы, цены, время
  notifier/     форма webhook Operations Notifier (format.py), проверка подписи (signature.py)
                и клиент его API подписок (client.py)
  worker/       событийный сбор: берёт задания и приносит транзакции целиком
    loader.py              аренда, шаги контекста, повторы
    cli.py                 run, once, status, retry, events
  discovery/    discovery: проход по /accounts?asset= (scan.py), открытия trustline
                в сохранённой истории (events.py), команды run, status, on, off
  subscriptions/ желаемое состояние подписок из списков (desired.py), сверка с Notifier
                (reconcile.py), команды status, reconcile, adopt, release
  watch/        жизнь аккаунта: добавление и включение (accounts.py), один проход
                (provision.py), команды run, status, add-account, disable-account, enable-account
  history/      очередь исторического импорта: воркер (runner.py) и команды
                run, once, status, pause, resume, retry, enqueue
  pool/         проверка пула (check.py) и команды check, status
  admin/        админка: дверь (auth, door), общее для страниц (support), группы страниц (areas/),
                изменения списков (lists.py), шаблоны и статика
  tasks/        долговечные задачи: что делает каждая (kinds), исполнитель (runner)
  smoke/        смоук-тест живого Notifier (python -m app.smoke)
  history_api/ исторический API — пути Horizon из локального архива
  stats/        что читают страницы: импорт (imports), дашборд (dashboard), активность (activity)
  collector/    чтение вперёд: восстановление и контрольные сверки
    loader.py              чтение вперёд, граница и отставание потока, бюджеты цикла
    cli.py                 once, run, status, check
    check.py               что делает источник при чтении вперёд
  backfill/     загрузка окна леджеров
    cli.py                 команды
    config.py              YAML-список наблюдения
    jobs.py                из каких потоков состоит окно
    loader.py              чтение назад, контекст транзакций, чекпоинты
    store.py               страница → строки базы
    probe.py, verify.py    что говорит сервер против того, что в базе
alembic/        миграции
tests/          875 тестов; встроенный Horizon — tests/fake_horizon.py, встроенный Notifier —
                tests/fake_notifier.py (подписывает как он) и tests/fake_notifier_api.py (его API)
scripts/        sdk_probe.py, replay_window.py (прочитать сохранённое окно как источник и измерить загрузку)
docs/           архитектура, схема Horizon, отчёты этапов 01–06, исторический API, инструкция владельцу
```

Направление зависимостей: `worker`, `history` и `discovery` → `watch` →
`subscriptions` → `notifier` и `backfill` → `sources` → `storage`; `pool` и
`collector` — те же `sources` → `storage`; `admin`, `tasks`, `history_api`
и `stats` читают эти службы и базу, своих правил записи не имеют.
`notifier` знает только форму присланного и API подписок.
Подробности — в [`docs/architecture.md`](docs/architecture.md).
